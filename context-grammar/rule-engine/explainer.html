Context Grammar · Concept Explainer · 平易な日本語で

Rule Engine は
「翻訳機」です。

Brain に貯まった記憶も、Token で測った今の状態も、そのままだと UI に出せません。
Rule Engine が 「Token の集まり」 → 「UI への命令」 に翻訳します。
山城家の朝で、同じ命令が冷蔵庫・iPhone・CarPlay に違う形で映るのを追いかけます。

§1

まず根っこから — Rule Engine は「コンパイラ」

Brain（記憶）と Token（今の状態）はそのままでは UI を作れません。 人間で言えば「眠い」「電車の中」「片手」という事実があっても、画面の何をどう描くかまでは決まっていない。 その事実を "画面はこう描け" という命令に翻訳するのが Rule Engine です。

📥
Tokens IN
今の状態

8 つの Context Tokens の現在値。Brain から読まれた人物・予算・予定の情報も含む。

  • Cognitive Load = high
  • Form Factor = phone
  • Social Exposure = public
  • Autonomy Dial = Confirm
→
⚙️
Rule Engine
翻訳機

条件にマッチするルールを発火する。同じ入力なら必ず同じ出力を出す。気分で変わらない。

  • if Cognitive Load = high → density: minimal
  • if Form Factor = phone → layout: vertical
  • if Social Exposure = public → hide: prices
  • 23 個の AX Pattern を組み合わせる
→
📤
UI Commands OUT
画面への命令

どの surface でも読めば描ける、抽象的な「描き方の指示書」。デバイスは関係ない。

  • density: minimal
  • items: 1
  • tone: gentle
  • hide: [price, calorie]
覚え方: Brain は本、Agent はシェフ、Rule Engine は注文票を書く仕組み。 本もシェフもあるけど、その間で「テーブル4番にこれを出せ」と紙に落とす役がいないと、料理は届かない。
もう一つ大事なこと: Rule Engine は決定論的（deterministic）。 同じ Token の組み合わせを入れたら、いつ・誰が・どのデバイスから呼んでも、必ず同じ命令が出る。 気分で変えないことが、家族みんなの信頼の土台になる。
§2 · 中身

Tokens IN → UI Commands OUT を解剖する

Rule Engine の中では、何が起きているのか。3 つの工程に分けると、迷子になりません。

① 読む
Token を集める

8 つの Token の今の値を集計。さらに Brain から関連する事実（家族のアレルギー、今月の予算、来週の予定など）を取ってくる。

② 当てる
ルールを発火する

条件式（if 〜 then 〜）を全件チェックして、当てはまるものを発火させる。複数ヒットしたら優先順位で重ね合わせる。

③ 出す
命令にまとめる

発火した結果を 1 個のui.command（命令オブジェクト）にまとめて吐き出す。デバイスはまだ知らない。

ポイント: Rule Engine はデバイスを知らない。 「冷蔵庫だから large」「iPhone だから vertical」と書くのは Rule Engine の仕事じゃなくて、Token（Form Factor）が伝える事実。 Rule Engine は「Form Factor=phone なら vertical」というルールを発火するだけ。
§3 · 比喩

レストランで考えてみる — 注文票の仕組み

Rule Engine をレストランの裏側に置き換えると、一発で見えます。

🍽 厨房の注文票システム

📥 入力 = ホール係のメモ

客の事実を集めたメモ。

・テーブル4番
・ランチセット注文
・ピーナッツアレルギー
・お子様連れ・急ぎ

⚙️ 翻訳機 = 注文票システム

メモを「厨房が読める指示書」に変換。

・アレルギー → ソース抜き
・お子様 → 量を 70%
・急ぎ → 先に出す
・毎回同じルールで翻訳

📤 出力 = 厨房チケット

厨房が一目で読める指示書。

・main: pan-seared chicken
・sauce: hold
・portion: 70%
・priority: rush
🎫 厨房チケット (= ui.command)
TABLE 4 · main:chicken · sauce:hold · portion:70% · priority:rush
お母さんが「ピーナッツアレルギー」と言っても、シェフはそのまま聞きません。 間に注文票システムが入って、「ソース抜き、ナッツ系トッピング NG、別フライパン」という厨房用の指示に翻訳します。
そして同じチケット 1 枚から、和食ステーションは煮物として、洋食ステーションはチキンとして、キッズメニューはうどんとして仕上げる。命令は 1 つ、出し方は surface 次第。
§4 · 実例

山城家の朝 7:02 AM — 同じ命令、3 つの surface

お母さん Mai が朝、子どもたちと格闘している最中に冷蔵庫の前を通る。Token がこう変わって、Rule Engine がこう動きます。

「あー、今日 Sota の弁当の中身どうしよう…時間ないんだけど」

— Mai (38歳・二児の母) · 火曜 7:02 AM, キッチン

1 7:02 AM の Token 状態 Tokens IN
Mai が冷蔵庫の前に立った瞬間、システムが収集した8 つの Context Tokens の現在値はこう。
📥 8 Context Tokens · 7:02 AM
  • ① Physical State 立っている・キッチン・両手は弁当箱で塞がっている
  • ② Cognitive Load HIGH（朝・カレンダー過密・直近 5 分で 3 件のタスク切替）
  • ③ Social Exposure family（家族だけ・公開度 low）
  • ④ Priority Weight 「弁当を時間内に作る」が最優先・他は後回し
  • ⑤ Form Factor fridge（Samsung Family Hub の前）
  • ⑥ Feasibility 残り 13 分で家を出る・調理時間 8 分以内
  • ⑦ Autonomy Dial Suggest（提案だけ・決めるのは Mai）
  • ⑧ Disclosure Dial 家族の食事履歴・冷蔵庫在庫 → AI に開示済み
さらに Brain から：Sota はピーナッツアレルギー、昨日も鮭弁・連続は避けたい、冷蔵庫に卵 6 個・ブロッコリー・ハム残あり といった事実が読まれて添えられる。
2 Rule Engine がルールを発火する Engine
Rule Engine は23 の AX Patternに対応するルールセットから、今の Token 状態にマッチするものを選び出す。 朝 7:02 にこの状態だと、こんなルールが同時に発火する。
⚙️ 発火したルール（抜粋）
  • if Cognitive Load = high → density: minimal, items: 1
  • if Feasibility < 10min → filter: only ready-fast recipes
  • if Brain.allergy(Sota) = peanut → exclude: peanut, sesame-cross
  • if Brain.history.yesterday = salmon → deprioritize: salmon
  • if Autonomy Dial = Suggest → action: propose only, no auto-cook
  • if Physical State = hands-busy → input: voice-first, tap fallback
→ 6 ルール発火 · 命令を 1 つに合成して emit へ
3 ui.command を emit する Emit
ルールたちが合成された結果、1 個の抽象的な命令オブジェクトが吐き出される。 この時点では「冷蔵庫の何 px に何を描くか」はまだ決まっていない。
📤 emit · ui.command
intent: suggest_lunchbox
density: minimal
items: 1
tone: gentle
input: voice-first
candidates: [egg-ham-broccoli, omelet-rice]
exclude: [peanut, sesame-cross, salmon]
time-budget: 8min
decision-by: user (Suggest mode)
4 3 つの surface が同じ命令を別々にレンダリングする Render
ここがポイント。同じ ui.commandを、それぞれの surface が自分の文法で描く。 Rule Engine は何も書き換えていない。
🧊
Samsung Family Hub
「卵ハム弁当はどう？8 分で作れます」
大きな写真 1 枚 + 音声『はい』ボタン
density:minimal · items:1 を、大画面では「写真 + ひと言」で表現。両手塞がっているから音声受け。
📱
Mai の iPhone
通知バナー：「🥚 卵ハム弁当 · 8min」
タップで詳細・スワイプで却下
同じ items:1 を、小画面では 1 行通知に圧縮。tone:gentle だから赤バッジは出さない。
🚗
CarPlay（あとで）
音声のみ：「今朝の弁当、卵ハムで作ったよ」
運転中はサマリーのみ・操作 UI なし
同じ candidates を、CarPlay では事後報告に変換。Form Factor=car では tap input 自体が成立しない。
3 つとも、Rule Engine の出力は 1 個。違いはレンダリング層（surface 側）が吸収している。 だから Brain は「冷蔵庫用」「iPhone 用」と分けて持たなくていい。Brain は 1 つ、surface は無限。
5 7:35 AM · 状態が変わると emit も変わる Tokens change
30 分後、Mai は車に乗っている。Token がこう変わる。
  • ① Physical State 運転中・両手はハンドル
  • ② Cognitive Load 運転で MEDIUM・新規タスクは禁止
  • ⑤ Form Factor car / CarPlay
  • ⑥ Feasibility 会議まで 25 分
Rule Engine は同じルールセットを、新しい Token 値で再発火する。出てくる命令はまったく違う。
📤 7:35 AM の emit
intent: report_lunchbox_done
density: audio-only
items: 1-line summary
input: disabled (driving)
tone: neutral
→ 同じ Rule Engine、違う Token、違う UI 命令
気づきポイント: Rule Engine は1 行も書き換えていない。Token の値が変わっただけで、出力が変わる。 これが「決定論的 = 同じ入力なら同じ出力」と「文脈に応じて変わる UI」が両立できる仕組み。 人間の気分で動くのは Token の値（Cognitive Load や Physical State）であって、Rule Engine そのものは静かに同じ仕事を続ける。
§5 · 位置づけ

なぜ Rule Engine が Brain と UI の「橋」なのか

Brain は記憶、UI は画面。中間に Rule Engine がいないと、両側が直接つながって泥沼になります。

Brain ↔ Rule Engine ↔ UI surfaces
Rule Engine がない世界を想像してみる: Brain が直接 UI に「冷蔵庫の右上に卵の写真を 240 px で出して」と指示するなら、UI が変わるたびに Brain を書き換えないといけない。 Samsung が新型冷蔵庫を出すたび、Apple が画面サイズを変えるたび、Brain を作り直し。地獄。
Rule Engine が間に立つと、Brain は「弁当を提案したい」と抽象的に言うだけで済む。
Brain がデバイス越しに portableになるのは、Rule Engine という翻訳層があるから。
23 の AX Pattern との関係: AX Pattern は「Silent Resolution」「Confirm before commit」「Ambient Notice」など、UI の小さな型紙。 Rule Engine は、発火した条件にマッチする型紙を組み合わせて 1 つの ui.command を作る。 Pattern = 単語、Rule Engine = 文を組む文法。だから "Context Grammar" と呼んでいる。
§6 · これからどうするか

推奨アクション

Rule Engine の正体が見えたら、ポートフォリオで使うときは 3 つを徹底する。

1
「Token IN → emit OUT」のフォーマットで書く
Rule Engine の章で、Token 状態を箇条書き → 発火ルール → ui.command という同じ並びを必ず守る。これが読者の「あ、また同じパターンだ」という認知の足場になる。
2
「同じ命令、違う surface」を毎回見せる
1 つの ui.command を Family Hub / iPhone / CarPlay の3 つで描き分ける図を、各プロジェクトに最低 1 つ入れる。これが「Brain は portable」という主張の証拠になる。手抜きすると概念が空疎になる。
3
「決定論的」を翻訳して説明する
読み手に「deterministic」とそのまま書かない。「同じ条件なら毎回同じ答えを返す。気分で変わらない。」という日本語に翻訳して書く。家族の信頼は「予測できること」から生まれる、という文脈で必ず触れる。
§7 · よくある混乱

よくある質問を整理する

Q1. Rule Engine は AI（LLM）なの？
違います。 Rule Engine は決定論的なルールの束。同じ入力 → 同じ出力。LLM は同じ入力でも毎回違う言葉を出す（生成的）。 Context Grammar の世界では、判断の骨格は Rule Engine、自然言語の表面は LLM と役割を分けている。 「卵ハム弁当を提案する」という骨はルール、「あ、お疲れさま。卵ハムどう？」という言葉遣いは LLM が当てる。
Q2. 同じ Token なら毎回同じ UI が出るの？飽きない？
同じ命令は出ます。 でも Token は毎瞬変わる。Cognitive Load は時刻と直近 5 分のタスク数で揺れる。だから実際の UI は飽きない。 飽きるとしたら、それはToken を取れていないサイン。「目の前に立っている人が違う」「時間帯が違う」という事実が Token に反映されていれば、UI は自然に変わる。
Q3. ルールが複数ヒットしたらどうする？
優先順位（priority）で重ね合わせる。 例：「Cognitive Load=high なら density:minimal」と「Social Exposure=public なら hide:price」が両方発火したら、両方とも適用する（互いに矛盾しないから）。 矛盾する場合は Priority Weight Token が裁定する。「弁当が最優先」と Mai が言っているなら、見た目より速さを優先するルールが勝つ。
Q4. ui.command って具体的に何？JSON？
抽象的な構造体。 実装は JSON でも protobuf でも何でもいい。大事なのは「intent / density / tone / candidates / constraints」みたいな共通語彙を持っていること。 この語彙さえ surface 側が読めれば、新しいデバイス（壁面ディスプレイ、AR グラス、ロボット…）が出ても、Brain と Rule Engine をいじらずに対応できる。
Q5. Rule Engine と AX Pattern Library はどう違う？
AX Pattern = 部品、Rule Engine = 組み立て工場。 AX Pattern Library には 23 個の「型紙」が並んでいる（Silent Resolution / Confirm before commit / Ambient Notice / Disposable Brain など）。 Rule Engine は、Token の状態に応じてどの型紙を選ぶか・どう組み合わせるかを決める。 Pattern が単語、Rule Engine が文法、出てくる ui.command が文 — そう覚えると関係が綺麗に整理できる。
