Position in the stack

6 Signals & 2 Dials in. One command out.

Context Grammar needs a place where state becomes behavior.

Brain remembers facts. Situation Signals describe the observed situation, while Relationship Dials define relationship boundaries. The Rule Engine decides what the interface should do next: reduce detail, ask for approval, hide sensitive data, switch to voice, or show one clear recommendation.

In restaurant terms, Situation Signals and Relationship Dials are the waiter's notes: table, allergy, kids, hurry. The Rule Engine is the ticket system that translates those notes into a kitchen instruction: hold the sauce, rush the order, reduce the portion. The ui.command is that standardized ticket.

The core translation

The Rule Engine compiles context.

Signals & Dials IN

Current state

Cognitive Load = high. Form Factor = phone. Social Exposure = public. Autonomy Dial = Confirm. Brain adds allergies, budgets, schedules, and history.

Rule Engine

Translator

Runs every matching if/then rule. Non-conflicting rules compose. Conflicts go through a clear priority order.

ui.command OUT

Screen instruction

density: minimal. items: 1. tone: gentle. hide: price and calories. input: voice-first.

Raw facts do not tell a screen what to draw. "Tired," "on the train," and "one hand free" have to become interface behavior.

The Engine translates those facts into a concrete instruction. The surface renderer still decides whether that instruction becomes a fridge card, a phone notification, a car voice response, or a dashboard row.

Deterministic: the same context state always returns the same ui.command, no matter who calls it or which device asks.

Internal anatomy

Read, match, emit.

01

Read

Collect all 6 Situation Signal values, 2 Relationship Dial settings, and relevant Brain facts: allergies, budget, brand constraints, research signals, and live session context.

02

Match

Check each if/then condition against the current state. Fire every match. Resolve contradictions by priority.

03

Emit

Merge all fired results into one ui.command. Device-specific rendering still happens later, inside each surface.

Live example

Yamashiro household, 7:02 AM.

"What should I put in Sota's lunch box? I'm running out of time."

Context state is collected

Mai is standing in the kitchen, both hands occupied with lunch boxes. Cognitive Load is high. The top priority is finishing lunch on time. Form Factor is a Samsung Family Hub fridge. Feasibility says 13 minutes to departure and an 8 minute cooking limit.

Brain reference: Sota has a peanut allergy. Yesterday was salmon. The fridge has eggs, broccoli, and ham.

Matching rules fire

if Cognitive Load = high → density: minimal, items: 1. if Feasibility < 10min → only ready-fast recipes. if Brain.allergy(Sota) = peanut → exclude peanut and sesame-cross. if Physical State = hands-busy → voice-first input.

Restaurant model: the ticket system converts "peanut allergy, kids, hurry" into "hold sauce, rush, safe station."

The Engine emits one command

intent: suggest_lunchbox. density: minimal. items: 1. tone: gentle. input: voice-first. candidates: egg-ham-broccoli and omelet-rice. exclude: peanut, sesame-cross, salmon. decision-by: user, because Autonomy Dial is Suggest.

Three surfaces render it differently

Fridge: "Egg and ham lunch box? Ready in 8 min." Phone: "Egg and ham, 8 min." CarPlay later: "Made the egg and ham box this morning." One command, three renderers.

Signals change, command changes

At 7:35 AM, Mai is driving. Physical State becomes driving, Form Factor becomes car, and input is disabled. The same ruleset now emits an audio-only summary instead of an interactive fridge suggestion.

The Rule Engine did not change. Only the signal values changed, so the output changed.

This is how deterministic rules and adaptive UI can coexist: the human situation lives in the Signals & Dials; the Engine quietly runs the same job every time.

Scale

One Engine for one Brain or five.

The Rule Engine is scale-agnostic. A household Brain and an enterprise stack of Brains both resolve into one synthesized context state, and the Engine runs the same rules either way.

P1 may use a single Context Brain. P4 may use Org Brain, Brand Brains, Research Brain, Project Master Brain, and Project Brains. Each contributes facts from Identity, Learning, and Now to a context bus.

The Engine never counts Brains. It translates the final context state. Same Engine, different Brain configuration, different output only when the Signals differ.

Technical depth

Rule syntax, schemas, and conflict resolution.

context.yml

Signals + Brain schema

Defines types, valid values, and defaults for all 6 Situation Signals and 2 Relationship Dials, plus Brain references such as brain.allergy and brain.history.yesterday.

rules.yml

33 Behavior Rules

Maps conditions to outputs. Each rule has a priority from 0 to 999 and tags that connect it to AX Patterns.

ui.command

Output vocabulary

intent, density, items, tone, candidates, exclude, input, time-budget, and decision-by become the shared dictionary every surface reads.

rules.yml excerpt 
- id: cog_load_minimal
  when: { cognitive_load: high }
  then:
    density: minimal
    items: 1
  priority: 80
  tags: [A2-cognitive-scaling]

- id: hands_busy_voice
  when: { physical_state: hands_busy }
  then:
    input: voice-first
    fallback: tap
  priority: 70
  tags: [A4-input-mode-switch]

- id: disclosure_guard
  when:
    disclosure: hidden
    autonomy: { gt: Confirm }
  then:
    constraint_violation: true
    reset_to: Confirm
  priority: 999
  tags: [E5-trust-breach-recovery]
Conflict arbitration
Stage Arbiter Criterion
1 Priority Weight Signal The user's current priority, such as "finish the lunch box," wins first.
2 Rule priority value Static numeric weight from 0 to 999. Trust-related guardrails use the highest priority.
3 Brain Learning Layer Past decisions for this conflict type break the tie when the first two stages are not enough.

Non-negotiable constraint: Disclosure = hidden and Autonomy > Confirm cannot coexist. Full delegation without disclosure is logically impossible, so the Engine resets Autonomy to Confirm.

Deterministic = testable: given cognitive_load: high and form_factor: phone, expect density: minimal and layout: vertical.

Parts + assembly

AX Patterns are the pieces the Engine assembles.

D1-D6

Delegation

AI handles more of the work as trust and disclosure allow.

E1-E5

Escalation

AI gives control back when confidence, capability, or trust breaks down.

A1-A8

Adaptation

Presentation changes as context, device, or disclosure changes.

X1-X4

Enterprise

High-stakes systems add audit, source, edit, and autonomy controls.

Total: 23 patterns. The Engine does not call a pattern by name; it fires matching rules. The resulting ui.command may contain one pattern or a composition of several.

Example: Silent Resolution combines D4 Omakase Mode, D6 Dynamic Friction, E5 Trust Breach Recovery, and A2 Cognitive Scaling. The user experiences one smooth morning. The Engine assembled four behavioral parts.

Q&A

Common questions.

Is Rule Engine an AI model?

No. The Rule Engine is deterministic. An LLM may write final wording, but the decision skeleton comes from rules.

Will deterministic rules make the UI repetitive?

The command is consistent, but Signals change. Cognitive Load, Form Factor, Social Exposure, and Feasibility shift as the user moves through the day.

What exactly is a ui.command?

A structured instruction. It can be JSON, protobuf, or another format. What matters is the shared vocabulary every surface can render.

Rules become useful when memory and patterns stay separate.
