Context Grammar — Reference

Specs

Specs は、Context Grammar を読むための文章から、デザイナーがレビューでき、機械が実行できる portable contract へ変える。

01 1つのUX上の意味には、Narrative と machine Spec の2つの顔がある。
02 YAML、JSON Schema、TypeScript types が契約を持ち運べる形にする。
03 Simulator は同じファイルをブラウザ上で実行する。

Quick overview

Spec は、UX scene の機械可読版である。

01

同じ意味

Portfolio narrative と machine Spec は、同じ context を別の読者向けに書いたものだ。

02

Device-neutral

iPhone、冷蔵庫、watch、car、desktop が、同じフィールドを別々の surface behavior に翻訳する。

03

Confidence matters

confidence が低ければ聞く方向へ、高ければ bounded risk の中で割り込みを減らす方向へ進む。

04

Versioned contract

古い surface を壊さずに新しいフィールドを追加できる。既存の意味は維持される。

Restaurant model

メニューとレシピカード。

レストランが新しい支店を出すとき、シェフは詩的な説明を送らない。鶏もも 180 g、油温 78 C +/- 2、調理 90 min、塩分 1.2% のようなレシピカードを送る。

メニューは客が料理を理解するためのもの。レシピカードは、どの厨房でも同じ料理を再現するためのもの。同じ料理、2つの言語、2人の読者。

Context Grammar も同じだ。Portfolio chapter は scene をデザイナーに説明する。Spec は iPhone、冷蔵庫、car dashboard がその scene に対して動くための契約になる。

Two faces of every Signal

Narrative は会話の言語。Spec は実行の言語。

Narrative

Human face

「7:02 AM - 舞は出勤準備をしながら弁当を作っている。」感情、背景、物語が入り、レビューする人が状況を理解できる。

Spec

Machine face

cognitive_load: 0.82、physical_state: hands_busy、confidence、source、projection rules が device behavior を決める。

Step by step

火曜の朝が Spec になる。

「7:02 AM。舞は息子の弁当を作りながら出勤準備をしている。Cognitive load は高い。」

Narrative を書く

人間が読める文を書く。文脈、感情、物語はあるが、それだけでは iPhone がどう振る舞うべきかは決まらない。

Signal を見つける

Cognitive Load は high、Physical State は hands busy、Social Exposure は family-private、Form Factor は kitchen iPhone。

Spec を書く

同じ scene を、signal value、confidence、source、projection rules を持つ structured data にする。

Device が render する

iPhone は voice と one step を使う。CarPlay なら voice only になる。Spec は変わらず、surface translation だけが変わる。

Narrative と Spec が一致する

「舞は overwhelmed で手が塞がっている」は、cognitive_load=0.82 と physical_state=hands_busy に対応する。不一致は design bug。

Example JSON contract 
{
  "context_id": "mai-tuesday-morning",
  "spec_version": "v1.2",
  "tokens": {
    "cognitive_load": {
      "value": 0.82,
      "confidence": 0.74,
      "source": "calendar+activity+time-of-day"
    },
    "physical_state": {
      "value": "hands_busy",
      "confidence": 0.91,
      "source": "kitchen-presence+cooking-activity"
    },
    "social_exposure": {
      "value": "family_private",
      "confidence": 0.99
    }
  },
  "projection_rules": {
    "voice_priority": true,
    "text_density": "low",
    "interaction_steps": "max_1"
  },
  "ui": {
    "command": {
      "mode": "confirm",
      "label": "Book the piano trial",
      "requires_human": true
    }
  }
}

Compile once, render anywhere

1つの Spec が6つの device に届く。

Surface Spec から読むもの Behavior
iPhone kitchen cognitive_load=0.82, hands_busy=true Voice-first、one step、text UI は隠す。
Family Hub fridge 同じ signal values 大きな icon と one tap、copy は最小限。
CarPlay 同じ signal values Voice only。visual UI は出さない。
Watch 同じ signal values Haptic と voice。screen を前提にしない。

Universal contract

同じ Specs がすべての Brain から出てくる。

Specs は Brain ごとではなく Signal・Dial ごとに定義される。Person Brain、Domain Brain、Household Brain、Project Brain のどれが出力しても、構造は同じ。

Brain は memory entity。Spec は output format。 Home Brain から Enterprise Brain に変わっても、変わるのは memory model であって Spec schema ではない。

Implementation proof

契約は、files、types、rules として存在する。

Human authoring

YAML specs

context-tokens-spec.yaml、ax-patterns-spec.yaml、brain-schema.yaml、design-rules.yaml は、designer と implementor がレビューできる。

Machine enforcement

Schema + SDK + ui.command

context-grammar.schema.json が ContextState を検証する。context-grammar.d.ts と SDK が typed evaluation を提供する。ui.command は Spec が具体的な UI action を要求できる証明である。

Forward compatibility rules
Rule Reason
Add new fields 常に可能。古い surface は unknown fields を無視する。
Delete fields 不可。alias として残す。
Change a field's meaning 不可。古い名前を再定義せず、新しい概念に新しい名前を与える。

Spec anatomy

すべての Spec が持つべき5つのフィールド。

Field 宣言するもの Example
token_id どの Signal / Dial を記述しているか。 cognitive_load
value Signal の現在値。number、enum、range。 0.82
confidence 推定の確かさ。 0.74
source 値がどこから来たか。 calendar+activity+time-of-day
projection_rules UI layer に渡す hints。 voice_priority: true
