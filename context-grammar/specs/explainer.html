Context Grammar · Concept Explainer · 平易な日本語で

Specs は
機械が読むレシピ。

人間に説明する「物語」と、機械が実行する「設計図」は別ものです。
Yamashiro 家の朝のシーンが、どう JSON の Spec になり、6つのデバイスに同じ意味で届くかを追跡します。

§1

Specs って何？ — 機械が読める Context Grammar

Context Grammar の Token、Brain、Rule Engine は、人間が読むときは物語として書かれています。「Mai は朝7時、認知負荷が高い」みたいに。
でもこのままでは、iPhone も冷蔵庫も Nest Hub も動けない。彼らに渡すには、もう一つの顔が必要です。それが Spec。

一言で: Spec とは、Context Grammar の概念を 機械が読める JSON のかたちで書き直したもの。意味は同じ、フォーマットだけ違う。
§2 · 二つの顔

物語と Spec — Token は二つの顔を持つ

すべての状況シグナルと関係性ダイヤルには二つの書き方があります。読み手が違うから、書き方も違う。同じ事実を、人間用と機械用の両方で表現します。

📖
Narrative
物語の顔

人間（デザイナー・読者・経営層）が読むため。文章で、文脈と感情を含めて書く。

  • 「7:02 朝、Mai は子供の弁当を作りながら出勤の支度をしている」
  • 感情・背景・物語が乗る
  • レビューや議論で使う
  • portfolio の本文がこれ
vs
⚙️
Spec
機械の顔

AI とデバイスが読むため。JSON で、値の範囲・確からしさ・出典を構造化して書く。

  • cognitive_load: 0.82
  • 値・範囲・confidence・source
  • 実装で使う
  • YAML / JSON ファイル
覚え方: 物語は会話のための言語。Spec は実行のための言語。同じ事実を、違う読み手のために二重に書く。
Context Grammar の portfolio に出てくる「7:02 Mai は…」という文章は物語。その裏には必ず対応するSpecがあります。
§3 · 比喩

レストランで考えてみる — メニューと厨房カード

Brain が「本」、Agent が「シェフ」だったように、Spec もレストランの世界で説明できます。

🍽 同じ料理を、二通りの言葉で書く

📖 Narrative = メニューの説明文

お客様に渡すための言葉。雰囲気・物語が乗る。

・「鶏のコンフィ、低温でゆっくり仕上げた一皿」
・読み手はお客様
・感じ取る、想像する
・グラム数は書かない

⚙️ Spec = 厨房の標準レシピカード

シェフが正確に再現するための言葉。曖昧さゼロ。

・chicken_thigh: 180g
・oil_temp: 78°C ± 2
・cook_time: 90min
・salt_ratio: 1.2%
お客様に「chicken_thigh: 180g, oil_temp: 78°C」と読み上げたら台無し。
シェフに「低温でゆっくり」と言ったら、78°C なのか 65°C なのか分からなくて料理が崩れる。
Spec は厨房カード。物語はメニュー説明。同じ料理の、違う書き方。
大事なポイント: 厨房カード（Spec）が標準化されているから、銀座店・京都店・LA 店でも同じ味が出せる。
Spec が標準化されているから、iPhone・冷蔵庫・CarPlayでも同じ意味の UI が出せる。これが Spec の本当の値うちです。
§4 · 変換

Yamashiro 家の朝が、Spec になる瞬間

実際の portfolio の文章を、JSON の Spec に変換していきます。ステップごとに何が起きているかを見ましょう。

「7:02 AM。Mai は息子の弁当を作りながら、自分の出勤準備もしている。
子供がリビングで叫んでいる。認知負荷は高い。」

— P1 Living Home · ある火曜の朝

1 物語として書く（人間用） Narrative
これは portfolio の本文に出てくる文章。読み手はデザイナー、レビュアー、Takao 自身。
文脈・感情・物語が含まれていて、人間が一読で「あ、Mai は今、忙しいんだな」と理解できる。
でもこの文章だけでは、iPhone はどう振る舞えばいいかは決まらない。
2 物語の中の Token を見つける Tokenize
この文章には、Context Grammar の Token が埋まっている。デザイナーが拾い出すと:
  • Cognitive Load — 「弁当 + 出勤準備 + 子供の叫び声」 → 高い
  • Physical State — 「料理中、両手がふさがっている」
  • Social Exposure — 「家、家族のみ」 → プライベート
  • Form Factor — 「キッチンの iPhone」
物語は4つの Token を暗黙のうちに含んでいる。次のステップで、これを明示する。
3 Spec として書く（機械用） Spec / JSON
同じ物語を、機械が読める JSON に書き直す。意味は同じ、フォーマットだけ違う。
// yamashiro-mai-0702.json
{ "context_id": "mai-tuesday-morning", "timestamp": "2026-04-30T07:02:00+09:00", "spec_version": "v1.2", "tokens": { "cognitive_load": { "value": 0.82, // 0.0–1.0 scale "confidence": 0.74, "source": "calendar+activity+time-of-day" }, "physical_state": { "value": "hands_busy", "confidence": 0.91, "source": "kitchen-presence + cooking-activity" }, "social_exposure": { "value": "family_private", "confidence": 0.99, "source": "location=home + bluetooth=family-only" }, "form_factor": { "value": "iphone-15-kitchen", "confidence": 1.00 } }, "projection_rules": { "voice_priority": true, "text_density": "low", "interaction_steps": "max_1" } }
4 AI と デバイスがこの Spec を読む Render
iPhone の Voice Agent はこの Spec を読み、判断する:
cognitive_load = 0.82, hands_busy = true → 文字 UI を出さない、音声で1ステップ完結させる。

もし Mai が同じ瞬間に CarPlay にいたら、CarPlay はもっと違う読み方をする。
でもSpec は同じ。各デバイスが自分の能力に合わせて翻訳するだけ。
5 物語と Spec が一致していると確認できる Result
物語: 「Mai は忙しい朝、両手がふさがっている。」
Spec: cognitive_load=0.82, physical_state=hands_busy

同じ事実の、違う表現。 どちらも嘘じゃない。だから portfolio の物語と、実装の挙動が必ず一致する。
→ Narrative ≡ Spec (同じ意味、別フォーマット)
気づきポイント: portfolio の文章を 1段ずつ「これは何の Token？値は何？」と問い直すと、Spec が自然に出てくる。
逆に Spec から出発しても、その値を文章に直せば必ず物語が再現できる。双方向に翻訳可能なのが Context Grammar の仕組みです。
§5 · 移植可能性

一つの Spec が、6つのデバイスに同時に届く

Spec の本当の値うちは、compile once, render anywhere — 一度書けば、どのデバイスでも同じ意味で表示できることです。Brain と Token はデバイス依存しない。Spec がそれを保証します。

📐 同じ Spec(cognitive_load=0.82, hands_busy=true)を読んだ各デバイスの振る舞い
📱
iPhone (キッチン)
音声で1ステップ完結。文字 UI は隠す。
❄️
Samsung Family Hub
大きな絵文字 + 1タップ。文字は最小限。
🚗
CarPlay
完全音声。視覚 UI は無効化。
🏠
Nest Hub
音声 + 大きなビジュアル確認。
⌚
Apple Watch
触覚 + 音声。ガラスは見ない前提。
💻
MacBook (書斎)
逆に full UI で表示（このコンテキストでは出ない）。
キーポイント: Spec を書いた人は、iPhone のことも、CarPlay のことも、冷蔵庫のことも考えていない。
"cognitive_load=0.82" としか書いていない。各デバイスが自分なりに翻訳する。
だから新しいデバイス（XR グラス、車内 HUD…）が増えても、Spec は書き直さない。デバイス側が新しい翻訳ルールを足すだけ。
これが Context Grammar が "implementation-agnostic"（実装に縛られない）と言える理由。
Brain はどこにあってもいい。Spec はどんなデバイスでも読める。設計者は「意味」だけに集中できる。
§6 · 進化させる

v1 → v2 → v3 — 古い surface を壊さずに新 Token を足す

Context Grammar はずっと進化します。新しい Token、新しい Dial、新しい AX Pattern が追加される。でも 2026 年に作った冷蔵庫の UI が、2030 年の Spec で動かなくなるのは困る。だから Spec はバージョンを持ちます。

📜 Spec バージョンの歴史（実例）
v1.0
初期 7 Token。 Cognitive Load / Physical State / Social Exposure / Priority Weight / Form Factor / Feasibility / Synchro Rate（Autonomy の前身）。2025-12 リリース。
v1.2
Synchro Rate → Autonomy Dial に改名。 仕組みは同じ。old field名は alias として残すので、v1.0 を読んでいる古い surface も壊れない。
v2.0
Disclosure Dial 追加 → 8項目に。 古い surface は Disclosure を読まなくても動く（デフォルト値が入る）。新しい surface だけが Disclosure を読んで挙動を変える。
v2.3
Substitution Modes を Spec に追加。 Exact / Flexible / Exploring / Surprise の 4 モードが選択可能に。古い P1 v1 の冷蔵庫 UI は Exact のまま動く。
v3.0 (予定)
6つの状況シグナルと2つの関係性ダイヤルへの明確な分離と、Multi-Person Orchestration の一級概念化。 状況と関係性の役割を分離。1つの Spec で家族全員の状態を表現する。v2 を読む surface は引き続き 1人ぶんだけ抽出して動く。
3 つのルール:
① 新フィールドの追加 OK（古い surface はそれを無視するだけ）
② フィールドの削除 NG（古い surface が壊れる）→ alias で残す
③ 値の意味を変える NG → 新しい名前にする
これをforward-compatibility（前方互換性）と言います。Spec はこのルールを必ず守る。
§7 · 解剖

Spec に必ず入っている 5 つのフィールド

どの Spec も、必ずこの 5 つを持ちます。これが揃っていれば、機械が読めて、レビューでき、進化させられる。

フィールド 意味 例
token_id どの Token か cognitive_load
value その Token の値（数値・列挙・範囲） 0.82（0.0–1.0 スケール）
confidence どれだけ確からしいか 0.74（74% の自信）
source その値がどこから来たか calendar+activity+time-of-day
projection_rules UI 側にどんなヒントを渡すか voice_priority: true
confidence が大事: Cognitive Load は estimation（推定）なので、常に 100% ではない。70% の自信しかなければ、その値を 70% としてしか扱わない。
AI はこの confidence を見て、「自信がないときは聞き返す」「自信があるときは黙ってやる」を切り替えられる。これが Autonomy Dial の動作根拠になる。
§8 · これからどうするか

Spec を使いこなすための 3 つのステップ

Spec の概念が分かったら、portfolio や実装で実際にどう使うか。

1
portfolio の物語を書くたび、Spec を裏で書く
P1 / P2 / P3 の本文を書くとき、その横に scene-spec.json を1ファイル作る習慣をつける。物語と Spec が常にペアで存在することを保証する。物語だけがあって Spec がない章は、実装できない章 ＝ 物語が曖昧という証拠。
2
Spec バージョンを Git で管理する
specs/v1/ specs/v2/ のようにフォルダを分け、各 Token の定義を明示。古い surface が古い Spec を読んでいても壊れないように、削除ではなく alias で扱う。これが forward-compatibility の実装。
3
レビューは "narrative ≡ spec" で行う
portfolio をレビューするとき、文章だけ読むのではなく、対応する Spec を見て「この物語の値は本当にこれか？」を確認する。物語と Spec がズレていたら、片方が嘘をついている。両方を一致させると、デザインが嘘をつかなくなる。
§9 · よくある混乱

よくある質問を整理する

Q1. Spec を書くのはデザイナー？エンジニア？
デザイナーが先に書きます。 Spec は実装の詳細ではなく意味の宣言。「この瞬間の認知負荷は 0.82 です」と決めるのは、シーンを設計したデザイナーの仕事。エンジニアはその Spec を各デバイスでどう翻訳するかを実装する。役割は分担されているが、Spec はデザイン側の成果物。
Q2. JSON じゃなきゃダメ？YAML や TOML でもいい？
フォーマットはどれでも OK。 JSON は機械が読みやすい、YAML は人間が読みやすい、というだけの違い。Context Grammar の Spec は「5つのフィールドが揃っていれば」どの形式でも有効。実際の design-rules.yaml は YAML で書かれている。重要なのは構造、形式じゃない。
Q3. confidence が低いとき AI はどうするの？
聞き返すか、黙って待ちます。 たとえば cognitive_load.confidence = 0.45 なら、「Mai は今、忙しい？」と最小限の確認をする（Autonomy Dial が Suggest 寄りに振れる）。confidence = 0.95 なら何も聞かずに動く（Auto に振れる）。Spec の confidence が、AI の遠慮量を決めている。
Q4. 物語と Spec が食い違ったらどっちが正しいの？
食い違いがある時点で、デザインが間違っています。 物語は読者用、Spec は機械用ですが、同じ事実の二つの書き方であるべき。食い違ったら、どちらかが嘘をついている。両方を見直して合わせます。レビューでこれを必ずチェックする。
Q5. これって OpenAPI や JSON Schema と何が違うの？
OpenAPI / JSON Schema はAPI のリクエスト・レスポンスの形を定義するもの。Context Grammar の Spec はUX の意味を定義するもの。レイヤーが違う。
実は Context Grammar Spec は JSON Schema で記述できる（実装上はそうしてもいい）。でも目的は別 — JSON Schema は「型が正しいか」、Context Grammar Spec は「このシーンの意味は何か」を答える。
