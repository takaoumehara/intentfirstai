Context Grammar · Concept · 8 Tokens (Combined)

8 Context Tokens
The sensors of agentic AI

AI が「今どんな状況？」を読み取るための8つのセンサー。
Brain が記憶を持ち、Token が瞬間を切り取る。Rule Engine が両者を掛け合わせて、AI の振る舞いを決める。

A · まず全体像

8 Tokens は2グループ — 6 Situation + 2 Dials

8つを丸暗記するのは大変。だから 6 Situation Tokens（状況） と 2 Relationship Dials（関係性のつまみ） の2グループで覚えます。前者は外側の事実を読む入力、後者は人と AI の境界を決める制御です。

📡
Group A · 6 Situation Tokens
状況センサー

「今どんな状況？」を6つの軸で測る。外側の事実を数値化するセンサー群。AI が読む入力。

  • ① Physical State — 体の状態（歩いてる／座ってる／運転中）
  • ② Cognitive Load — 頭の忙しさ（朝の支度ピーク／週末リラックス）
  • ③ Social Exposure — 周りの目（一人／家族／会議中）
  • ④ Priority Weight — 何を優先するか（時間 vs お金 vs 健康）
  • ⑤ Form Factor — どの画面（時計／スマホ／TV／車）
  • ⑥ Feasibility — そもそも実行可能か（在庫・時間・距離）
+
🎚
Group B · 2 Relationship Dials
関係性のつまみ

人と AI の距離感を決める。状況とは別軸で、ユーザー・サービス・AI の3者が「どこまで任せるか」「どこまで知らせるか」を決める。

  • ⑦ Autonomy Dial — どこまで自動でやらせる？（Suggest / Confirm / Notify / Auto）
  • ⑧ Disclosure Dial — どこまで AI に教える？（領域別・人別）
大事な違い: Situation Tokens は「今のあなた」を見る（変動する）。Relationship Dials は「あなたと AI の関係」を決める（じっくり育つ）。
一瞬の状況 + 長期の関係性 = AI の動きが決まる。
Multi-Brain の前提: Token は単独で生まれるわけではない。
各 Token は複数の Brain（Identity / Learning / Now の3層）から信号を集めて算出される。たとえば Priority Weight は「今この瞬間の緊急度（Now Layer）」と「過去どう優先順位を解いたか（Learning Layer）」の合算。Brain が記憶、Token が瞬間、Rule Engine が判断 — この3つが組になって初めて機能する。
B · 比喩

レストランの店員さんで考える

良いウェイターは、お客さんの様子を一瞬で読み取って対応を変えます。8 Context Tokens は、そのウェイターが見ている8つの信号と全く同じです。

🍽 ウェイターが読み取っている8つの信号

① Physical State

お客さんは座ってる？立ち話してる？

→ 座ってない人にメニューを渡しても読めない

② Cognitive Load

テーブルが満席で店が大混雑？それとも空いてて落ち着いてる？

→ 混雑時は要点だけ。空いてる時はワインの話もできる

③ Social Exposure

キャンドルの2人？仕事の接待？子供連れ？

→ デート中に「ご予算は？」とは聞かない

④ Priority Weight

このお客さんは「速さ」重視？「ゆっくり」重視？

→ ランチタイムのサラリーマンには「お急ぎですか？」

⑤ Form Factor

テーブル席？カウンター席？テラス？

→ カウンターなら大皿は出せない、サイズに合わせる

⑥ Feasibility

頼まれた料理、今日は作れる？材料ある？

→ 「申し訳ありません、本日は…」と早めに言う

⑦ Autonomy Dial

常連さん「いつものでいいよ」 vs 初来店「相談したい」

→ 常連には黙って出す、初来店には一つ一つ確認する

⑧ Disclosure Dial

このお客さんは自分のアレルギーを話してくれてる？

→ 教えてもらってない情報で勝手に判断しない
良いウェイターは、お客さんが何も言わなくても 8つの信号を読んで対応を変える。
AI もこれと同じことをやろうとしている。それが Context Grammar の Tokens です。
C · 4×2 で一望

山城家の朝で見る、8つのトークン

抽象的な定義だけだと忘れます。山城家の Mai（母）・Sota（11歳）・Hana（6歳）の日常から、各トークンを1つずつ拾います。星の数は 2026年3月時点の技術リアリティ。

① Physical State ★★★★☆
体が今どんな状態にあるか。歩行・運転・座位・運動中など。
山城家の例 Mai は7:45、駅まで全力ダッシュ中。Watch が「歩行速度 6km/h・心拍 110」と検出。AI は通知を出さない（読めないから）。
② Cognitive Load ★★☆☆☆
頭がどれだけ忙しいか。直接は測れない、時刻 × カレンダー × 行動パターンから推定するしかない。
山城家の例 平日朝 7:02、Mai は弁当2つ作りながら Hana の保育園バッグも準備中。AI は「density:minimal」を選び、画面に1行だけ出す。
③ Social Exposure ★★★★☆
周りに誰がいるか。一人 / 家族 / 同僚 / 不特定多数。最も実装が進んでいるトークン。
山城家の例 Mai が会議室の TV にミラーリングした瞬間、AI は家計の通知を消す。「他人がこの画面を見ている」と察知。
④ Priority Weight ★★★☆☆
競合する欲求のうち、今は何を優先するか。「時間 vs お金 vs 健康」の衝突解決のため。
山城家の例 Sota の塾が遅延 → 夕食を早めるか、迎えに行くか。Mai の Brain は「平日は時間 > 食事のクオリティ」と学習済み → AI は冷凍ストック提案。
⑤ Form Factor ★★★★☆
今どの画面・どの面に出すか。Watch / Phone / Tablet / TV / Fridge / Car / Voice / Ambient。
山城家の例 家族の予定を Mai の Watch に出すと「19:00 塾迎え」だけ。同じ情報を冷蔵庫の画面に出すと、家族全員のタイムラインが広がる。
⑥ Feasibility ★★★☆☆
そもそも今、それは可能なのか。在庫・時間・距離・天気・お金のどれかが足りないと無理。
山城家の例 AI が「カレー」を提案しかけたが、冷蔵庫に玉ねぎが無く、雨で買い物に行けない → 提案を「在庫で作れるパスタ」に切り替える。
⑦ Autonomy Dial ★★★☆☆
どこまで AI に任せるか。Suggest → Confirm → Notify → Auto の4段。サービス側のデフォルト × AI 調整 × ユーザー操作の3つの力で決まる。
山城家の例 Sota の靴 $48（消耗品）= Auto。家族旅行のホテル予約 $400 = Confirm。Mai の手術同意 = Suggest（決して自動化しない）。
⑧ Disclosure Dial ★☆☆☆☆
どこまで AI に自分のことを教えるか。領域別・人別。Autonomy の前提条件（知らせない × 任せる は論理的に不可能）。
山城家の例 Mai は「家計」を AI に開示するが、「健康診断結果」は閉じている。だから AI は食費の提案はできるが、体調に踏み込んだ献立は出さない。
星の読み方: ★★★★☆ = 今すぐ実装できる（センサーや OS の API がある）。★★☆☆☆ = まだ推定でしかなく、研究段階。★☆☆☆☆ = まだ概念段階で、横断的な API が存在しない。
Cognitive Load や Disclosure を「測れる／既に実装済み」と書くと嘘になる。だから「推定する」「概念段階」と正直に書く。これが Context Grammar の知的誠実さです。
D · 1つずつ深く

8つのトークンを、機構レベルで分解する

ここからが本体。各トークンの仕組み（どう計算するか）、信号源（どの Brain / どのセンサーから来るか）、技術リアリティ、具体例、禁じ手（やってはいけないこと）を順番に整理します。

① Physical State "Are they rushing or relaxed?" ★★★★☆ Mostly shipping
Definition
体が今どんな状態にあるか。歩行・走行・運転・座位・睡眠・運動中。デザイン判断の最初に効く軸 — 状態が読めなければ、内容を変える前に形（form）を変えるべき場面で何もできない。
Mechanism
Activity Recognition API（iOS / Android）が walking / running / driving / still を分類。Galaxy Watch / Apple Watch が心拍・ストレス・睡眠負債を加算。複数信号を1つの「state」に圧縮し、設計判断（出すか出さないか、声か画面か）に渡す。
Signal sources
  • Now Layer加速度センサー、心拍、ジャイロ、CarPlay/Android Auto 接続状態
  • Learning Layer「Mai は平日朝7:30〜7:50は必ず駅まで走る」というパターン
  • Identity Layer持病・身体的制約（妊娠中・術後など）
Concrete example
Mai は7:45、駅まで全力ダッシュ中。Watch が「速度 6km/h・心拍 110」と検出 → AI は通知を全停止し、19:00 の塾迎えリマインダーは「電車に座ったあと」に再スケジュール。
逆に土曜の朝、ソファで座位 + 心拍 65 のときは、家族カレンダーの提案を画面に出してよい。
Projection rule
状態が「読めない」ときほど慎重に。 走行中・運転中は通知を声に切り替える、もしくは抑制する。形を先に変えてから、内容を考える。
Forbidden
禁じ手: 走っている人に、長文のリッチ通知を出す。運転中に画面操作を要求する確認ダイアログを出す。状態を読まずに「ベル鳴らせば届く」と思い込む設計。
② Cognitive Load "How much mental bandwidth remains?" ★★☆☆☆ Estimation only
Definition
頭がどれだけ忙しいか — 残っている認知帯域。直接は測れない。脳波計を付けてるわけじゃないので、推定するしかない。これが Context Grammar で最も正直さが要求されるトークン。
Mechanism
時刻 × カレンダー密度 × 直近10分のアプリ切替回数 × 行動パターン履歴。複数のプロキシを重み付け平均し、3〜5段階の density（minimal / low / medium / high / overload）に丸める。常に「推定値」というメタ情報を付ける。
Signal sources
  • Now Layerカレンダー15分粒度の埋まり具合、直近のタスク完了数、画面切替頻度
  • Learning Layer「平日朝7:00-7:30は必ず overload」のパターン、過去の「No, I'm free」上書き履歴
Concrete example
平日朝 7:02、Mai は弁当2つ作りながら Hana の保育園バッグも準備中。AI は density:overload と推定し、冷蔵庫の画面には「昨日の残り + 卵焼き」と1行だけ表示。タップ操作は不要。
同じ Mai でも土曜10:00ならゆっくりレシピ提案を出してよい。
Projection rule
high / overload では 1画面 1判断。3択以上を出さない。低 Cognitive Load の時にだけ「探索」「学習」系の提案を解禁。AI が「分かったフリ」をして外したら、ユーザーが手動で「No, I'm free」と上書きできる UI が必須。
Forbidden
禁じ手: 「あなたは今 high load です」と断定する UI。推定だと書かずに脳波測定したかのように振る舞う。overload 時に複数の選択肢ダイアログを出す。フォールバックを用意しない。
③ Social Exposure "Who else is watching?" ★★★★☆ Mostly shipping
Definition
いま誰がこの画面・この音声を一緒に見聞きしているか。一人 / 家族 / 同僚 / 不特定多数（カフェ・電車）。8つの中で最も実装が進んでいるトークン。
Mechanism
Bluetooth / Wi-Fi 近接で他人のデバイスを検出。Voice ID で家族メンバーを区別（Samsung Family Hub は最大6プロファイル対応）。ミラーリング状態（AirPlay / Cast / DeX）を OS から取得。可能ならオンデバイス Vision で人数を推定。
Signal sources
  • Now Layer近接デバイス、Voice ID 一致、ミラーリング ON/OFF、画面共有 ON
  • Identity Layer「家族」「同僚」「友人」の関係マップ — 誰がそばに居るかを意味づけ
Concrete example
Mai が会議室の TV にミラーリングした瞬間、AI は家計の通知を消し、Sota の塾代の話題は19:30まで遅延配信。Voice ID が「Sota が居間に居る」と検出すると、Mai のスマホで開いていた「Sota への誕生日サプライズ」プランは自動で hidden 化。
Projection rule
誰が見ているかで、内容ではなくフィルタを変える。 同僚が居るなら「家計」領域は出さない。子供が居るなら「サプライズ」は出さない。Disclosure Dial の領域設定と掛け算で動く。
Forbidden
禁じ手: 画面共有中に金額・パスワード・健康情報を表示する。家族用デバイスで「個人」スコープの通知を全員に晒す。Voice ID なしで「いつもこの人」と決め打ちする。
④ Priority Weight "When demands collide, what wins?" ★★★☆☆ Partially shipping
Definition
複数の欲求が衝突したとき、今は何を優先するか。「速さ vs 値段 vs 健康 vs 家族の都合」の衝突解決のため。単なる「重要度ランキング」ではなく、競合した瞬間のトレードオフ判定。
Mechanism
2層構造。Layer 1 = 今この瞬間の緊急度（Now Layer から、カレンダー直前度・通知の種類・期限）。Layer 2 = 学習済みのトレードオフパターン（Learning Layer から、「Mai は平日は時間 > 食事のクオリティ」「土曜は健康 > 値段」など）。Rule Engine が両者を掛け合わせる。
Signal sources
  • Now Layerカレンダー優先度、メールの flag、通知 importance、期限まで残時間
  • Learning Layer過去の衝突解決履歴 — 「同じ状況で何を捨てたか」
  • Identity Layer絶対譲れない軸（アレルギーは食味より勝つ、子供の安全は仕事より勝つ）
Concrete example
Sota の塾が遅延 → 夕食を早めるか、迎えに行くか。Mai の Brain は「平日は時間 > 食事のクオリティ」と学習済み → AI は「冷凍ストックでパッと夕食、Mai は7:50に駅で迎え」を提案。
別の例: 会議が5分後に始まる + 娘の学校から電話 → アレルギーや安全に関わる電話なら「会議に1分遅れる」を選ぶ。Identity Layer が勝つ。
Projection rule
AI は勝手に重みを決めない。学習履歴に基づいて提案する。ユーザーが上書きしたらその選択を Person Brain の Learning Layer に書き戻す。Identity Layer に書かれた軸（安全・健康）は他のどの軸より絶対に勝つ。
Forbidden
禁じ手: ユーザーに「優先順位を1〜5で並べてください」と毎回聞く設計。Identity Layer の軸（アレルギー・既往症）を「学習済みパターン」で上書きしてしまう。
⑤ Form Factor "What surfaces surround them?" ★★★★☆ Mostly shipping
Definition
いま AI が話しかけられる面（surface）の集合。Watch / Phone / Tablet / TV / Fridge / Car、それから Voice-only / AR / Ambient（環境）も含む。画面の話だけではない。
Mechanism
OS が常時保持しているデバイス情報＋ Continuity / DeX / CarPlay / Cast の接続状態。複数面が同時に有効なら、内容ごとに最適な面を選ぶ（dynamic multi-screen allocation）。Voice / Gesture / Ambient も surface の1種として扱う。
Signal sources
  • Now Layer接続中デバイス、画面サイズ、入力モダリティ、CarPlay/AR 起動状態
  • Identity Layer所有デバイス・主に使う面（「Mai は Watch を常時装着」）
Concrete example
家族の予定を Mai の Watch に出すと「19:00 塾迎え」だけ。同じ情報を冷蔵庫の画面に出すと、家族全員のタイムラインが広がる。同じ情報を CarPlay に出すと、声で「19時に塾」とだけ読み上げる。
Voice-only（Earbuds 単独）なら、確認は「Yes / No」だけで完結する形に圧縮する。
Projection rule
面が変われば、情報量を変える。 Watch = 1行、Phone = 段落、Tablet/TV = 並列表示、Voice = 1問1答。面ごとに「同じ情報の別の見せ方」を持つのが Context Grammar の Form Factor。
Forbidden
禁じ手: Phone の UI をそのまま Watch に縮小コピーする。Voice の応答を Phone と同じ長文で読み上げる。「Responsive Web」だけで済むと思って Ambient / Voice を考えない。
⑥ Feasibility "What's actually possible right now?" ★★★☆☆ Partially shipping
Definition
そもそも今この瞬間、それは実行可能か。在庫・時間・距離・天気・お金・人的リソース — どれかが足りないと不可能。「No」で終わらせず、「代わりに何ができるか」まで返すための判定。
Mechanism
各ドメインの API（在庫 / 配送 ETA / 天気 / 営業時間 / 残高）から個別フィージビリティを取得 → 複数制約を1つのfeasibility score に統合 → 不足があれば Substitution Mode（Exact/Flexible/Exploring/Surprise）と組んで代替案を提示。
Signal sources
  • Now Layer在庫 API、天気 API、配送 ETA、店舗営業状況、家計残高
  • Learning Layer「在庫切れのとき何を代替に選んだか」の履歴 → Substitution Mode の学習
Concrete example
AI が「今夜カレー」を提案しかけたが、冷蔵庫に玉ねぎが無く、雨で買い物に行けない → 提案を「在庫で作れるパスタ」に切り替え。
別例: Mai が「明治ブルガリアヨーグルト」を頼んだが品切れ → Substitution Mode が Flexible なら「他のブルガリア風ヨーグルト」を勝手に置き換え、Exact なら「今日は無理」と返す。
Projection rule
不可能を「不可能」で終わらせない。 必ず「では何ができるか」を1〜3案添える。Substitution Mode と必ず組で実装する。
Forbidden
禁じ手: 「在庫がありません」だけで終わる。複数制約を見ずに「行けます」と返してから現地で詰む（雨 + 営業時間切れ + 子供同伴を見落とす）。Exact 以外のモードで勝手に変な代替をして信頼を失う。
⑦ Autonomy Dial "How much can AI act on its own?" ★★★☆☆ Shipping in dev tools
Definition
AI にどこまで任せるか。Suggest → Confirm → Notify → Auto の4段。これは「ユーザーが自由に決めるトグル」ではなく、3つの力の合成で決まる。
The 4 stages
  • Suggest — AI が選択肢を見せる、ユーザーが選ぶ
  • Confirm — AI が1案に決め打ち、実行前にユーザー承認
  • Notify — AI が実行する、終わってから通知
  • Auto — AI が静かに実行、通知すらしない
Mechanism
3つの力で1つの dial 値が決まる:
① サービスのデフォルト（Netflix のレコメンドはすでに高 Autonomy で出荷されている）
② AI の調整（夜中・休日・初回利用時はデフォを下げる）
③ ユーザーの能動的変更（明示的にスライダーを動かす）
ドメイン別（家計 / 健康 / 仕事 / 子育て）に独立して持つ。
Signal sources
  • Now Layer金額の大きさ、可逆性、緊急度
  • Learning Layer過去の AI 提案の成功率、ユーザーの介入履歴 → trust score
  • Identity Layer「絶対自動化しない領域」の宣言（医療同意・大型契約）
Concrete example
Sota の靴 $48（消耗品・低リスク・前回も同型）= Auto。家族旅行のホテル予約 $400 = Confirm。Mai の手術同意書 = Suggest（決して自動化しない、Identity Layer の宣言）。
Projection rule
初回は必ず Suggest から始める。track record（成功・失敗の履歴）に応じて段階を上げる。失敗が起きたら1段階下げる（trust drop）。Identity Layer に「絶対自動化しない」と書かれた領域は、どれだけ track record が良くても上げない。
Forbidden
禁じ手: 「AI 自動化 ON / OFF」の二択トグル。初回から Auto で出荷する。失敗してもダイヤルを下げない。Disclosure Dial が低いまま Autonomy だけ上げる（次項参照）。
⑧ Disclosure Dial "How much does AI know about you?" ★☆☆☆☆ Concept stage
Definition
ユーザーが AI にどこまで自分のことを開示するか。領域別 × 人別に独立して持つ。Autonomy の論理的前提条件（知らせない × 任せる は不可能）。
The 4 levels
  • Full — 全データを AI に開示
  • Summary — 集計・要約だけ開示（個別ログは隠す）
  • Existence — 「そういう領域がある」だけ AI に伝える
  • Hidden — AI に存在自体を隠す
Mechanism
領域（家計 / 健康 / 仕事 / 子育て / 性 / 趣味 …）× 受け手（AI / 家族 / 同僚 / 友人 / 公開）のマトリクス。各セルが Full / Summary / Existence / Hidden の4段から1つを取る。OS レベルの統一 dial として実装する。
Signal sources
  • Identity Layer「家計は配偶者には Full、子供には Hidden」のような宣言的設定
  • Learning Layer過去にユーザーが「これは見せたくない」と非公開化した履歴
Concrete example
Mai は「家計」を AI に Full 開示するが、「健康診断結果」は Hidden。
だから AI は食費の最適化提案はできるが、コレステロール値を踏まえた献立変更は提案しない。
家計を「夫には Full、子供には Hidden、同僚には絶対 Hidden」と人別に設定可能。これは既存 OS には存在しない構造。
Projection rule
Disclosure が Hidden の領域では Autonomy を Auto に上げてはいけない（知らせていないのに任せるのは不可能）。Autonomy が Auto を求めるなら、まず Disclosure を上げる UI を先に出す。Disclosure → Autonomy の順序は不可逆。
Forbidden
禁じ手: 「プライバシー設定 ON / OFF」の二択トグル。Disclosure と Autonomy を独立に動かして、Hidden × Auto の不可能組み合わせを許す。同意なしに「学習」名目でデータを内部利用する。
E · 組み合わせ

トークンは1つでは意味を持たない — 重なって初めて答えが出る

1つのトークンだけでは決められません。複数のトークンが重なって、はじめて AI の動きが定まります。2つの実例で見ます。

朝7:02、Mai が冷蔵庫の前で立ち止まる

— 山城家・平日 · ある火曜の朝

Combo 1 · 「弁当のおかず、何にする？」 3 tokens × 1 dial
  • ② Cognitive Load朝7:02 = ピーク（カレンダー密度 + 平日パターン）
  • ① Physical State立ち作業中、両手は塞がってる
  • ③ Social Exposure家族のみ（プライベート）
  • ⑦ Autonomy Dial朝の食事 = Auto-suggest（提案だけ表示、確認不要）
→ 結論: 冷蔵庫画面に「昨日の残り + 卵焼き」と1行だけ表示。タップ操作不要。
Combo 2 · 「Sota の塾代の相談、今出していい？」 3 tokens × 2 dials
  • ③ Social Exposure会議中、画面共有 ON（同僚が見ている）
  • ⑤ Form FactorMacBook、ミラーリング先は会議室 TV
  • ⑥ Feasibility金額の議論は今すぐは不要、夜でも可
  • ⑧ Disclosure Dial家計 = 同僚には非開示の領域
  • ⑦ Autonomy Dial金銭の通知 = Notify（確認させる）レベル
→ 結論: 通知を抑制。19:30、Mai が一人になった時点で再表示。
気づきポイント: 同じ「塾代の通知」でも、出すタイミングと場所が完全に変わる。これは1つのトークンでは決まらない。
8つのトークンが掛け算のように作用して、初めて「今この瞬間に出すべきか」が決まる。
F · なぜ8つか

7つから8つへ — Disclosure Dial が一級市民になった理由

Context Grammar は当初 7 トークンでした。2026年初頭に Disclosure Dial を独立トークンとして昇格させ、8つになりました。「プライバシーをトークンの一級市民にする」ためです。

項目 7-Token 時代 8-Token 時代（現在）
プライバシー Social Exposure に内包（曖昧） Disclosure Dial として独立（明示的）
Autonomy との関係 暗黙の前提 「知らせない × 任せる は不可能」と明文化
領域別の制御 不可能 家計 / 健康 / 仕事 / 子育て を別々に開示できる
人別の制御 不可能 家族には開示、同僚には非開示
ダイヤル数 1 dial（Autonomy のみ） 2 dials（Autonomy + Disclosure が対）
キーポイント: Autonomy Dial（任せる度合い）と Disclosure Dial（教える度合い）は対になっている。AI に何も教えていないのに「全自動でやって」と頼むのは、自分のことを何も知らない執事に「いい感じにやって」と言うようなもの。
だから Disclosure は Autonomy の前提条件。独立トークンに昇格させる必要があった。
G · 実装する人へ

技術リアリティと推奨アクション

8つを「全部いま実装できる」と書いたら嘘になる。2026年3月時点での出荷可能度を1枚にまとめ、その上でどこから手をつけるかを示します。

Token Reality Status One-liner
① Physical State★★★★☆Mostly shippingActivity Recognition + Watch センサーで実装可
② Cognitive Load★★☆☆☆Estimation only直接測定不可。proxy ベースの推定
③ Social Exposure★★★★☆Mostly shippingVoice ID / 近接 / ミラーリングで読める
④ Priority Weight★★★☆☆Partially shipping領域内なら可、領域横断はまだ
⑤ Form Factor★★★★☆Mostly shippingOS が既に持っている。multi-surface 配信が次の壁
⑥ Feasibility★★★☆☆Partially shipping個別 API は揃ってる、複合制約の解消が課題
⑦ Autonomy Dial★★★☆☆Shipping in dev toolsClaude Code / Cursor で実例あり、消費者向けはこれから
⑧ Disclosure Dial★☆☆☆☆Concept stage領域 × 人 マトリクスの統一 UI は未存在

推奨アクション（実装順）

1
最初に着手すべきは ③ Social Exposure と ⑤ Form Factor
どちらも ★★★★☆。OS が既に持っている情報（画面のミラーリング状態、デバイス種別）を読むだけで実装できる。「会議中は通知を抑える」だけでも体感が変わる。
2
次に ⑦ Autonomy Dial の4段を UI に出す
Suggest / Confirm / Notify / Auto を「機能ごと」に切り替えられる UI を入れる。エージェント系プロダクトでは標準になりつつある（Claude Code / Cursor など）。Disclosure と組にして見せると一気に「制御できている」感が出る。
3
⑧ Disclosure Dial は「領域 × 人」のマトリクス UI で
家計 / 健康 / 仕事 / 子育て × 家族 / 同僚 / 友人 / 公開、のグリッドを見せる。Full / Summary / Existence / Hidden の4段を選ばせる。これがあるだけで、Autonomy を高くしても「怖くない」感覚になる。
4
② Cognitive Load は「推定値だ」と明示する
直接測定ではないので、「busy mode 推定」のように UI に書く。確実に外れる時があるので、ユーザーが手動で「No, I'm free」と上書きできる UI が必要。これがないと AI が「分かったフリ」をして信頼を失う。
5
8つを「全部使う」必要はない — シーンごとに3〜4個で十分
1つの判断で8つ全部を読む必要はない。たいてい3〜4個。「朝の弁当提案」なら ② + ① + ③ + ⑦ で足りる。残りはデフォルト値のまま。設計者はシーンごとに「使うトークン」を選ぶだけでいい。
H · よくある混乱

よくある質問を整理する

Q1. Token と Brain は同じ？
違います。 Token は今この瞬間の状況（センサー値）。Brain は長期の記憶（蓄積した知識）。
たとえば「今 Mai は会議中」は Token（瞬間）、「Mai は毎週火曜の朝が一番忙しい」は Brain（パターン）。Rule Engine がToken × Brain を掛け算して動きを決めます。
Q2. Cognitive Load って本当に測れるの？
直接は測れません。 脳波計を付けてるわけじゃない。だから推定するしかない。「平日の朝7時 + カレンダーが詰まっている + 直近1時間で12個タスクをこなした」 = 高いだろう、と。
この限界を正直に書くのが Context Grammar の立ち位置。「測れる」と言い切る他社のフレームワークは、技術的に嘘になります。
Q3. Autonomy Dial はユーザーが自分で決めるんでしょ？
純粋に自分で決めるわけではありません。 3つの力で決まります:
① サービスのデフォルト（Netflix のレコメンドはすでに高 Autonomy）
② AI の調整（夜中はデフォを下げて確認多めにする等）
③ ユーザーの能動的変更（明示的にスライダーを動かす）
「ユーザーがゼロから決める」と書くのは古い UI 教科書の発想。現実は3者の合成です。
Q4. Disclosure Dial と「プライバシー設定」は同じ？
違います、もっと細かい。 既存のプライバシー設定は ON / OFF の二択。Disclosure Dial は 領域別 × 人別。
たとえば Mai は「家計を AI には開示」「家計を夫には開示」「家計を子供には非開示」「家計を同僚には絶対非開示」を別々に設定できる。これは既存 OS には存在しない構造です。
Q5. Token は1つの Brain から来るの？それとも複数？
多くは複数の Brain から合算されます。 たとえば Priority Weight は「今この瞬間の緊急度（Now Layer）」+「学習済みのトレードオフパターン（Learning Layer）」+「絶対譲れない軸（Identity Layer）」の合算。
Multi-Brain モデルでは、各 Token は「どの Brain がソースか」を必ず持ちます。AI が「なぜそう判断したか」を後から説明できるように。
Q6. 結局、Token があると何がうれしいの？
AI の動きが「気が利く」ようになります。 今の AI（ChatGPT/Siri）は、相手の状況を見ずに同じトーンで返事をする。
Token が読めると「Mai は今会議中だから後で返す」「Sota は寝る前だから明るい色は避ける」といった状況に応じた振る舞いができる。良いウェイターと、機械的なファミレス店員の差です。
