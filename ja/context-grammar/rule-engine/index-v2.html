1 分でわかる

家庭版「注文票システム」

仕組みに入る前に、全体を一発で掴めるたとえ話をひとつ。

レストランに例えると

ホール係がオーダーをとると、「テーブル4番、ピーナッツアレルギー、お子様連れ、急ぎ」というメモができます。そのメモをそのまま厨房に投げ込むのではなく、注文票システムが「ソース抜き・量 70%・優先提供」という厨房用の指示書に変換します。

シェフはその指示書（チケット）を読む。和食ステーションはそれを煮物に、洋食ステーションはチキンに、キッズメニューはうどんに仕上げます。チケットは 1 枚、出し方は surface 次第。

Rule Engine がその注文票システム。Token がホール係のメモ。ui.command がチケット。冷蔵庫・スマホ・車が各ステーション。

入口と出口
Tokens IN → ui.command OUT

根幹の翻訳

Rule Engine は「コンパイラ」

Brain の記憶と Token の状態は、そのままでは UI に届きません。「眠い」「電車の中」「片手しか使えない」という事実があっても、画面の何をどう描くかは決まっていない。その事実を「画面への命令」に翻訳するのが Rule Engine です。

📥
Tokens IN
今の状態

8 Context Tokens の現在値。Brain から読んだ事実 — アレルギー、予算、予定 — も含む。

  • Cognitive Load = high
  • Form Factor = phone
  • Social Exposure = public
  • Autonomy Dial = Confirm

⚙️
Rule Engine
翻訳機

条件にマッチするルールを発火する。同じ入力なら必ず同じ出力。気分で変わらない。

  • if Cognitive Load = high → density: minimal
  • if Form Factor = phone → layout: vertical
  • if Social Exposure = public → hide: prices
  • 23 AX Patterns を組み合わせる
→
📤
ui.command OUT
画面への命令

どの surface でも読める抽象的な「描き方の指示書」。デバイスの種類は関係ない。

  • density: minimal
  • items: 1
  • tone: gentle
  • hide: [price, calorie]
決定論的（deterministic）とは: Rule Engine は同じ Token の組み合わせを入れたら、いつ・誰が・どのデバイスから呼んでも、必ず同じ命令が出る。同じ条件なら毎回同じ答えを返す。気分で変わらない。家族全員の信頼の土台はこの予測可能性にある。

内部構造

読む → 当てる → 出す

Rule Engine の中では何が起きているのか。3 つの工程に分けると、迷子になりません。

① 読む
Token を集める

8 つの Token の今の値を集計する。さらに Brain から関連する事実 — アレルギー、今月の予算、Brand 制約、Research の最新シグナル — を取ってくる。家庭なら 1 個の Brain、企業なら最大 5 種類。

② 当てる
ルールを発火する

if/then の条件式を全件チェックして、マッチするものをすべて発火させる。複数ヒットしたら優先順位で重ね合わせる。矛盾が生じたら Priority Weight Token が裁定する。

③ 出す
命令にまとめる

発火した結果を 1 個のui.command（命令オブジェクト）にまとめて emit する。この時点でデバイスはまだ関係ない — それは surface 側の仕事。

ポイント: Rule Engine はデバイスを知らない。「冷蔵庫だから大きく」「iPhone だから縦レイアウト」と判断するのは Token（Form Factor）が持つ事実。Engine は if Form Factor = phone → layout: vertical というルールを発火するだけ。
Brain の出所も知らない: 「Org Brain から来た事実」「Brand Brain から来た事実」を区別しない。Brain 側がそれぞれの責任で Token を構成し、Engine はその合成結果を読むだけ。だから 1 個の Engine が家庭にも企業にも使える。
実例
山城家の朝 7:02 AM — 同じ命令、3 つの surface

ライブウォークスルー

朝の一場面が ui.command になるまで

Mai がキッチンで子どもたちと格闘中、冷蔵庫の前に立つ。Rule Engine の中で何が起きるか、ステップを追います。

「あー、Sota の弁当の中身どうしよう…時間ないんだけど」

— Mai（38歳・二児の母）· 火曜 7:02 AM, キッチン

1 7:02 AM の Token 状態 Tokens IN
Mai が冷蔵庫の前に立った瞬間、システムが収集した 8 Context Tokens の現在値。
8 Context Tokens · 7:02 AM
  • ① Physical State 立っている・キッチン・両手は弁当箱で塞がっている
  • ② Cognitive Load HIGH — 朝・カレンダー過密・直近 5 分で 3 件のタスク切替
  • ③ Social Exposure family（家族だけ・公開度 low）
  • ④ Priority Weight 「弁当を時間内に作る」が最優先
  • ⑤ Form Factor fridge（Samsung Family Hub の前）
  • ⑥ Feasibility 残り 13 分で家を出る・調理時間 8 分以内
  • ⑦ Autonomy Dial Suggest（提案だけ・決めるのは Mai）
  • ⑧ Disclosure Dial 家族の食事履歴・冷蔵庫在庫 → AI に開示済み
Brain からも読まれる: Sota はピーナッツアレルギー · 昨日も鮭弁 · 冷蔵庫に卵 6 個・ブロッコリー・ハム残あり
2 Rule Engine がルールを発火する Engine
Rule Engine は 23 の AX Pattern に対応するルールセットから、今の Token 状態にマッチするものをすべて選び出す。
発火したルール（抜粋）
  • if Cognitive Load = high→density: minimal, items: 1
  • if Feasibility < 10min→filter: only ready-fast recipes
  • if Brain.allergy(Sota) = peanut→exclude: peanut, sesame-cross
  • if Brain.history.yesterday = salmon→deprioritize: salmon
  • if Autonomy Dial = Suggest→action: propose only, no auto-cook
  • if Physical State = hands-busy→input: voice-first, tap fallback
→ 6 ルール発火 · 1 つの命令に合成して emit へ

レストランに例えると

ホール係のメモ（ピーナッツアレルギー・お子様・急ぎ）が揃った。注文票システムがルールを照合し、「ソース抜き・量 70%・優先提供」と書いたチケットを切る。シェフは生のメモを聞かず、標準化されたチケットだけを受け取る。

3 ui.command を emit する Emit
発火したルールが合成され、1 個の抽象的な命令オブジェクトが吐き出される。この時点では「冷蔵庫の何 px に何を描くか」はまだ決まっていない。
ui.command · emit
intent: suggest_lunchbox density: minimal items: 1 tone: gentle input: voice-first candidates: [egg-ham-broccoli, omelet-rice] exclude: [peanut, sesame-cross, salmon] time-budget: 8min decision-by: user (Suggest mode)
4 3 つの surface が同じ命令を別々にレンダリングする Render
ここがポイント。同じ ui.command を、それぞれの surface が自分の文法で描く。Rule Engine は何も書き換えていない。

スケール

同じ Engine — P1 の 1 Brain でも P4 の 5 Brain でも

Rule Engine はスケールを選ばない。家庭の Brain 1 個でも企業の 5 Brain スタックでも、Engine には合成済みの Token セットが 1 つ届くだけ。

⌬ Multi-Brain との関係

Rule Engine が読み取るのは Token の現在値。ただしその Token の中身は、1 つの Brain だけから来るわけではありません。P1 の Context Brain（家庭用 1 個）でも、P4 の Enterprise Context Brain（5 種類の Brain が並列）でも、Engine から見れば「合成された Token 状態が 1 セット入ってくる」だけです。

  • Org Brain — 全社の永続的な土台（組織図・ポリシー・用語集）
  • Brand Brain × N — 判断 DNA（B2C / B2B など並列）
  • Research Brain — ユーザー理解 + 売上 / サポート / CRM 流入
  • Project Master Brain — 戦略を考える脳（プロジェクト群を統括）
  • Project Brain × N — 時限付き・各プロジェクトの実行

これらの Brain が Identity Layer / Learning Layer / Now Layer から事実を持ち寄り、Token Bus で合成する。Rule Engine は Brain の数を意識せず、毎回同じ翻訳を行う。同じ Rule Engine、違う Brain 構成 — 出力は Token 次第。これが家庭にも企業にも同じ Engine が使える理由です。

技術詳細

ルール構文 · スキーマ · 衝突解決

Rule Engine は理論じゃない。3 つの YAML ファイルと 33 の Behavior Rules で、実際に書ける。

context.yml
Token と Brain のスキーマ
8 Context Tokens の型・取りうる値・既定値を宣言する。Brain 参照（brain.allergy、brain.history.yesterday 等）の型もここで定義。
rules.yml
33 Behavior Rules の if/then 定義
条件式 → 出力フィールドのマッピング。各ルールに priority（優先度）と tags（どの AX Pattern に属するか）を持たせる。
patterns.yml
23 AX Patterns の合成レシピ
Delegation / Escalation / Adaptation / Enterprise の 4 カテゴリ。どのルール群を束ねたら「Pattern 発火」と呼ぶか、その単位を定義。
ui.command schema
出力構造体の語彙
intent / density / items / tone / candidates / exclude / input / time-budget / decision-by — surface 側が読む共通辞書。実装は JSON でも protobuf でも構わない。
rules.yml — 抜粋
- id: cog_load_minimal when: { cognitive_load: high } then: density: minimal items: 1 priority: 80 tags: [A2-cognitive-scaling] - id: hands_busy_voice when: { physical_state: hands_busy } then: input: voice-first fallback: tap priority: 70 tags: [A4-input-mode-switch] - id: dyn_friction_high_value when: autonomy: Auto price: { gt: 15000 } then: require_confirm: true reason: "high-value purchase" priority: 100 tags: [D6-dynamic-friction] - id: disclosure_guard when: disclosure: hidden autonomy: { gt: Confirm } then: constraint_violation: true reset_to: Confirm priority: 999 tags: [E5-trust-breach-recovery]

衝突解決 — ルールが矛盾したらどうする？

複数ルールが同時に発火するのは普通のこと。互いに矛盾しなければ全部適用、矛盾したら 3 段階で裁定する。

段階 裁定者 判断基準
1 Priority Weight Token 「弁当が最優先」のようなユーザー宣言の今の重み。最初に当てる。
2 Rule の priority 値 静的に設定された数値（0–999）。Disclosure Guard など信頼系は 999。
3 Brain の Learning Layer 過去のユーザー判断パターン — 同じ衝突で何度どっちを選んできたか。
重要な不変条件: Disclosure = hidden かつ Autonomy > Confirm は論理的に成立しない。「知らせない × 任せる」は不可能なので、Engine は必ず Autonomy を Confirm に戻す。これは priority 999 の Trust Breach Recovery ルールで強制される。
決定論的だから testable: Rule Engine は同じ Token 状態 → 同じ ui.command を返す。だから単体テストが書ける。given: { cognitive_load: high, form_factor: phone } → expect: { density: minimal, layout: vertical }。LLM では絶対にできない検証が、Rule Engine では当たり前にできる。

部品と組み立て

AX Pattern Library との関係 — 23 の型紙を Engine が組む

AX Pattern はUI の小さな型紙。Rule Engine は、Token の状態に応じてどの型紙を選ぶか・どう組み合わせるかを決める。Pattern が単語、Rule Engine が文法 — だから "Context Grammar" と呼ぶ。

Delegation
D1–D6
AI が引き受ける
（6 パターン）
Escalation
E1–E5
人に確認をとる
（5 パターン）
Adaptation
A1–A8
見せ方を変える
（8 パターン）
Enterprise
X1–X4
組織内ふるまい
（4 パターン）

合計 23 パターン。Rule Engine は直接呼び出すのではなく、Token の状態を見てマッチするルールを発火し、結果として複数のパターンが合成された 1 個の ui.command を出す。

合成例 · "Silent Resolution"
山城家の朝、Mai が冷蔵庫前で何も言わなくても提案が出る瞬間 — これは単一パターンではなく、4 つのパターンの合成。
D4 · Omakase Mode D6 · Dynamic Friction E5 · Trust Breach Recovery A2 · Cognitive Scaling

D4 が「お任せモード」の骨格を提供し、D6 が「重要度に応じて確認を入れる」摩擦を加え、E5 が「Disclosure と Autonomy が矛盾していないか」を監視し、A2 が「Cognitive Load=high なので最小密度に圧縮する」役を果たす。Rule Engine はこの 4 つを 1 個の ui.command に畳み込んで emit する。

整理すると: AX Pattern Library = 部品カタログ、Rule Engine = 組み立て工場、ui.command = 完成した 1 個の指示書。新しいパターンを Library に足すと、Rule Engine はそのタグを持つルールが発火条件を満たしたときに自動で組み込む。Engine 自体に手を入れる必要はない。

アーキテクチャ

なぜ Rule Engine が Brain と UI の「橋」なのか

Brain は記憶、UI は画面。Rule Engine がいなければ、両側が直接つながって、デバイスが変わるたびに Brain を書き直す地獄になります。

Brain ↔ Rule Engine ↔ UI Surfaces
Rule Engine がない世界を想像してみる: Brain が直接 UI に「冷蔵庫の右上に卵の写真を 240 px で出して」と指示するなら、Samsung が新型冷蔵庫を出すたびに Brain を書き換えないといけない。Apple が画面サイズを変えるたびに作り直し。Rule Engine が間に立つと、Brain は「弁当を提案したい」と抽象的に言うだけで済む。Brain がデバイスを越えて portable になるのは、Rule Engine という翻訳層があるから。

よくある質問

疑問をまとめて解消する

Q1. Rule Engine は AI（LLM）なの？
違います。 Rule Engine は決定論的なルールの束。同じ入力 → 同じ出力。LLM は同じ入力でも毎回違う言葉を出す（生成的）。Context Grammar では、判断の骨格は Rule Engine、自然言語の表面は LLM と役割を分けている。「卵ハム弁当を提案する」という骨はルール、「あ、時間ないね。卵ハムどう？」という言葉遣いは LLM が当てる。
Q2. 同じ Token なら毎回同じ UI が出るの？飽きない？
命令は一致します。でも Token は毎瞬変わる。 Cognitive Load は時刻と直近 5 分のタスク数で揺れる。Form Factor はスマホを手に取った瞬間に変わる。だから実際の UI は飽きない。飽きるとしたら、それはToken を十分に読めていないサイン。「目の前に立っている人が違う」「時間帯が違う」という事実が Token に反映されていれば、UI は自然に変わる。
Q3. ルールが複数ヒットしたらどうする？
矛盾しなければ全部適用する。 「Cognitive Load=high → density:minimal」と「Social Exposure=public → hide:price」が同時に発火したら、両方適用（矛盾しないから）。矛盾した場合は Priority Weight Token が裁定する。「弁当が最優先」と Mai が言っているなら、見た目より速さを優先するルールが勝つ。詳細は Section F の衝突解決テーブル参照。
Q4. ui.command って具体的に何？JSON？
抽象的な構造体。 実装は JSON でも protobuf でも何でもいい。大事なのは intent / density / tone / candidates / constraints のような共通語彙を持つこと。この語彙さえ surface 側が読めれば、新しいデバイス（壁面ディスプレイ、AR グラス…）が出ても、Brain と Rule Engine をいじらずに対応できる。
Q5. Rule Engine と AX Pattern Library はどう違う？
AX Pattern = 部品、Rule Engine = 組み立て工場。 AX Pattern Library には 23 個の型紙が並ぶ（D1–D6 Delegation / E1–E5 Escalation / A1–A8 Adaptation / X1–X4 Enterprise）。Rule Engine は Token の状態に応じてどの型紙を選ぶか・どう組み合わせるかを決める。Pattern が単語、Rule Engine が文法、出てくる ui.command が文 — そう覚えると関係が綺麗に整理できる。
Q6. P1 の Context Brain と P4 の 5 Brain で Rule Engine は変わる？
変わりません。 Engine は Token の合成結果しか見ない。P1 では家庭用 Context Brain が 1 個で全 Token を構成する。P4 では Org / Brand × N / Research / Project Master / Project の 5 系統が並列で事実を持ち寄り、Token Bus で合成される。Engine の側からは「8 Token の現在値が来ている」だけで、上流が 1 個だろうと 5 個だろうと同じルールが回る。Engine を再利用できるのはこのためです。
