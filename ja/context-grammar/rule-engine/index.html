Rule Engine

Tokenが入力される。ひとつのui.commandが出力される。コンテキスト状態とUI描画の間にある決定論的な変換レイヤー。

Tokens IN → Rule Engine → ui.command OUT

スタック内の位置

8つのTokenが入力され、1つのCommandが出力される。

Rule Engineは語彙と動作をつなぐ橋である。8つのContext TokenとBrainのmemoryを受け取り、if/thenロジックを実行し、インタラクションごとにひとつのui.commandを出力する。

家のオーダーチケットシステム

仕組みに入る前に、全体をひとつのイメージで掴んでおこう。

レストランで例えると

ウェイターが注文を取るとき、事実を書き留める—「4番テーブル、ピーナツアレルギー、子連れ、急いでいる」。その事実をそのままキッチンに叫ぶわけではない。チケットシステムが標準化されたキッチン指示に変換する：ソース: 控えめ · 量: 70% · 優先度: 急ぎ。

シェフはチケットを読む。各キッチンステーションはそれぞれのスタイルで盛り付ける—和食、洋食、キッズメニュー。チケットはひとつ、表現は複数。

Rule Engineがそのチケットシステムだ。Tokenがウェイターのメモ。ui.commandがキッチンチケット。各サーフェス（冷蔵庫・スマホ・車）がそれぞれのステーションに当たる。

中核的な変換

Rule Engineはコンパイラである

BrainのmemoryとToken状態は、UIに直接到達できない。「疲れている」「電車の中」「片手」といった人間的な事実は、画面に何を描くべきかを伝えない。Rule Engineはそれらの事実を具体的な描画指示—ui.command—に変換する。

📥
Tokens IN
現在の状態

8つのContext Tokenの現在値、およびBrainから読み取った事実—アレルギー、予算、スケジュール。

  • Cognitive Load = high
  • Form Factor = phone
  • Social Exposure = public
  • Autonomy Dial = Confirm

Rule Engine
変換器

一致するルールを実行する。同じ入力は常に同じ出力を生成する—気分で変わることはない。

  • if Cognitive Load = high → density: minimal
  • if Form Factor = phone → layout: vertical
  • if Social Exposure = public → hide: prices
  • 23のAX Patternから組み立てる
→
📤
ui.command OUT
画面への指示

あらゆるサーフェスが読み取れる抽象的なコマンド—デバイスに依存しない描画指示。

  • density: minimal
  • items: 1
  • tone: gentle
  • hide: [price, calorie]
決定論的： Rule Engineは同じToken状態に対して、いつ・誰が・どのデバイスから呼び出しても、常に同じui.commandを返す。同じ条件、同じ答え。気分で変わることはない。この一貫性が、家族の信頼を支える基盤だ。

内部構造

Read → Match → Emit

Rule Engineのサイクルは3段階で動く。この流れを把握すれば、仕組みは迷いなく理解できる。

① Read
Tokenを収集する

8つのTokenの現在値をすべて集める。Brainから関連する事実を取得する—自宅では1つのBrain、エンタープライズでは最大5つ。アレルギー、予算、Brandの制約、Researchシグナル—すべてがここに集まる。

② Match
ルールを実行する

すべてのif/then条件を現在のToken状態に照合し、一致したものをすべて実行する。複数のルールが一致した場合は優先度でオーバーレイする。衝突はまずPriority Weight Tokenへ。

③ Emit
コマンドを組み立てる

実行された結果をひとつのui.commandオブジェクトに統合して出力する。この時点でデバイスはまだ決まっていない—それはサーフェス側の仕事であり、Engineの関与することではない。

重要： Rule Engineはデバイスを知らない。「冷蔵庫だから大画面」「スマホだから縦レイアウト」—これらはToken（Form Factor）の事実であり、Engineの判断ではない。Engineが実行するのは if Form Factor = phone → layout: vertical というルールだけだ。
Brainも同様： EngineはBrainの出所を区別しない。「Org Brainからの事実か」「Brand Brainからの事実か」を問わない。各BrainがToken setへの貢献に責任を持つ。Engineは統合された結果を読むだけだ。だから1つのEngineが家庭でもエンタープライズでも機能する。

スケール

1つのEngine — P1の単一BrainでもP4の5つのBrainでも

Rule Engineはスケールに依存しない。家庭のBrainでも5つのBrainからなるエンタープライズスタックでも、Engineは常にひとつの統合されたToken setを受け取り、同じルールを実行する。

⌬ マルチBrainの一貫性

Rule Engineが読むのはTokenの現在値だ—しかしその値は必ずしもひとつのBrainから来る必要はない。P1の単一Context BrainでもP4の5つのBrainを持つエンタープライズスタックでも、Engineは常にひとつの統合されたToken setを受け取る。

  • Org Brain — 永続的な基盤：組織図、ポリシー、用語集
  • Brand Brain × N — 判断DNA（B2C / B2Bが並列で動く）
  • Research Brain — ユーザー理解 + リアルタイムのCRM/売上シグナル
  • Project Master Brain — 戦略家：すべてのプロジェクトを統括する
  • Project Brain × N — 時限付き、プロジェクトごとの実行

これらのBrainはそれぞれのIdentity Layer・Learning Layer・Now LayerからToken Busへ事実を提供する。Rule EngineはBrainの数を数えない—常に同じ変換を実行する。同じEngine、異なるBrain構成—出力はTokenに従う。

技術的な深掘り

ルール構文 · スキーマ · 衝突解決

Rule Engineは理論ではない。3つのYAMLファイルと33のBehavior Rule—実際に書ける。

context.yml
Token + Brain スキーマ
8つのContext Token全体の型・有効な値・デフォルトを宣言する。Brainのリファレンスタイプもここで定義する—brain.allergy、brain.history.yesterdayなど。
rules.yml
33のBehavior Rule
条件と出力のif/thenマッピング。各ルールにはpriority（0〜999）と、所属するAX Patternを宣言するtagsが付与される。
patterns.yml
23のAX Patternレシピ
Delegation / Escalation / Adaptation / Enterprise — 4カテゴリ。どのルールグループが「Patternの発火」ひとつを構成するかを定義する。
ui.command スキーマ
出力構造の語彙
intent / density / items / tone / candidates / exclude / input / time-budget / decision-by — すべてのサーフェスが読む共通辞書。実装はJSONでもprotobufでもよい。
rules.yml — 抜粋
- id: cog_load_minimal when: { cognitive_load: high } then: density: minimal items: 1 priority: 80 tags: [A2-cognitive-scaling] - id: hands_busy_voice when: { physical_state: hands_busy } then: input: voice-first fallback: tap priority: 70 tags: [A4-input-mode-switch] - id: dyn_friction_high_value when: autonomy: Auto price: { gt: 15000 } then: require_confirm: true reason: "high-value purchase" priority: 100 tags: [D6-dynamic-friction] - id: disclosure_guard when: disclosure: hidden autonomy: { gt: Confirm } then: constraint_violation: true reset_to: Confirm priority: 999 tags: [E5-trust-breach-recovery]

衝突解決 — ルールが矛盾した場合

複数のルールが同時に実行されるのは通常の動作だ。矛盾しないルールはすべて適用される。矛盾するルールは3段階の仲裁を経る。

段階 仲裁者 判断基準
1 Priority Weight Token ユーザーが宣言した現在の優先事項—「お弁当を仕上げる」が最初に適用される。
2 ルールのpriority値 静的な数値ウェイト（0〜999）。Disclosure Guardのような信頼関連ルールは999に設定される。
3 BrainのLearning Layer この衝突タイプに対するユーザーの過去の判断パターン—歴史的により多く選ばれたほうを優先する。
絶対的な制約： Disclosure = hiddenとAutonomy > Confirmは共存できない。「開示なし × 完全委任」は論理的に不可能だ—Engineは常にAutonomyをConfirmにリセットする。これはpriority 999のTrust Breach Recoveryルールによって強制される。
決定論的 = テスト可能： Rule Engineは同じToken状態に対して常に同じui.commandを返すため、ユニットテストは簡単に書ける。given: { cognitive_load: high, form_factor: phone } → expect: { density: minimal, layout: vertical }。これはLLMが提供できない保証だ。

部品と組み立て

AX Pattern Library — Engineが組み立てる23のピース

AX PatternはUIの小さな設計図だ。Rule EngineはToken状態に基づいて、どの設計図を選びどう組み合わせるかを決める。PatternがBrainの語彙、Rule Engineが文法—このシステムが「Context Grammar」と呼ばれる理由はここにある。

Delegation
D1–D6
AIが委ねられる
（6パターン）
Escalation
E1–E5
AIが先に確認する
（5パターン）
Adaptation
A1–A8
AIが表示を調整する
（8パターン）
Enterprise
X1–X4
組織的な動作
（4パターン）

合計：23パターン。Engineはそれらを直接呼び出すのではなく、一致するルールを実行し、その結果として1つ以上のパターン発火に対応するui.commandを組み立てる。

コンポジション例 — 「沈黙の解決」
山代家のキッチンで、舞が一言も言わないまま提案が浮かび上がる瞬間。単一のパターンではなく、4つの組み合わせだ。
D4 · Omakase Mode D6 · Dynamic Friction E5 · Trust Breach Recovery A2 · Cognitive Scaling

D4が「AIに委ねる」骨格を提供する。D6が高額な場面で摩擦を加える—金額が閾値を超えたとき確認が発火する。E5がDisclosureとAutonomyの論理的整合性を監視する。A2がCognitive Loadが高いためdensityをminimalに圧縮する。Engineは4つすべてを1つのui.commandに折りたたむ。

一言で： AX Pattern Library = 部品カタログ。Rule Engine = 組み立て工場。ui.command = 完成した指示書。Libraryに新しいPatternを追加すれば、そのPatternのタグが付いたルールが発火するたびにEngineが自動的に拾い上げる—Engine自体は変更不要だ。

アーキテクチャ

Rule Engineが橋である理由

Brainはmemoryを保持する。UIはピクセルを描画する。この2つの間にRule Engineがなければ、両者は密結合になる—デバイスが変わるたびに修正が必要な保守の悪夢だ。

Brain ↔ Rule Engine ↔ UI Surfaces
Rule Engineなしの世界を想像してほしい：BrainはSamsung Family Hubに直接指示することになる—「卵の写真を右上240pxに配置せよ」と。Samsungの新モデルが出るたび、画面サイズが変わるたびにBrainを書き直す必要が生まれる。Rule Engineがそのすべてを吸収する。Brainはただ「お弁当を提案する」と言うだけでいい—将来出荷されるすべてのデバイスで動き続ける。

Q&A

よくある質問

Q1. Rule EngineはAI（LLM）ですか？
違う。 Rule Engineは決定論的なルール束だ—同じ入力は常に同じ出力を生成する。LLMは同じ入力に対して毎回異なる言葉を生成する（生成的）。Context Grammarでは、意思決定の骨格がRule Engine、自然言語サーフェスがLLMだ。「卵&ハムのお弁当を提案する」がルール。「時間ないけど、卵&ハムはどう？」がLLMレイヤーだ。
Q2. 同じTokenが常に同じUIを生成するなら、単調にならないですか？
commandは一貫している—しかしTokenは毎秒変化する。Cognitive Loadは時刻と最近のタスク量によって変動する。Form Factorはスマホを手に取った瞬間に変わる。UIは自然に追従する。単調さは読み取られているTokenが少ないサインだ—立っている人が違う、時刻が違う、それらの事実がすでにTokenに入っているはずだ。
Q3. 複数のルールが同時に実行された場合はどうなりますか？
矛盾しないルールはすべて適用される。「Cognitive Load=high → density:minimal」と「Social Exposure=public → hide:price」は同時に発火する—矛盾しないため両方が適用される。矛盾する場合は3段階の仲裁へ：Priority Weight Tokenが最初、次にルールのpriority値、そしてBrainのLearning Layerの履歴。詳細はセクションFの衝突テーブルを参照。
Q4. ui.commandとは具体的に何ですか？JSONですか？
抽象的な構造だ。実装はJSON、protobuf、何でもよい。重要なのは、すべてのサーフェスが読める共通語彙—intent / density / tone / candidates / constraints—が存在することだ。新しいデバイス（壁面ディスプレイ、ARグラス、ロボット）が加わっても、BrainやEngineに触れる必要はない。
Q5. Rule EngineとAX Pattern Libraryの違いは何ですか？
AX Pattern = 設計図。Rule Engine = 組み立て工場。Libraryは23の設計図を持つ—D1〜D6 Delegation、E1〜E5 Escalation、A1〜A8 Adaptation、X1〜X4 Enterprise。Rule Engineは現在のToken状態に対してどの設計図を選びどう組み合わせるかを決める。PatternがBrainの語彙、Rule Engineが文法、出力されるui.commandが一文だ。
Q6. P1の単一BrainとP4の5つのBrainの間でRule Engineは変わりますか？
変わらない。Engineが読むのは統合されたToken setだけだ。P1では1つのContext Brainが8つのTokenをすべて組み立てる。P4では5つのBrainタイプ—Org、Brand × N、Research、Project Master、Project—がそれぞれToken Busへ事実を提供し、最終的なToken setを統合する。Engineにはどちらも「8つのToken値がある」と見える。同じルールを実行するだけだ。その再利用こそが設計の狙いだ。
