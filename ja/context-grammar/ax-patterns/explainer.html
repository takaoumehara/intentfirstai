Context Grammar · Concept Explainer · 平易な日本語で

AX Patterns は
「型紙」の集まりです。

Brain は記憶、Token は今の状態、Rule Engine は翻訳機。
最後に出てくる UI を作るときに、毎回ゼロから考えないための型紙が AX Patterns。
23 個の小さな部品を組み合わせて、家族の朝・旅・買い物すべての画面を組み立てます。

§1

まず根っこから — AX Pattern は「再利用できる型紙」

AX は Agentic eXperience の略。AI が動く時代の UI 体験のことです。 その体験を作る型紙が AX Pattern。23 個に整理されていて、どれも「いつ使うか」「どう振る舞うか」がセットで決まっています。

🧩
これは Pattern
再利用できる型紙

いつ発動するか（Token 条件）と、どう振る舞うか（UI 規則）が決まっている。プロジェクトをまたいで使える。

  • Approval Gate(D1) — 承認・修正・却下の関門
  • Confidence Signal(E1) — AI の確信度を可視化
  • Cognitive Scaling(A2) — 忙しさで情報密度を変える
  • P1, P2, P3, P4 すべてで再登場する
vs
🖼
これは Pattern じゃない
ただの画面・ただの機能

「弁当提案画面」「旅プラン編集ページ」のような固有の画面。一度きり、他で使えない。

  • 「Mai の朝の弁当画面」(個別)
  • 「ロンドン旅 4 日目の地図」(個別)
  • 「Sota のサッカー靴注文ページ」(個別)
  • これらは Pattern を使って組み立てた結果
覚え方: Pattern はレゴブロック。画面はレゴで作った家。 家は無限にあるけど、ブロックは 23 種類で済む。だから家族の朝も、旅先のアプリも、エンタープライズの管理画面も同じブロックで組める。
§2 · 線引き

「Pattern」と「ただの UI 工夫」は別もの

「これって Pattern？」と迷ったら、3 つの問いを通せば分かります。3 つ全部 YES なら Pattern。1 つでも NO なら、ただの UI アイデア。

Q1 · Token 条件
いつ発動するか書ける？

「Cognitive Load=high のとき」「Autonomy Dial=Confirm のとき」のように、Token の値で発動条件を書けるか。

書けない → 単発のアイデアであって、Pattern ではない。

Q2 · 再利用
違うシーンでも使える？

弁当でも、靴でも、旅程でも、社内承認でも同じ仕組みで動くか。シーン固有のものは型紙ではない。

1 シーン専用 → 画面 (screen) であって、Pattern ではない。

Q3 · デバイス独立
どの surface でも成立する？

iPhone・冷蔵庫・CarPlay・Apple Watch、どれにも形を変えて当てはまるか。「iPhone 限定」のものは型紙ではない。

1 デバイス専用 → コンポーネント (component) であって、Pattern ではない。

具体例で線引き:
✓ Approval Gate (承認関門) — Token 条件あり / 弁当でも靴でも使える / 冷蔵庫でも iPhone でも成立 → Pattern。
✗ 「弁当提案カードの右上に時間を出す」 — Token 条件なし / 弁当限定 / iPhone 限定 → ただの UI 工夫。Pattern ではない。
§3 · 比喩

レストランで考えてみる — 「盛り付けの型」と「料理そのもの」

Pattern の正体は、料理のレシピでも、メニューでもありません。料理人が体に染み込ませている「こういう時はこう盛る」「こういう客にはこう声をかける」という型。

🍽 厨房とホールの「型」

🧩 AX Pattern = 盛り付け・接客の型

「どう出すか」「どう声をかけるか」の決まった作法。何の料理にも使える。

・お会計を「カード／現金／後払い」で聞く型 (Approval Gate)
・自信のない料理は「お口に合わなかったら替えますね」と添える型 (Confidence Signal)
・忙しそうな客には選択肢を 3 つに絞る型 (Cognitive Scaling)
・常連には黙ってビールを出す型 (Omakase Mode)

🍳 これは Pattern じゃない

「今日の鮭の照り焼き」みたいな個別の料理・個別のシーンは Pattern ではない。

・本日のメニュー (= 画面)
・特定の客の好み台帳 (= Brain)
・冷蔵庫の在庫表 (= Token)
・「ピーナッツ抜きで」という一回の指示 (= 個別命令)
料理 (= 画面) は毎日違うけど、盛り付けの型 (= Pattern) はずっと同じ。 だから新人でも、型を覚えれば初めて作る料理でもサマになる。AX Pattern Library が目指しているのも、これと同じ。 新しいプロジェクトで新しい画面を作るときに、デザイナーが毎回ゼロから悩まないように、型紙を 23 枚だけ用意しておく。
§4 · 全体像

3 つのバケツに 23 個の型紙

23 個の型紙は、3 つの大きなバケツに分けて整理されています。 Delegation (委譲) / Escalation (返却) / Adaptation (適応)。さらに Enterprise 専用の追加が 4 個。

Delegation · 6 patterns
人 → AI に任せていく

信頼を少しずつ AI に渡していく型紙。「最初は毎回確認、慣れたら任せる」という流れを設計する。

  • D1Approval Gate 承認・修正・却下の関門を置く Sota の靴 ¥4,800 → Mai に「OK / 違う色 / やめる」を出す
  • D2Progressive Trust 成功体験が貯まると確認回数を減らす 8 週連続で食材代替 OK → 確認 → 通知だけに昇格
  • D3Proactive Nudge 余裕がある時間帯に先回り提案する 9:15 AM、Cognitive Load 低 → 「明日の食材を見ておきますか？」
  • D4Omakase Mode 十分信頼できる領域は完全委任 牛乳・ヨーグルトの定期発注 → 黙って買って事後報告
  • D5Substitution Modes 代替の自由度を 4 段階で指定 (Exact / Flexible / Exploring / Surprise) アレルギー食材 = Exact 固定 / 飲料 = Surprise OK
  • D6Dynamic Friction 高リスク・高額は信頼が育っても摩擦を残す ¥200 のおやつ = Auto / ¥15,000 のワイン = 必ず提案のみ
Escalation · 5 patterns
AI → 人に判断を返す

AI が自分の限界・不安を認識して、人に判断を戻す型紙。返さなさすぎる AI は暴走、返しすぎる AI は使えない。

  • E1Confidence Signal 確信度をバーで見せる (71% など) 翻訳の自信が低い箇所をオレンジで表示
  • E2Limitation Disclosure 「これは私には判断できません」と正直に開示 Hana が発熱 → 「医療判断は不可。近くの病院 →」
  • E3Rollback 実行済みを取り消し、代替を提示 航空券キャンセル → 16:30 便を自動提案
  • E4Ambiguity Escalation グレーゾーン (40-79%) は警告つきで人に渡す Sota にこの辛さは大丈夫？ → A/B で Mai に判断委ね
  • E5Trust Breach Recovery AI が間違えたら Autonomy Dial を 1-2 段階降格 誤注文 → Notify から Suggest に戻して再構築
Adaptation · 8 patterns
文脈 → UI を変形させる

場面・デバイス・同席者の変化に応じて UI の形・密度・公開度を変える型紙。文脈が戻れば UI も戻る。

  • A1Form Factor Transform デバイス変化で UI 構造ごと作り直す iPhone の縦リスト → TV のグリッドへ
  • A2Cognitive Scaling 忙しさに応じて情報密度を増減 朝 7:02 = 候補 1 つ / 9:15 = フルメニュー
  • A3Social-Aware Filtering 同席者で表示内容をフィルタ 来客時は買い物履歴と価格を非表示
  • A4Disclosure Cascade FULL / SUMMARY / EXISTENCE / HIDDEN の 4 段階 医療情報 = 本人 FULL、配偶者 SUMMARY、客は HIDDEN
  • A5Disposable Surface 目的のために生まれ、達成後に消える UI London Trip 用画面 → 帰宅後に消滅、学びだけ Home Brain に残す
  • A6Care Architecture 効率より関係性。ケアの機会を浮かび上がらせる 「お母さんの誕生日来週、去年は花でしたね」
  • A7Live Recomposition 外部状態が変わったら計画を即時再構成 雨予報 80% → 屋外マーケット → 屋内博物館に差し替え
  • A8Temporal Handoff 時限 Brain の学びを Home Brain に蒸留して戻す Trip Brain 終了 → 「3 つの好み」だけ Home Brain に残す
Enterprise · 4 patterns
エンタープライズ専用の追加

P4 (Enterprise Context Brain) で必要になった 4 つ。組織で AI を使うときに欠かせない型紙。

X1Reasoning Trace — 判断の根拠を折りたたみで開示。「なぜこの提案？」に展開で答える。

X2Inline Edit — AI 提案をその場で修正して再実行。「ほぼ良いが微調整したい」に応える。

X3Autonomy Dial UI — Suggest → Confirm → Notify → Auto を明示的に操作する UI。Disclosure Dial と連動。

X4Source Attribution — AI 回答がどのデータに依拠したかを明示。CRM・メール・カレンダー等。

23 = 6 + 5 + 8 + 4。 「23 という数字に意味はあるの？」とよく聞かれるけど、意味はない。 Yamashiro 家・London Trip・P4 の 8 章すべてを実装してみたら、ちょうど 23 種類の型で足りた。
新しいシーンを設計して、どの型でも書けないと分かったら、24 個目を足す。逆に重複が見つかったら統合する。固定数ではなく育つカタログ。
§5 · 合成

Pattern は組み合わせて使う — Silent Resolution の正体

Pattern は単体で輝かない。4 つを組み合わせて 1 つの体験になる。 Yamashiro 家でいちばん象徴的な「Silent Resolution (静かに解決)」を例に、4 つの型紙がどう噛み合うかを分解します。

「お母さん、サッカーシューズきつい！」

— Sota (11歳) · 火曜 7:08 AM, 朝食中

この一言で起きること: Mai は何も判断しない。AI が裏で 4 つの型紙を発火させ、靴を注文し、事後報告だけ届く。これが Silent Resolution。 Pattern を 1 つだけ使ってもこれは作れない。4 つの組み合わせで初めて成り立つ。
🧩 Silent Resolution = 4 patterns wired together
D4
Omakase Mode
「子供の必需品 ¥50 以下なら任せる」と Mai が事前設定済み。土台。
D6
Dynamic Friction
$48 は安全圏。これが ¥30,000 のスニーカーなら摩擦が戻り、Auto は止まる。
E5
Trust Breach Recovery
「Tap to undo」が 30 分残る。失敗したら Autonomy が 1 段階下がる安全装置。
A2
Cognitive Scaling
朝 7 時の Mai は両手塞がり。通知は 1 行・受動・スワイプで終わる形に圧縮。
= Silent Resolution. 「Mai が朝の判断地獄から解放される」体験は、この 4 つの型紙が同時に発火している結果。1 つでも欠けると破綻する。
1 D4 Omakase Mode が発動条件を満たす Delegation
Mai は Brain の Identity Layer に「子供の必需品 ¥50 以下は任せる」を 6 か月前に登録済み。 Sota の靴は $48 = 子供必需品カテゴリ。D4 の発動条件 (Autonomy=Auto + Disclosure=FULL + Brain L2 trust score=HIGH) を満たす。

もしこの設定がなければ、AI は提案で止まり、Mai に「買っていい？」と聞いていた。Omakase Mode は"自動進行を許可する旗"。
2 D6 Dynamic Friction が金額をチェック Delegation
Auto に進む前に、もう一つ関門がある。D6 が「この金額・この種類は本当に Auto で良いか」を再判定する。 $48 は予算枠 $50 の中、月次バジェット $230 残り十分。Friction = 0 → 通過。

これが ¥30,000 の高級スニーカーだったら、D4 が許可しても D6 が止める。D4 と D6 は重なって守る。Omakase の暴走は D6 が押さえる。
3 E5 Trust Breach Recovery が安全装置を仕込む Escalation
購入と同時に、E5 が「30 分以内なら Tap to undo で取り消せる」窓を開ける。 もし Mai が「あ、それじゃなくて」と Undo したら、E5 は Autonomy Dial を Auto → Notify に 1 段階降格し、Brain の Learning Layer にネガティブシグナルを記録する。

Pattern は失敗を前提に組まれている。Auto は不可逆ではなく、「短い時限つきの Auto」として実装される。
4 A2 Cognitive Scaling が通知の形を圧縮する Adaptation
最後に、A2 が「Mai に何をどう見せるか」を整える。 朝 7 時、両手塞がり、Cognitive Load = HIGH。詳細画面は出さない。1 行・色控えめ・スワイプで消せる通知に圧縮する。

"Sota's soccer shoes ordered. Auto-approved. $48. — Tap to undo."
昼ごはんの後、Mai が落ち着いて確認するときには A2 が再発火し、同じ事実をもっと詳しい形に展開できる。
5 結果: Silent Resolution が成立 Result
Mai が朝食で受けた「シューズきつい」一言は、4 つの Pattern が連鎖した結果として、注文済み・取消可・通知最小・予算反映済の状態になっている。 Mai は何も決めていない。でも全部のセーフティが効いている。これが Silent Resolution の正体。
→ D4 + D6 + E5 + A2 = Silent Resolution
大事な気づき: Silent Resolution は独立した「機能」ではない。 23 個の型紙のうち 4 つを正しい順序で発火させた結果として現れる現象。だから新しいシーン (旅行先のチケット予約・在宅介護の薬の補充など) でも、同じ 4 つの型紙を組めば再現できる。
Pattern は単語、合成は文章、Silent Resolution は段落。これが "Context Grammar" の "Grammar" たる所以。
§6 · なぜカタログ化するのか

Pinterest じゃなくて、システム

「いいデザイン」を集めただけなら、Pinterest や Mobbin で十分。AX Pattern Library が違うのは、Token 条件・原則・合成ルールがセットで定義されていること。これが「集まり」と「システム」の境目。

① 再利用

同じ型を別シーンに使い回せる

Approval Gate は靴の購入でも、旅程の確定でも、営業メールの送信承認でも、まったく同じ仕組みで動く。23 個の型を覚えれば、無限のシーンが組める。

② 一貫性

家族・職場・どこでも同じ作法

D2 Progressive Trust の昇格条件 (8 週連続成功 → Notify) は P1 でも P4 でも同じ。家庭の弁当 AI と会社の営業 AI が同じ作法で振る舞う。学習コストが激減する。

③ 検証可能

「これは正しいか」を議論できる

「この画面は Pattern X の発動条件を満たしているか？」と問えば、議論が具体になる。「なんか良くない気がする」が「D6 の摩擦が抜けている」になる。デザイン批評が言語化される。

④ 育つカタログ

新シーンが新パターンを呼ぶ

新しい設計をして、23 個のどれでも書けないと分かったら、24 個目を提案する。Care Architecture (A6) は P5 で初めて出てきた。ライブラリは固定ではなく、家族構成や事業領域と一緒に育つ。

Pinterest との違いを一言で: Pinterest は「いいデザインの写真集」。AX Pattern Library は「いつ・なぜ・どう組み合わせるか」のルールブック。 前者は眺めるもの、後者は使うもの。だからカタログ化に意味がある。
§7 · これからどうするか

推奨アクション

AX Pattern Library を portfolio で使うときに、徹底すべき 3 つ。

1
画面ごとに「使った Pattern」をタグで貼る
各 UI モックアップに D1 / E5 / A2 のような Pattern ID を 2-4 個タグ付けする。読者が「あ、ここでも Approval Gate 使ってる」と横串で認識できる。これが "system" を可視化する一番手軽な方法。
2
「合成して 1 体験」を毎プロジェクトで 1 回見せる
Silent Resolution のように 4 つ程度の Pattern を組んで 1 つの現象を描くシーンを、各プロジェクト最低 1 つ用意する。単発の Pattern 紹介だけだと、読者は「なんかいいけど点でしかない」と感じる。線で繋ぐと一気に強度が出る。
3
新しい Pattern を発見したら 24 個目として記録する
設計中に「23 個のどれにも当てはまらない」シーンに出会ったら、それは新しい Pattern の候補。安易に既存 Pattern にねじ込まず、AX_Pattern_Library_Definition.md に下書きで追加し、Token 条件・原則・例を埋める。育つカタログを実装する。
§8 · よくある混乱

よくある質問を整理する

Q1. AX Pattern と「デザインパターン」(GoF など) は同じもの？
遠い親戚です。 ソフトウェアの GoF パターンは「Singleton」「Observer」のようにコードの構造を扱う。 AX Pattern は Agentic UX の振る舞いを扱う。共通点は「再利用できる型紙にする」という考え方。 違いは、AX Pattern は必ず Token 条件 (人間や状況) をトリガーに含むこと。コードだけでは閉じない。
Q2. なぜ Delegation・Escalation・Adaptation の 3 バケツ？
3 つが互いに独立しているから。 Delegation は「人 → AI」、Escalation は「AI → 人」、Adaptation は「文脈 → UI」。方向と主語がそれぞれ違う。 ある場面で 3 つすべてが同時に起きうるし、片方だけが起きることもある。だから 3 つに分けると Pattern が綺麗に整理される。 (2 つだと足りない、4 つ目を加えても他の 3 つの組み合わせで書けてしまう。Einstein's Test 済み。)
Q3. 23 個も覚えないとダメなの？
全部覚える必要はないです。 設計中に「これって Pattern として整理されてないかな？」と思ったときにカタログを引けばいい。 よく使う 5-6 個 (Approval Gate · Progressive Trust · Cognitive Scaling · Disclosure Cascade · Trust Breach Recovery など) は自然に手に馴染む。 残りはレファレンスで十分。"覚えるカタログ" ではなく "引くカタログ"。
Q4. Pattern と Component (CSS の部品) はどう違う？
Pattern は「振る舞いのレシピ」、Component は「具体的な UI 部品」。 Approval Gate (Pattern) は「承認・修正・却下を 3 ボタンで聞く」という振る舞いの規約。 これを iPhone 用に実装した「3 ボタンの SwiftUI ビュー」が Component。 Pattern は 1 つでも、Component は surface ごと (iPhone / Watch / 冷蔵庫) に複数存在する。AX Pattern Library が定義するのは Pattern の方だけ。
Q5. これって Material Design の "design system" と何が違うの？
カバーしている層が違います。 Material は見た目とコンポーネント (色・余白・ボタン形状) を統一するシステム。 AX Patterns は振る舞いと判断のしかた (いつ AI が引き下がるか、いつ任せるか、いつ画面を作り直すか) を統一するシステム。 両者は対立しないし、両方必要。Material が「絵の具」だとすれば、AX Pattern は「絵の構図」。Context Grammar は構図の文法を扱う。
