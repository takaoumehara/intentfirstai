Context Grammar — Floor 5

AX Patterns

AIが届け、判断を戻し、適応する方法を定義した23のパターン。Rule Engineが動いたとき、レスポンスが取る形がここにある。

AX Patterns

レシピではなく、技法

レシピは「何を作るか」を決める。技法は「包丁の使い方」を決める。Context GrammarのRulesはレシピだ — 何をすべきかを決める。AX Patternsはキッチンの技法 — どう実行するかを決める。どんな料理を作っていてもその技法は変わらない。

パターンはデバイス非依存、Token起動、再利用可能だ。 D2 Progressive Trustはスマートフォンでも冷蔵庫のディスプレイでも車のスクリーンでも同じように機能する — トリガーはBrain Context Brain · Level 2 — Learning Layerの成功回数であり、サーフェスではない。

レストランで例えると

メニューはキッチンに「何を作るか」を伝える。でも料理をどう席まで届けるか — 料理の説明をするか、アレルギーを確認するか、グラスを黙って注ぎ足すか — それが技法だ。腕のいいウェイターは、どのゲストにも、毎晩同じ技法を使う。それがAX Patternsだ。

定義

パターンか、そうでないか

すべてのデザイン判断がパターンになるわけではない。カタログに名前を載せるには、3つの問いに答える必要がある。

1

Tokenの条件はあるか？

特定のToken値がトリガーになっているか？「なんとなく適切なとき」という曖昧なトリガーはヒューリスティックであり、パターンではない。

2

文脈をまたいで再利用できるか？

食料品の買い物、旅行計画、企業の承認フローで同じように使えるか？1つのシナリオにしか合わなければ、それはフィーチャーであり、パターンではない。

3

デバイス非依存か？

インタラクションのロジックはフォームファクターに関係なく成立するか？スマートフォン以外で崩れるならコンポーネントであり、パターンではない。

Pattern

D4 Omakase Mode

AIへの完全委任 — Autonomy = Auto、Disclosure = Full、Brain Context Brain · Level 2 — Learning Layerの信頼が高いときに起動する。

  • トリガー：3つの特定Token条件がすべて成立
  • 食料品、スケジュール、旅行予約、エンタープライズで機能する
  • スマートフォン、冷蔵庫、CarPlay、企業ダッシュボードでも同じロジック
VS

パターンではない

"スマートな提案"

AIが自信を持ったときに提案を表示する。定義されたトリガーなし、一貫した形式なし、再利用の契約なし。

  • Token条件の指定なし — ただ「自信がある」だけ
  • 実装はプロダクトチームごと、四半期ごとに異なる
  • 一貫した成功基準に照らしてテストできない

カテゴリ

4つのカテゴリ、23のパターン

すべてのパターンは3つの方向性 — Delegation、Escalation、Adaptation — のどれか1つに属し、さらにEnterpriseという拡張がある。各方向性は概念レベルで相互排他的だ。

D · Delegation

AIへ権限を委ねる

6 patterns

人間が意思決定と実行をAIへ段階的に委ねていく設計。信頼が前提条件 — これらのパターンは信頼を測定し、それに基づいて動く。

Human → AI
E · Escalation

判断を人間に返す

5 patterns

AIが自分の限界を認識し、制御を返す設計。Autonomy Dialのレベルに関係なく適用される — AIの不確実性は委任より常に優先される。

AI → Human
A · Adaptation

UIがコンテキストとともに変容する

8 patterns

Token値が変わったとき、インターフェースが自分を再構成する設計。コンテンツは変わらなくても、形・密度・可視性が変化する。

Context ↔ UI
X · Enterprise

高リスクな組織向けパターン

4 patterns

複数人・コンプライアンス重視・監査が必要なコンテキスト固有のパターン。同じ3方向を基盤にしつつ、組織の信頼要件に対応して強化されている。

Team + AI

レストランで例えると

Delegationは、ウェイターがゲストの好みをだんだん信頼して、頼まれる前に選択肢を届けるようになること。Escalationは、「スパイスについては自信がないので、シェフに確認します」とウェイターが言うこと。Adaptationは、ダイニングルームが場に応じて照明・テーブルの間隔・メニューの形式を調整すること。Enterpriseは、引き継ぎを記録しながら200人分をさばくバンケット運営チームのことだ。

D Delegation（委任） 6 patterns
D1

Approval Gate（承認ゲート）

AIの提案が実行される前に、ユーザーが承認・編集・却下できるチェックポイント。

トリガー：Autonomy = Confirm + Priority Weight = HIGH。例：冷蔵庫が食料品の注文を提案 — 花は送信前に「承認」「編集」「スキップ」のいずれかをタップする。

D2

Progressive Trust（段階的信頼）

成功した実績が積み重なるにつれて、AIはより少ない摩擦で行動する権限を得ていく。

トリガー：Brain Context Brain · Level 2 — Learning Layerの成功カウントが閾値を超える。例：1〜3週目、花はすべての代替品を承認する。8週目にはシステムがNotifyに移行 — 彼女は交換を事後に確認する形になる。

D3

Proactive Nudge（先回りの提案）

Cognitive Loadが低く、行動できる余裕があるタイミングを狙ってAIが非緊急の提案を表示する。

トリガー：Cognitive Load = LOW + Priority Weight = MEDIUM + Feasibility = OK。例：土曜の朝、誰も急いでいない — アプリが「海のサッカースパイクがそろそろ替え時。シーズン末セール中」と表示する。

D4

Omakase Mode（おまかせモード）

信頼・開示・Brainの確信度がすべて最大値に達したドメインで、AIに完全委任する。

トリガー：Autonomy = Auto + Disclosure = FULL + Brain Context Brain · Level 2 — Learning Layer trust ≥ HIGH。例：花は何も言わない — いつもの食料品注文が、彼女が頼んだとおりに自動で完了する。

D5

Substitution Modes（代替モード）

商品ごと・リスクレベルごとに設定できる4段階の代替自由度 — Exact（完全一致）、Flexible（柔軟）、Exploring（探索）、Surprise（サプライズ）。

トリガー：在庫切れ + Brain Context Brain · Level 2 — Identity Layerに代替設定が保存されている。例：光司のピーナッツバターはExact設定（アレルギーリスク）。ヨーグルトのブランドはFlexible。新しいスナックはSurprise。

D6

Dynamic Friction（動的摩擦）

高コストまたは高リスクな操作は、全体の信頼が成熟していても確認ステップを維持する — Progressive Trustが超えられない上限。

トリガー：Feasibility × Risk ≥ 閾値。例：冷蔵庫はヨーグルトを自動で再注文する。しかし15,000円の家電は必ず確認を求める — 信頼とリスクは独立した軸だ。

E Escalation（エスカレーション） 5 patterns
E1

Confidence Signal（確信度の提示）

AIが自分の不確実性を段階的に表示する — 疑念を隠すのではなく、読み取れる形にする。

トリガー：AI確信度 ≤ 80% + Social Exposure ≥ MEDIUM。例：旅行アプリがホテルの推薦に「71%マッチ — 他の候補あり」と表示する。自信ありげな1択ではなく。

E2

Limitation Disclosure（能力限界の開示）

AIが自分にできないことを正直に伝え、適切なリソースへ誘導する。

トリガー：AIの能力範囲外のリクエスト + Priority Weight = HIGH。例：旅行中にミアが体調不良を訴える。アプリは「近くのクリニックは探せますが、医療判断はできません」と伝え、地図を表示する。

E3

Rollback（巻き戻し）

実行後に外部条件が変わったとき、AIが完了した操作を取り消して代替案を提示する。

トリガー：実行済み + 実行後にFeasibilityが変化。例：予約済みの14:00便が航空会社によってキャンセルされた。アプリが取り消し線を引き、追加費用なしの16:30便を表示する。

E4

Ambiguity Escalation（曖昧性のエスカレーション）

AIがグレーゾーンの判断を警告とともに提示し、最終決定を明示的に人間に委ねる。

トリガー：AI確信度 = 40〜79%。例：プランナーが特定の美術館を海が楽しめるか確信を持てない。疑念をフラグ立てし、2つの選択肢を示して「あなたが決めてください」と伝える。

E5

Trust Breach Recovery（信頼回復）

AIの判断ミスの後、Autonomy Dialが一段階下がり、信頼が低いステージから再構築される。

トリガー：ユーザーがAIの判断を却下または取り消す。例：花が明示的にブロックしていた代替品を却下する。システムはNotify → Suggestに降格し、信頼が再確立されるまですべての交換を確認する。

A Adaptation（適応） 8 patterns
A1

Form Factor Transform（フォームファクター変換）

アクティブなデバイスが変わると同じコンテンツが再構成される — メッセージは同じ、器だけが変わる。

トリガー：Form Factorが変化（スマートフォン ↔ TV ↔ ウォッチ）。例：家族旅行のitineraryは花のスマートフォンではスクロールリスト。TVにキャストすると写真付きのフルブリードタイムラインになる。

A2

Cognitive Scaling（認知スケーリング）

Cognitive Loadが高いときは情報密度と選択肢の数が絞り込まれ、低下すると広がる。

トリガー：Cognitive Load = HIGH。例：空港で遅刻しそうな花には3つの事前選択済み候補が表示される。家の静かな夜には12件すべてのリストが見える。

A3

Social-Aware Filtering（ソーシャル対応フィルタリング）

誰がそこにいるかによって表示内容が変わる — 露出度が上がるにつれて価格・ウィッシュリスト・個人メモが隠れていく。

トリガー：Social Exposure ≥ MEDIUM + Disclosure Dial ≠ FULL。例：1人でいるとき、花には価格と予算統計が見える。ディナーパーティーでは、TVはレシピだけを表示し、費用は見えない。

A4

Disclosure Cascade（開示のカスケード）

情報の可視性がドメインごと・人ごとに4段階 — FULL → SUMMARY → EXISTENCE → HIDDEN — で変化する。

トリガー：Disclosure Dialの設定 × Social Exposureの変化。例：光司の病歴：花にはFull、かかりつけ医のアプリにはSummary、学校の保健室フォームにはExistenceのみ。

A5

Disposable Surface（使い捨てサーフェス）

UIのインスタンスが特定の目的のために生まれ、その目的が完了したら消える — Disposable Brainのライフサイクルと連動する。

トリガー：Intent = 期間限定の目標 + Disposable Brain生成。例：京都旅行のUIは出発の朝に現れ、旅の間に学び、帰宅すると消える。

A6

Care Architecture（ケアの設計）

AIが感情的・関係的なコンテキストを追跡し、日常に埋もれたケアの機会を浮かび上がらせる。

トリガー：Brain Context Brain · Level 2 — Learning Layerの関係データ + 感情的コンテキストの変化。例：花が気づく前に「来週お母さんの誕生日 — 去年はお花を送りました」とアプリが表示する。

A7

Live Recomposition（ライブ再構成）

天気・キャンセル・在庫など外部条件が変化したとき、既存のプランが継ぎ目を見せずに即座に再構築される。

トリガー：外部Feasibilityの変化 + 既存プランが存在。例：屋外マーケットが雨で中止になった。itineraryが同じ時間帯の屋内美術館に静かに差し替える。

A8

Temporal Handoff（時限の引き継ぎ）

Disposable Brainが終了するとき、そこで蒸留された学びが永続的なHome Brainに戻る — 一時的なコンテキストは消え、知識は残る。

トリガー：Disposable Brainのライフサイクル終了 + Brain Context Brain · Level 2 — Learning Layerの統合ウィンドウが開く。例：京都旅行後、「海はラーメンが大好き」「ミアは15時を過ぎると疲れる」がHome Brainに書き込まれる。Trip Brainは消える。

X Enterprise（エンタープライズ） 4 patterns
X1

Reasoning Trace（推論の追跡）

AIの意思決定の根拠を折りたたみ形式で表示できる — 高リスクな判断では自動展開し、それ以外は非表示。

トリガー：Priority Weight = HIGH またはユーザーが展開を要求。例：AIがベンダーAを推薦する。プリヤは答えを見る。「なぜ？」をタップすると、その根拠になった3件のCRMスレッドと2件のカレンダー項目が現れる。

X2

Inline Edit（インライン編集）

AIの提案をその場で編集して即座に再実行できる — Approval Gate内の「編集」パス。

トリガー：Approval Gateで「編集」を選択。例：AIがセールスメールの下書きを生成する。プリヤが1文をインラインで変更すると、システムが下書きを再生成し、数秒で修正版が返ってくる。

X3

Autonomy Dial UI（Autonomy Dial の操作UI）

Suggest・Confirm・Notify・Autoの4段階のAutonomy levelをユーザーが明示的に制御する — Disclosure Dialとセットで使う。

トリガー：ユーザーが設定で明示的に調整。例：プリヤがブリーフ作成エージェントを、クライアント向けコンテンツはConfirm、内部ドラフトはNotify、初回リサーチ要約はAutoに設定する。

X4

Source Attribution（ソース帰属）

AIの回答に、それを生成した具体的なデータソース — CRM・メール・カレンダー — を含め、監査・コンプライアンス要件を満たす。

トリガー：コンプライアンスルールが有効またはユーザーがソース証拠を要求。例：「Q3売上12%増」の表示にCRM・Email・Calendar・Sheetsのチップが付き、1タップで追跡できる。

組み合わせ

パターンは重なり合う

1つのパターンが単独で動くことはほとんどない。本物のエージェント動作は、複数のパターンが順番に、あるいは並列に発火した結果だ。1つの例を示す：Silent Resolution（静かな解決） — 山城家の食料品注文が、ブロックされた商品を誰の朝も邪魔せずに処理する方法。

1

D4 · Omakase Mode

注文が自動で走り始める

火曜の朝。Autonomy = Auto、Disclosure = Full、食料品ドメインのBrain Context Brain · Level 2 — Learning Layer信頼度は高い。週次注文が誰にも確認せずに動き始める。

2

D6 · Dynamic Friction

4,800円の商品が摩擦の上限に引っかかる

ある商品 — 特定のサプリメント — が在庫切れで、最安の代替品が4,800円と花の1商品あたりのリスク閾値を超える。Dynamic Frictionはこの商品だけ自動実行をブロックする。

3

E5 · Trust Breach Recovery

花が代替品を却下する

アプリが低摩擦の通知でブロックされた商品を提示する。花は代替品を却下 — 元のブランドしか嫌だった。E5がBrainにネガティブシグナルを記録し、この商品カテゴリのAutonomy Dialを1段階下げる。

4

A2 · Cognitive Scaling

回復通知が適切なタイミングで届く

システムはCognitive Loadが下がるまで待つ — 子供の送り届けが終わり、カレンダーが空いたタイミングで。そして2択カードを提示する：元のブランドを待つか、今週はスキップするか。12択ではなく、2択だ。

結果

Silent Resolution（静かな解決）

注文は完了する。1つの商品だけが保留になる。家族の朝は邪魔されない。信頼は正確に記録される — このカテゴリにはより多くの確認が必要だとシステムは把握している。この結果を生んだのは、1つのパターンではない。4つのパターンが順番に重なった結果だ。

レストランで例えると

スムーズに動くレストランは、1食事に1技法しか使わない、なんてことはしない。ウェイターは気取らず挨拶し（D4）、高価なワインを注ぐ前に一息つき（D6）、キッチンのミスには明確に謝罪し（E5）、自然な間を見てデザートメニューを案内する（A2）。ゲストはシームレスな夜を体験する。その背後には：リアルタイムで組み合わされた4つの別々のプロ技法がある。

なぜ重要か

リストではなく、ライブラリ

リストは集合だ。ライブラリは共有の契約だ。すべてのチームがパターンに同じ名前をつけて一貫して記述すると、デザインの判断は検証可能・移転可能・組み合わせ可能になる。

01

再利用性

一度定義されたパターンは、食料品・旅行・医療・エンタープライズ — 同じToken条件が発生するあらゆるサーフェスで機能する。チームが同じインタラクションをゼロから作り直すことがなくなる。

02

一貫性

D1 Approval Gateが6つのプロダクト領域で同じ見た目・同じ動作をすれば、ユーザーは6つではなく1つのメンタルモデルを作れる。一貫性とはビジュアルスタイルではなく、行動の契約だ。

03

検証可能性

トリガー条件に名前のついたパターンはテストできる。「Feasibility × Riskが閾値を超えたときD6 Dynamic Frictionが発火したか？」という問いにはYes/Noで答えられる。曖昧なヒューリスティックは監査できない。

04

成長するカタログ

現在23パターン。新しいプロジェクトコンテキスト — P5・P6・エンタープライズ縦断 — が設計されるたびに、新パターンが抽出・命名・追加される。ライブラリは既存パターンを壊さずに成長する。

Q&A

よくある質問

Q プロダクトチームがこのライブラリを使わずに独自のパターンを作ってもよいか？

作れる — ただし、共有された名前とトリガー条件の定義がなければ、そのパターンは再利用できず、仕様書での参照もQAによるテストもできない。ライブラリの価値はカタログではなく契約にある。チームは拡張できる。ただし3つの問いフィルターに従う必要がある。

Q DirectionとPatternの違いは何か？

Direction（Delegation・Escalation・Adaptation）は大まかなカテゴリで、人間とAIの関係性を記述する。Patternはそのカテゴリ内にある、具体的で命名され、トリガーが定義されたインタラクションだ。Dパターンはすべて信頼の移転を含む。D4 Omakase Modeは、信頼が最大で開示が完全なときにその移転が取る特定の形だ。

Q なぜDirectionは3つだけなのか？4つや5つではいけないのか？

概念レベルで、委任システムにおけるAIの行動が取れる方向は3つしかない：権限を渡す（Delegation）、権限を返す（Escalation）、権限を変えずに表現を変える（Adaptation）。4つ目の方向は、これらのどれかと重複するか、別のシステムを記述することになる。Enterpriseパターンは4つ目のDirectionではなく、同じ3方向にハイステークスな制約を重ねたものだ。

Q すべてのTokenに専用のパターンが必要か？

必要ない。Tokenは入力で、Patternは行動の出力だ。複数のパターンが同じTokenを読める — D4とD6はどちらもAutonomy Dialを読む。また、いくつかのパターンは複数のTokenを同時に読む（D3はCognitive Load・Priority Weight・Feasibilityをまとめて読む）。関係は多対多だ。

Q 23のパターンは網羅的か？

網羅的ではなく、そうするつもりもない。これはProject 1〜5時点のカタログだ。既存パターンの組み合わせで記述できないデザインシナリオが出てきたとき、新しいパターンが抽出される。ルール：2つのチームが同じ無名パターンを独立して発明したとき、そのパターンに名前が付きライブラリに追加される。
