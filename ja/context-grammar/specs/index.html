Specs が必要な理由

メニューとレシピカード

レストランが新しい支店を開くとき、料理長は標準化されたレシピカードを書く。「鶏のスロークック」ではない。カードにはこう書かれている：鶏もも肉 180g・油の温度 78°C ± 2・調理時間 90分・塩分比 1.2%。

メニューの説明は客が料理を想像するためにある。レシピカードはどのキッチンでも正確に再現するためにある。同じ料理、異なる読者に向けた2つの言語だ。

Context Grammar も同じように機能する。ポートフォリオの章に書かれたナラティブは、デザイナーがシーンを理解するためにある。Spec は iPhone・冷蔵庫・カーダッシュボードが、誰かに3回説明し直してもらわずとも、そのシーンに対して正しく動くためにある。

レストランで言うと

メニューの説明は「じっくり煮込んだ鶏肉、柔らかくて黄金色」と書いてある。客はそれを読んで注文したくなる。

レシピカードには chicken_thigh: 180g, oil_temp: 78°C, cook_time: 90min と書かれている。料理人はそれを読んで、どのキッチンでも毎回正確に再現できる。

Specs はレシピカードだ。ナラティブはメニューだ。同じ料理 — 異なる読者向けの異なる言語。

すべての Token の2つの顔

人間側と機械側

同じ事実を2通りに書く。理解のための言語と、実行のための言語。

📖

Narrative

人間側

デザイナー・レビュアー・ステークホルダー向けに書く。文章がコンテキスト・感情・ストーリーを伝える。

  • 「7:02 AM — 舞は出勤準備をしながら息子のお弁当を作っている」
  • 感情と背景を含む
  • レビューや議論で使う
  • ポートフォリオの章はこちら
vs
⚙️

Spec

機械側

AI とデバイス向けに書く。JSON が値・範囲・信頼度・ソースを運ぶ — 曖昧さはゼロ。

  • cognitive_load: 0.82
  • 値・範囲・信頼度・ソース
  • 実装で使う
  • YAML / JSON ファイル

ナラティブは会話の言語だ。Spec は実行の言語だ。同じ事実を、2種類の読者に向けて書いたもの。ポートフォリオの章に「舞は7時AM に追い詰められている」と書かれているとき、その背後には必ず対応する Spec がある。

ステップごとに

火曜の朝が Spec になる

ポートフォリオのナラティブに書かれた1シーンが、機械可読な JSON ファイルになるまでの流れを示す。

「7:02 AM。舞は出勤準備をしながら息子のお弁当を作っている。子どもたちがリビングで叫んでいる。認知負荷は高い。」

— P1 Living Home · A Tuesday Morning

1 ナラティブを書く（人間向け） Narrative
これがポートフォリオに掲載される文章だ。読者はデザイナー・レビュアー・採用担当者。コンテキスト・感情・ストーリーを伝え、「舞は今プレッシャーを受けている」と人間はすぐ理解できる。ただしこの文章だけでは、iPhone がどう振る舞うべきかは伝わらない。
2 ナラティブの中に Token を見つける Tokenize
ナラティブには Context Token が埋め込まれている。デザイナーはそれを取り出す：
  • Cognitive Load — 「お弁当作り＋着替え＋叫ぶ子ども」→ 高い
  • Physical State — 「料理中、両手がふさがっている」
  • Social Exposure — 「自宅、家族のみ」→ プライベート
  • Form Factor — 「キッチンの iPhone」
このナラティブには4つの Token が暗黙的に含まれている。次のステップでそれを明示化する。
3 Spec を書く（機械向け） Spec / JSON
同じシーンを機械可読な JSON として書き直す。意味は同じ — フォーマットが違う。
// yamashiro-mai-0702.json 
{
  "context_id": "mai-tuesday-morning",
  "timestamp": "2026-04-30T07:02:00+09:00",
  "spec_version": "v1.2",

  "tokens": {
    "cognitive_load": {
      "value": 0.82,        // 0.0–1.0 scale
      "confidence": 0.74,
      "source": "calendar+activity+time-of-day"
    },
    "physical_state": {
      "value": "hands_busy",
      "confidence": 0.91,
      "source": "kitchen-presence + cooking-activity"
    },
    "social_exposure": {
      "value": "family_private",
      "confidence": 0.99,
      "source": "location=home + bluetooth=family-only"
    },
    "form_factor": {
      "value": "iphone-kitchen",
      "confidence": 1.00
    }
  },

  "projection_rules": {
    "voice_priority": true,
    "text_density": "low",
    "interaction_steps": "max_1"
  }
}
4 AI とデバイスが Spec を読む Render
iPhone の音声エージェントはこの Spec を読み、判断する：cognitive_load = 0.82, hands_busy = true → テキスト UI をスキップし、1ステップの音声で完了。

同じ瞬間に舞が車の中にいれば、CarPlay は同じ Spec を異なる方法で解釈する。しかしSpec は変わらない。各デバイスが自分の能力に合わせて翻訳する。
5 ナラティブと Spec の一致を確認する Result
ナラティブ：「舞は追い詰められ、両手がふさがっている。」
Spec：cognitive_load=0.82, physical_state=hands_busy

同じ事実、2つのフォーマット。どちらも嘘をついていない。だからポートフォリオのストーリーとデバイスの振る舞いは常に一致する。
→ Narrative ≡ Spec（同じ意味、異なるフォーマット）

一度コンパイルして、どこでもレンダリング

1つの Spec が6つのデバイスに届く

デザイナーが書くのは cognitive_load: 0.82 だけだ。各デバイスがその値を自分のサーフェス挙動に翻訳する。デバイスごとの書き直しは不要。

各デバイスが同じ Spec をどう読むか（cognitive_load=0.82, hands_busy=true）

📱

iPhone（キッチン）

音声、1ステップ。テキスト UI は非表示。

❄️

Samsung Family Hub

大きなアイコン＋1タップ。テキスト最小化。

🚗

CarPlay

音声のみ。ビジュアル UI は無効化。

🏠

Nest Hub

音声＋大きなビジュアル確認。

⌚

Apple Watch

触覚＋音声。画面の利用は前提としない。

💻

MacBook（書斎）

フル UI — このコンテキストでは関係しない。

Spec の作者は iPhone・CarPlay・冷蔵庫のことを考えていなかった。書いたのは cognitive_load=0.82 だけだ。各デバイスが自分でそれを翻訳した。

新しいデバイスが登場しても — XR グラス・カー HUD — Spec は変わらない。新しいデバイスが翻訳ルールを追加するだけだ。これが「実装非依存」の実際の意味だ。

普遍的な契約

同じ Specs がすべての Brain から流れ出る

Spec は Token ごとに定義される — Brain ごとではない。Spec が Person Brain・Domain Brain・Project Brain のどこから来ても、構造は同一だ。Token のフィールドは、どの Brain が生成したかによって変わらない。

つまり Team Brain と Home Brain はどちらも同じ cognitive_load フィールドを、同じ5つの必須キーとともに出力する。ある Brain タイプを読むデバイスが、別の Brain タイプのために異なるパーサーを用意する必要はない。

Person Brain

cognitive_load, social_exposure を出力する。フィールドは同じ、ソースが人物固有。

Domain Brain

金融・健康・旅行 — それぞれの Brain が同じ Token フィールドを出力する。ドメインが変わるのは値であって、スキーマではない。

Project Brain（P4）

エンタープライズ Brain インスタンスも同じ Spec 契約を生成する。1つのパーサーがすべての Brain タイプを読める。

Brain はメモリーの実体だ。Spec は出力フォーマットだ。この2つは別の関心事。Home Brain からエンタープライズ Brain に切り替えても変わるのはメモリーモデルであって、Spec スキーマではない。

前方互換性

v1 → v2 → v3 — 既存サーフェスを壊さずに進化する

Context Grammar は進化し続ける。新しい Token・新しいダイアル・新しい AX Pattern が追加される。2026年に作られた冷蔵庫の UI は、2030年の Spec でも動くべきだ。そのためにバージョン管理が必要になる。

Spec バージョン履歴

v1.0
最初の 7 Token。Cognitive Load・Physical State・Social Exposure・Priority Weight・Form Factor・Feasibility・Synchro Rate（Autonomy の前身）。リリース：2025-12。
v1.2
Synchro Rate → Autonomy Dial にリネーム。動作は変わらず。旧フィールドはエイリアスとして保持 — v1.0 を読むサーフェスは引き続き動作する。
v2.0
Disclosure Dial 追加 → 8 Token。Disclosure を読まない既存サーフェスはそのまま動作する — デフォルト値が注入される。新しいサーフェスだけが Disclosure フィールドに反応する。
v2.3
Substitution Modes を Spec に追加。Exact・Flexible・Exploring・Surprise が選択可能になる。P1 v1 の冷蔵庫 UI は Exact のまま動き続ける。
v3.0（計画中）
Multi-Person Orchestration がファーストクラスの概念になる。1つの Spec が家族全員の状態を表現する。v2 を読むサーフェスは1人分のスライスを抽出して引き続き動作する。

前方互換性の3つのルール

01

新フィールドの追加 — 常に許可

既存サーフェスは未知のフィールドを無視する。壊れない。

02

フィールドの削除 — 絶対に禁止

既存サーフェスが壊れる。代わりにエイリアスとして残す。

03

フィールドの意味変更 — 絶対に禁止

新しい概念には新しい名前をつける。再定義ではなくリネーム。

Spec の構造

すべての Spec が持つべき5つのフィールド

この5つのフィールドを持つ Spec は、機械可読・レビュー可能・進化可能だ。これが最小限の契約。

フィールド 何を宣言するか 例
token_id このエントリーがどの Token を説明するか cognitive_load
value Token の現在値（数値・enum・範囲） 0.82（0.0–1.0 スケール）
confidence 推定の確実性 0.74（信頼度74%）
source 値の取得元 calendar+activity+time-of-day
projection_rules UI レイヤーに渡すヒント voice_priority: true

Cognitive Load は測定値ではなく推定値なので、confidence が重要だ。信頼度70%の場合、システムはその値を70%の信頼性として扱う — 無言で実行するのではなく確認を求める。この confidence 値が Autonomy Dial の機械的な基盤だ：高い信頼度 → Auto、低い信頼度 → Suggest。

よくある質問

Q&A

Q1. Spec を書くのはデザイナー？それともエンジニア？

最初に書くのはデザイナーだ。Spec は実装の詳細ではない — 意味の宣言だ。「このシーンの cognitive load は 0.82 だ」はデザイン上の決定。エンジニアはその後、各デバイスがその値をどう振る舞いに翻訳するかを実装する。Spec はデザイン成果物だ。

Q2. JSON でないといけない？YAML や TOML でも使える？

どのフォーマットでも構わない。JSON は機械向けに読みやすく、YAML は人間向けに読みやすい — 違いはそれだけだ。Context Grammar Spec は5つのフィールドさえあれば、どのフォーマットでも有効だ。既存の design-rules.yaml は YAML で書かれている。構造が重要であって、フォーマットは関係ない。

Q3. 信頼度が低いとき、AI はどう動く？

確認するか、待つ。cognitive_load.confidence = 0.45 の場合、システムは最小限の確認を求める：「今、大丈夫ですか？」（Autonomy Dial が Suggest 方向にシフトする）。confidence = 0.95 なら確認なしで実行する（Autonomy Dial が Auto）。confidence フィールドが AI のためらいの度合いを決める。

Q4. ナラティブと Spec が食い違ったら？

どちらかが間違っている — 両方を直す。ナラティブと Spec は同じ事実の2つの表現だ。もし乖離があれば、デザインが矛盾している。レビューで一緒に確認すること。2つの間の不一致は編集上の選択ではなく、デザインのバグだ。

Q5. OpenAPI や JSON Schema とどう違う？

レイヤーも目的も違う。OpenAPI は API リクエストとレスポンスの形状を定義する。JSON Schema はデータ型が正しいかを検証する。Context Grammar Spec は UX シーンの意味を宣言する。Spec を JSON Schema で記述することはできる — ただしその目的は型の検証ではなく、「このシーンはユーザーにとって何を意味するか」に答えることだ。
