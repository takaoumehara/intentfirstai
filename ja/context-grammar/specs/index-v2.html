Concept · Specs

Token は持ち運べる契約書

すべての Context Token には二つの顔がある。人間が読む物語と、機械が実行する Spec。一つの JSON ファイルが、どのデバイスにも同じ意味を届ける。

なぜ Spec が必要か

メニューと厨房の標準レシピカード

チェーンレストランが新しい店舗を開くとき、料理長は標準レシピカードを書く。「ゆっくり低温で焼いた鶏肉」ではない。カードにはこう書いてある。鶏もも肉 180g · 油温 78°C ± 2 · 調理時間 90分 · 塩分比 1.2%。

メニューの説明文はお客様が料理を想像するためのもの。レシピカードはどの厨房でも同じ味を再現するためのもの。同じ料理を、読み手の違う二つの言葉で書く。

Context Grammar も同じ構造を持つ。ポートフォリオの本文にある物語は、デザイナーがシーンを理解するためのもの。Spec は iPhone、冷蔵庫、カーダッシュボードが、そのシーンを正確に実行するためのもの。三回説明し直す必要はない。

レストランに例えると

メニューの説明文は「低温でゆっくり仕上げた鶏肉、黄金色でやわらか」と書く。お客様はそれを読んで料理を想像する。

厨房の標準レシピカードは 鶏もも肉: 180g, 油温: 78°C, 調理時間: 90min と書く。シェフはそれを読んで、どの店舗でも同じ味を再現する。

Spec はレシピカード。物語はメニュー説明。同じ料理の、読み手の違う二つの言葉。

Token の二つの顔

人間側と機械側

同じ事実を二回書く。一方は理解のため、もう一方は実行のため。

📖

Narrative

物語の顔

デザイナー、レビュアー、採用担当者が読むために書く。文章が文脈・感情・背景を運ぶ。

  • 「7:02 AM — Mai は弁当を作りながら出勤の支度をしている」
  • 感情と背景が含まれる
  • レビューや議論で使う
  • ポートフォリオの本文がこれ
vs
⚙️

Spec

機械の顔

AI とデバイスが読むために書く。JSON が値・範囲・confidence・source を構造化して運ぶ — 曖昧さゼロ。

  • cognitive_load: 0.82
  • 値・範囲・confidence・source
  • 実装で使う
  • YAML / JSON ファイル

物語は会話のための言語。Spec は実行のための言語。同じ事実を、読み手の違う二人のために二回書く。ポートフォリオの本文に「Mai は朝7時に追い詰められている」と書いてあれば、その裏には必ず対応する Spec がある。

ステップごとに追う

ある火曜の朝が Spec になる瞬間

ポートフォリオの物語が、機械可読な JSON ファイルになるまでを追う。

「7:02 AM。Mai は息子の弁当を作りながら、自分の出勤準備もしている。子供がリビングで叫んでいる。認知負荷は高い。」

— P1 Living Home · ある火曜の朝

1 物語として書く（人間用） Narrative
ポートフォリオの本文に出てくる文章。読み手はデザイナー、レビュアー、採用担当者。文脈・感情・背景が含まれていて、人間は一読で「Mai は今、追い詰められている」と分かる。しかしこの文章だけでは、iPhone はどう振る舞えばいいか分からない。
2 物語の中に埋まっている Token を見つける Tokenize
この文章には Context Token が暗黙のうちに含まれている。デザイナーが拾い出すと:
  • Cognitive Load — 「弁当 + 出勤準備 + 子供の叫び声」→ 高い
  • Physical State — 「料理中、両手がふさがっている」
  • Social Exposure — 「家、家族のみ」→ プライベート
  • Form Factor — 「キッチンの iPhone」
物語は4つの Token を含んでいる。次のステップでそれを明示する。
3 Spec として書く（機械用） Spec / JSON
同じ物語を、機械が読める JSON に書き直す。意味は同じ — フォーマットだけ違う。
// yamashiro-mai-0702.json 
{
  "context_id": "mai-tuesday-morning",
  "timestamp": "2026-04-30T07:02:00+09:00",
  "spec_version": "v1.2",

  "tokens": {
    "cognitive_load": {
      "value": 0.82,        // 0.0–1.0 スケール
      "confidence": 0.74,
      "source": "calendar+activity+time-of-day"
    },
    "physical_state": {
      "value": "hands_busy",
      "confidence": 0.91,
      "source": "kitchen-presence + cooking-activity"
    },
    "social_exposure": {
      "value": "family_private",
      "confidence": 0.99,
      "source": "location=home + bluetooth=family-only"
    },
    "form_factor": {
      "value": "iphone-kitchen",
      "confidence": 1.00
    }
  },

  "projection_rules": {
    "voice_priority": true,
    "text_density": "low",
    "interaction_steps": "max_1"
  }
}
4 AI とデバイスがこの Spec を読む Render
iPhone の Voice Agent はこの Spec を読んで判断する。cognitive_load = 0.82, hands_busy = true → テキスト UI を出さない、音声で1ステップ完結させる。

Mai が同じ瞬間に CarPlay にいたなら、CarPlay は同じ Spec を別のやり方で読む。しかしSpec は変わらない。各デバイスが自分の能力に合わせて翻訳するだけ。
5 物語と Spec が一致していることを確認する Result
物語：「Mai は忙しい朝、両手がふさがっている。」
Spec：cognitive_load=0.82, physical_state=hands_busy

同じ事実の、二つのフォーマット。どちらも嘘をついていない。だからポートフォリオの物語と、デバイスの振る舞いは必ず一致する。
→ Narrative ≡ Spec（同じ意味、別フォーマット）

compile once, render anywhere

一つの Spec が6つのデバイスに届く

デザイナーは cognitive_load: 0.82 と書くだけ。各デバイスがその一つの値を、自分なりのサーフェス動作に翻訳する。デバイスごとに書き直しは要らない。

同じ Spec（cognitive_load=0.82, hands_busy=true）を読んだ各デバイスの振る舞い

📱

iPhone（キッチン）

音声で1ステップ完結。テキスト UI は隠す。

❄️

Samsung Family Hub

大きいアイコン + 1タップ。文字は最小限。

🚗

CarPlay

完全音声。視覚 UI は無効化。

🏠

Nest Hub

音声 + 大きなビジュアル確認。

⌚

Apple Watch

触覚 + 音声。画面を見ない前提。

💻

MacBook（書斎）

このコンテキストでは出ない想定。

Spec を書いた人は iPhone のことも、CarPlay のことも、冷蔵庫のことも考えていない。cognitive_load=0.82 としか書いていない。各デバイスが自分なりに翻訳する。

新しいデバイス — XR グラス、車内 HUD — が増えても、Spec は書き直さない。デバイス側が新しい翻訳ルールを追加するだけ。これが「implementation-agnostic」の実際の意味。

普遍的な契約

同じ Spec がどの Brain からも流れ出る

Spec は Token ごとに定義される — Brain の種類には依存しない。Person Brain からだろうと Domain Brain からだろうと、Project Brain からだろうと、構造は同一。Token フィールドは、どの Brain が生成したかによって変わらない。

つまり、Team Brain も Home Brain も同じ cognitive_load フィールドを、同じ5つの必須キーと共に出力する。一方の Brain を読むデバイスは、もう一方のために別のパーサーを必要としない。

Person Brain

cognitive_load, social_exposure を出力。フィールドは同じ、source が個人ごとに変わる。

Domain Brain

Finance・Health・Travel — どの Brain も同じ Token フィールドを出力する。ドメインが変えるのはスキーマではなく値。

Project Brain（P4）

企業の Brain インスタンスも同じ Spec 契約を生成する。一つのパーサーがすべての Brain タイプを読める。

Brain は記憶のエンティティ。Spec は出力フォーマット。これは別の関心事。Home Brain から Enterprise Brain に切り替えても、メモリモデルは変わるが Spec スキーマは変わらない。

前方互換性（forward compatibility）

v1 → v2 → v3 — 古いサーフェスを壊さずに進化させる

Context Grammar は進化し続ける。新しい Token、新しい Dial、新しい AX Pattern が追加される。2026年に作った冷蔵庫の UI が、2030年の Spec で動かなくなるのは困る。だから Spec はバージョンを持つ。

Spec バージョン履歴

v1.0
初期 7 Token。 Cognitive Load · Physical State · Social Exposure · Priority Weight · Form Factor · Feasibility · Synchro Rate（Autonomy の前身）。2025-12 リリース。
v1.2
Synchro Rate → Autonomy Dial に改名。仕組みは同じ。古いフィールド名は alias として残すので、v1.0 を読む古いサーフェスも動き続ける。
v2.0
Disclosure Dial 追加 → 8 Token へ。Disclosure を読まない古いサーフェスは動き続ける — デフォルト値が注入される。新しいサーフェスだけが Disclosure フィールドを読んで挙動を変える。
v2.3
Substitution Modes を Spec に追加。Exact · Flexible · Exploring · Surprise が選択可能に。P1 v1 の冷蔵庫 UI は Exact のまま動き続ける。
v3.0（予定）
Multi-Person Orchestration を一級概念化。一つの Spec で家族全員の状態を表現する。v2 を読むサーフェスは一人分のスライスだけを抽出して動き続ける。

前方互換性の3つのルール

01

新フィールドの追加 — 常に OK

古いサーフェスは知らないフィールドを無視するだけ。壊れない。

02

フィールドの削除 — NG

古いサーフェスが壊れる。代わりに alias として残す。

03

フィールドの意味を変える — NG

新しい概念には新しい名前をつける。再定義ではなく改名。

Spec の解剖

どの Spec にも必ず入っている5つのフィールド

この5つが揃っていれば、機械が読めて、レビューできて、進化させられる。これが最低限の契約。

フィールド 何を宣言するか 例
token_id どの Token を記述しているか cognitive_load
value Token の現在値（数値・列挙・範囲） 0.82（0.0–1.0 スケール）
confidence 推定の確からしさ 0.74（74% の自信）
source 値がどこから来たか calendar+activity+time-of-day
projection_rules UI 層に渡すヒント voice_priority: true

confidence が重要なのは、Cognitive Load が測定ではなく推定だから。70% の自信しかなければ、システムはその値を70% として扱う — 黙って動くのではなく確認を一つ入れる（Autonomy Dial が Suggest 寄りに振れる）。95% の自信があれば確認なしで動く（Auto に振れる）。confidence フィールドが AI の遠慮量を決めている。

よくある質問

Q&A

Q1. Spec を書くのはデザイナー？エンジニア？

デザイナーが先に書く。 Spec は実装の詳細ではなく、意味の宣言。「このシーンの認知負荷は 0.82 です」と決めるのは、シーンを設計したデザイナーの仕事。エンジニアはその Spec を各デバイスでどう翻訳するかを実装する。Spec はデザインの成果物。

Q2. JSON でなくてもいい？ YAML や TOML でも使えるか？

フォーマットはどれでも OK。 JSON は機械が読みやすく、YAML は人間が読みやすい — それだけの違い。Context Grammar の Spec は5つのフィールドが揃っていればどの形式でも有効。既存の design-rules.yaml は YAML で書かれている。重要なのは構造で、形式ではない。

Q3. confidence が低いとき AI はどう動くか？

確認するか、待つ。 cognitive_load.confidence = 0.45 なら、AI は最小限の確認を入れる。「今、大丈夫ですか？」（Autonomy Dial が Suggest に振れる）。confidence = 0.95 なら確認なしで動く（Auto に振れる）。confidence フィールドが AI の遠慮量を設定している。

Q4. 物語と Spec が食い違ったらどちらが正しいか？

食い違いがある時点で、どちらかが間違っている。 物語と Spec は同じ事実の二つの書き方であるべき。食い違ったら、片方が嘘をついている。両方を見直して合わせる。レビューでは物語と Spec を必ずセットで確認すること。

Q5. OpenAPI や JSON Schema と何が違うか？

レイヤーが違い、目的が違う。 OpenAPI は API のリクエスト・レスポンスの形を定義する。JSON Schema はデータ型が正しいかを検証する。Context Grammar Spec は UX シーンの意味を宣言する。Spec を JSON Schema で記述することはできる — しかし目的は型の検証ではなく「このシーンはユーザーにとって何を意味するか」への回答。

Spec はデザインと実行の間の握手。

Token が何を読むかを定義する。Brain が記憶を提供する。Spec が意味をすべてのデバイス、すべてのバージョンに運ぶ。
