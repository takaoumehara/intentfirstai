Context Grammar — Floor 2

Context Tokens

人の「いま」を測るための、8つの軸。AIが言葉を発する前に、まず場の空気を読むための語彙。

Context Tokensの役割

AIが場の空気を読む

AIが振る舞いを変えるには、まず状況を読み取らなければならない。Context Tokensは、優れたウェイターが注文を取る前にテーブルを一瞥して読み取るような直感を、AIに与えるための8つの測定可能なシグナルだ。

レストランで例えると

優れたウェイターは、ひとつも質問せずに同時に8つのシグナルを読む。テーブルは料理で埋まっている — Cognitive Loadが高い。キャンドルを灯した二人席 — Social Exposureが高い（同僚ではなく、デート）。客は腕時計を何度も見る — Priority Weightは「料理の質」ではなく「時間」。カウンターは狭い — Form Factorがフル展開を許さない。

Context Grammarは、この直感をAIに8つの軸として与える。各軸は、そのままひとつのトークンに対応する: ① Physical State、② Cognitive Load、③ Social Exposure、④ Priority Weight、⑤ Form Factor、⑥ Feasibility、⑦ Autonomy Dial、⑧ Disclosure Dial。

2つのグループ

8つのトークン — 6つの状況 + 2つのダイヤル

8つを丸暗記するのは大変だ。2つのグループに分けると、一気に腹落ちする: 周囲の世界を読み取る6つのセンサーと、AIが「知っていいこと・やっていいこと」を司る2つのダイヤル。

Group A · 6 Situation Tokens
状況センサー

いま、何が起きているかを読む — 測定可能な6つの軸。ユーザーが設定する項目ではなく、AIが読み取るインプット。

  • ① Physical State — 身体モード（歩行 / 運転 / 静止）
  • ② Cognitive Load — 認知の余裕（ピーク / 低 / リラックス）
  • ③ Social Exposure — 誰が見ているか（一人 / 家族 / 同僚）
  • ④ Priority Weight — 要求が競合したとき何が勝つか（時間 vs お金 vs 安全）
  • ⑤ Form Factor — どのサーフェスが使えるか（Watch / スマホ / TV / 車）
  • ⑥ Feasibility — いま実際に何が可能か（在庫 / 時間 / 距離）
+
Group B · 2 Relationship Dials
関係性ダイヤル

人とAIのあいだの距離を決める。サービス側のデフォルト × AIの自動調整 × ユーザーの能動的な変更 — この3つの力が両方のダイヤルを同時に動かす。

  • ⑦ Autonomy Dial — AIはどこまで自分で動いていいか（Suggest / Confirm / Notify / Auto）
  • ⑧ Disclosure Dial — AIはあなたについてどこまで知っていいか（領域ごと、相手ごと）
重要な区別

Situation Tokensは「いまのあなた」を表す — 瞬間ごとに変わる。Relationship Dialsは「あなたとAIの関係」を定義する — 時間をかけて少しずつ育つ。瞬間の状況 + 長期の関係 = AIの振る舞い。

8つのトークン — 全体俯瞰
Overview · 山城家

8つすべて — 山城家の朝

抽象的な定義はすぐ忘れる。ここでは各トークンを、母・舞、息子・颯太（11歳）、娘・はな（6歳）の火曜日の朝に紐づけて見ていく。星の数は2026年3月時点の技術的現実を反映している。

① Physical State ★★★★☆
いま身体が何をしているか — 歩いている、運転している、座っている、運動している。
山城家 · 07:45 舞は駅に向かって全力疾走中。Watchは速度6km/h、心拍110を読み取っている。AIは通知をすべて保留する — 走りながらでは、どうせ読めない。
② Cognitive Load ★★☆☆☆
頭にどれだけ余裕が残っているか。直接は測れない — 時刻 × カレンダー密度 × 直近の行動から推定する。
山城家 · 07:02 舞は2人分のお弁当を作りながら、はなの保育園バッグを詰めている。AIは「過負荷」と推定。冷蔵庫の画面は1行だけ表示する: 「昨日の残り + 卵焼き」。タップは不要。
③ Social Exposure ★★★★☆
いま、ほかに誰が見ている・聞いているか — 一人 / 家族 / 同僚 / 公共。8つの中で最も既に実装されているトークン。
山城家 · 会議中 舞が会議室のTVに画面ミラーリング。AIは家計関連の通知を即座に外す。「いま、他の人にもこの画面が見えている」。
④ Priority Weight ★★★☆☆
要求が競合している — いま、何が勝つか? 時間 vs お金 vs 健康。単なる重要度ランキングではなく、衝突を解く判断。
山城家 · 夕方 颯太の塾が遅れる。舞のBrainは「平日は、時間 > 食事の質」と学習している。AIは夕食を冷凍ストックで提案 + 19:50に塾までお迎え。
⑤ Form Factor ★★★★☆
いまAIが届くサーフェス — Watch / スマホ / タブレット / TV / 冷蔵庫 / 車 / 音声 / アンビエント。
山城家 · 同じ情報、違うサーフェス 舞のWatch: 「19:00 お迎え」。冷蔵庫: 家族全員のタイムラインが展開。CarPlay: 音声で「19時にお迎え」と読み上げ。
⑥ Feasibility ★★★☆☆
それは、いま本当にできるのか? 在庫、時間、距離、天気、予算 — 欠けている制約がひとつでもあれば「不可」。
山城家 · 夕食 AIはカレーを提案しかけた。冷蔵庫に玉ねぎがない + 外は雨 → 提案を「いまある食材でパスタ」に切り替える。
⑦ Autonomy Dial ★★★☆☆
AIはどこまで自分で動いていいか? Suggest → Confirm → Notify → Auto。 サービス側のデフォルト × AIの自動調整 × ユーザーの選択、という3つの力で形作られる。
山城家 · リスクの段階に応じて 颯太の靴 $48（消耗品・リスク低）= Auto。家族のホテル $400 = Confirm。舞の手術同意 = Suggest（自動化は永遠に不可 — Identity Layerでの宣言）。
⑧ Disclosure Dial ★☆☆☆☆
AIはあなたについてどこまで知っているか — 領域ごと、相手ごと。Autonomyの前提条件（Hidden × Auto は論理的に成立しない）。
山城家 · プライバシー 舞は「家計」をAIにFullで開示しているが、「健康診断の結果」はHiddenのまま。AIは食費の最適化はできるが、コレステロール値に基づく食事提案には一切踏み込まない。
星の読み方

★★★★☆ = 今日にも出荷可能 — センサーAPIやOSのフックがすでにある。★★☆☆☆ = 推定のみ — 直接の測定はできない。★☆☆☆☆ = コンセプト段階 — 領域横断のAPIがまだ存在しない。「Cognitive Loadは計測できる」と書けばそれは嘘になる。Context Grammarは、できることとできないことを正直に区別する。

技術的な内側

8つのトークン — 仕組みのレベルまで

各トークンについて、仕組み（どう計算されるか）、シグナル源（Brainのどの層から来るか）、山城家の具体例、投影ルール、そして禁じ手まで踏み込んで見ていく。

① Physical State 「急いでいるのか、落ち着いているのか」 ★★★★☆ ほぼ実装済み
定義
いま身体が何をしているか — 歩いている、走っている、運転している、座っている、寝ている、運動している。設計判断に最初に効いてくる軸: 身体状態が読めなければ、AIは中身（content）に手をつける前に形態（form）を変えることすらできない。
仕組み
Activity Recognition API（iOS / Android）が歩行 / 走行 / 運転 / 静止を分類する。Galaxy WatchやApple Watchが心拍、ストレス指数、睡眠負債を加える。複数のシグナルがひとつの「state」値に圧縮され、設計判断 — 表示するか抑制するか、音声か画面か — を駆動する。
シグナル源
  • Now Layer加速度計、心拍、ジャイロ、CarPlay / Android Autoの接続状態
  • Learning Layerパターン: 「舞は平日7:30–7:50は必ず駅まで全力疾走」
  • Identity Layer身体的な制約 — 持病、術後、妊娠中
具体例
07:45 — 舞は駅に向かって全力疾走中。Watchは速度6km/h、心拍110。AIは通知をすべて保留。19:00の塾リマインダーは「電車の座席に座ったあと」に再スケジュール。
土曜日の朝、ソファ、心拍65 — AIは家族カレンダーの提案をスマホに上げてくる。
投影ルール
状態が「読めない」ときは、保守的に倒す。 走行・運転中 → 通知を音声に切り替えるか、丸ごと抑制する。まず形態を変える、それから中身を考える。
禁じ手
禁じ手: 走っている人に長文リッチ通知を送る。運転中に画面操作を要求する確認ダイアログを出す。「鳴らした = 届いた」前提で設計する。
② Cognitive Load 「頭にどれだけ余裕が残っているか」 ★★☆☆☆ 推定のみ
定義
認知の残り帯域 — 脳がどれだけ忙しいか。直接の測定はできない。 EEGも脳スキャナーも使わない。観測可能な代理指標から推定するしかない。8つの中で、推定の限界をもっとも正直に書く必要があるトークン。
仕組み
時刻 × カレンダー密度 × 直近10分のアプリ切り替え回数 × 行動履歴。複数の代理指標を重みづけして平均し、3〜5段階のdensity（minimal / low / medium / high / overload）に集約する。「これは推定値である」というメタデータを常に持ち回る。
シグナル源
  • Now Layer15分単位のカレンダー埋まり度、直近のタスク完了、画面切り替え頻度
  • Learning Layerパターン: 「平日朝7:00–7:30は必ず過負荷」 — および手動オーバーライド履歴（「いや、空いてる」）
具体例
平日 07:02 — 舞は2人分のお弁当を作りながら、はなの保育園バッグを詰めている。AIはdensity:overloadと推定。冷蔵庫の画面は1行だけ表示する: 「昨日の残り + 卵焼き」。タップは不要。
土曜日 10:00 — 同じ舞、density:low → 写真つきのフルレシピ提案が妥当。
投影ルール
high / overload時: 1画面、1判断。3つ以上の選択肢を出さない。探索や学習系の提案は、負荷が低いときにだけ解禁する。 AIが推定を外したとき、ユーザーが「いや、空いてる」と上書きできるUIが必要だ — それがないと、AIは「分かったふり」をしているように見える。
禁じ手
禁じ手: 「あなたはいま負荷が高い状態です」と断定するUI。推定なのに測定したかのように振る舞うこと。過負荷時の複数選択ダイアログ。フォールバックを省略すること。
誠実なデザインノート

Cognitive Loadは8つの中で最も推測の度合いが大きい。直接の測定方法は今日存在しない。このトークンに依存する設計判断には、必ず優雅なフォールバックを用意し、推定の精度を超えた確信を主張しないこと。

③ Social Exposure 「いま、ほかに誰が見ているか」 ★★★★☆ ほぼ実装済み
定義
いま、この画面・音声を誰が見ている・聞いているか — 一人 / 家族 / 同僚 / 不特定多数（カフェ、電車）。8つの中でもっとも既に実装が進んでいるトークン。
仕組み
Bluetooth / Wi-Fiの近接で周囲のデバイスを検出。Voice IDで家族の個人を識別する（Samsung Family Hubは最大6プロファイル対応）。ミラーリング状態（AirPlay / Cast / DeX）はOSから取得。可能な範囲ではオンデバイスVisionで人数も推定する。
シグナル源
  • Now Layer近接デバイス、Voice ID、ミラーリングのON/OFF、画面共有中かどうか
  • Identity Layer関係マップ — 「家族」「同僚」「友人」 — がそばにいる相手に意味を与える
具体例
舞が会議室のTVに画面ミラーリング → AIは家計関連の通知を即座に外し、塾代の相談を19:30まで遅らせる。リビングでVoice IDが颯太を検出 → 舞のスマホに表示されていた「颯太の誕生日サプライズ」計画は自動的に隠れる。
投影ルール
観客が変えるのはフィルタであって、中身そのものではない。 同僚が同席 → 家庭領域を抑制。子どもが同席 → サプライズを隠す。このトークンはDisclosure Dialの「領域ごとの開示設定」と掛け算される。
禁じ手
禁じ手: 画面共有中に金額・パスワード・健康データを表示する。家族デバイスで個人スコープの通知を全員にブロードキャストする。Voice IDで確認せずに「いつもの人」と決めつける。
④ Priority Weight 「要求が競合したとき、何が勝つか」 ★★★☆☆ 一部実装中
定義
複数の要求が衝突したとき — スピード vs コスト vs 健康 vs 家族 — いま、何が勝つか? 単純な重要度ランキングではない。衝突の瞬間に下すトレードオフの判断。
仕組み
二層構造。レイヤー1 = いまの緊急度（Now Layerから — カレンダーの直近性、通知の種別、締め切り）。レイヤー2 = 学習されたトレードオフのパターン（Learning Layerから — 「舞は平日、食事の質より時間を優先する」）。Rule Engineが両者を掛け算する。
シグナル源
  • Now Layerカレンダーの優先度、フラグつきメール、通知の重要度、締め切りまでの時間
  • Learning Layer過去の衝突解決 — 「同じ状況で、彼女は何を諦めたか」
  • Identity Layer絶対に譲れない軸 — アレルギー > 味 > 価格、子どもの安全 > 仕事の予定
具体例
颯太の塾が遅れる → 夕食を早めるか、お迎えを優先するか? Learning Layer: 「平日は、時間 > 食事の質」。AIは冷凍ストックの夕食 + 19:50に塾までお迎えを提案。
もうひとつの例: 5分後に会議開始 + 学校からアレルギー関連の電話 → Identity Layerが勝つ — 「会議に1分遅れる」。
投影ルール
AIは重みを一方的に決めない。 学習履歴に基づいて提案するだけ。ユーザーが上書きすれば、その選択はLearning Layerに書き戻される。Identity Layerの軸（安全、健康）は学習パターンを常に上回る — 例外なし。
禁じ手
禁じ手: 毎回ユーザーに「優先度を1〜5で並べてください」と聞くこと。学習パターンがIdentity Layerの軸（アレルギー、既往歴）を上書きするのを許すこと。
デザインノート

Priority Weightは二層構造を持つ: いまの緊急度（このトークン、瞬間ごとに変わる）と、学習されたトレードオフのパターン（Brainに蓄積され、時間をかけて育つ）。トークンは「いま何が押し迫っているか」を捉える。Brainは「過去、似た衝突がどう解かれたか」を覚えている。

⑤ Form Factor 「いま、どんなサーフェスに囲まれているか」 ★★★★☆ ほぼ実装済み
定義
いまAIが届くサーフェスの集合 — Watch / スマホ / タブレット / TV / 冷蔵庫 / 車、そして音声のみ / AR / アンビエント。画面の話だけではない。
仕組み
OSが現在のデバイス状態 + Continuity / DeX / CarPlay / Castの接続状況を保持している。複数サーフェスが同時にアクティブなとき、AIはコンテンツの種類に応じて最適なサーフェスを選ぶ（動的なマルチサーフェス配分）。音声 / ジェスチャー / アンビエントもサーフェスとして扱う。
シグナル源
  • Now Layer接続中のデバイス、画面サイズ、入力モダリティ、CarPlay / ARのアクティブ状態
  • Identity Layer所有デバイス、主たるサーフェス（「舞はいつもWatchをつけている」）
具体例
同じ情報 — 家族のスケジュール — がサーフェスごとに違う形で出る: Watchは「19:00 お迎え」（1行）。冷蔵庫は家族全員のフルタイムライン。CarPlayは「19時にお迎え」と音声のみ。
イヤホンの音声のみ: あらゆる確認が「はい / いいえ」の2択に圧縮される。
投影ルール
サーフェスが変われば、情報密度が変わる。 Watch = 1行。スマホ = 段落。タブレット / TV = 並列カラム。音声 = 一度にひとつの質問。同じ情報、サーフェスごとに異なる表現 — それがForm Factorの契約だ。
禁じ手
禁じ手: スマホ用UIをそのまま縮小してWatchに載せる。音声のみのサーフェスで長文をそのまま読み上げる。「レスポンシブWebで十分」と決めつけてアンビエントや音声サーフェスを無視する。
⑥ Feasibility 「いま、本当にできるのは何か」 ★★★☆☆ 一部実装中
定義
そのアクションは、いま実行可能か? 在庫、時間、距離、天気、お金、人手 — 欠けている制約がひとつでもあれば成立しない。目指すのは「無理」で終わることではなく、「では、代わりに何ができるか?」
仕組み
各ドメインのAPI（在庫 / 配送ETA / 天気 / 営業時間 / 口座残高）から個別の実行可能性を取り、複数の制約をひとつのfeasibilityスコアに統合する。ブロックされた場合は、Substitution Mode（Exact / Flexible / Exploring / Surprise）が代替案を生成する。
シグナル源
  • Now Layer在庫API、天気API、配送ETA、店舗営業時間、口座残高
  • Learning Layer「いつもの品が欠品したとき、彼女は何で代用したか?」 → Substitution Modeの学習
具体例
AIは夕食にカレーを提案しかけた — が、冷蔵庫に玉ねぎがない、外は雨 → 提案を「いまある食材でパスタ」に切り替える。
もうひとつの例: 舞が明治ブルガリアヨーグルトを注文したが欠品。Substitution Mode Flexible → AIは別のブルガリア系ヨーグルトに静かに差し替える。Mode Exact → AIは「本日は入手不可」と報告する。
投影ルール
「無理」で終わらせない。 必ず1〜3個の代替案を添える。FeasibilityとSubstitution Modeは常にセットで実装する。
禁じ手
禁じ手: 「在庫切れ」だけ返して終わる。1つの制約だけで「行ける」と判断し、他（雨 + 閉店時間 + 子どもが車内）を見落とす。Exact以外のモードで、開示なしに勝手に差し替えて信頼を壊す。

⑦ Autonomy Dial 「AIはどこまで自分で動いていいか」 ★★★☆☆ 開発ツールでは実装済み
定義
AIが、聞かずにどこまで動けるか。Suggest → Confirm → Notify → Auto。 これはユーザーが自由に切り替えるトグルではない — 3つの力が同時に働いた結果として決まる。
4段階
Stage 1
Suggest
Stage 2
Confirm
Stage 3
Notify
Stage 4
Auto

Suggest — AIは選択肢を出し、ユーザーが選ぶ。  |  Confirm — AIが決めるが、実行前にユーザーが承認する。  |  Notify — AIが実行し、事後に報告する。  |  Auto — AIが静かに実行する。

仕組み
ひとつのダイヤル値を、3つの力が決める:
① サービス側のデフォルト — Netflixのレコメンドはすでに高いAutonomyで出荷されている
② AIの自動調整 — 深夜、初回利用、失敗直後はデフォルトを下げる
③ ユーザーの能動的な変更 — 自分でスライダーを動かす
各ドメイン（家計 / 健康 / 仕事 / 子育て）はそれぞれ独立のダイヤルを持つ。
シグナル源
  • Now Layer取引額、可逆性、緊急度
  • Learning Layer過去のAI提案の成功率、ユーザーの介入履歴 → 信頼スコア
  • Identity Layer「この領域は絶対に自動化しない」という宣言（医療同意、重要契約）
具体例
颯太の靴 $48（消耗品、リスク低、前回と同じモデル）= Auto。 家族のホテル $400 = Confirm。 舞の手術同意 = Suggest — 自動化は永遠に不可、Identity Layerでの宣言。
投影ルール
常にSuggestから始める。実績（成功 / 失敗の履歴）が積まれるたびに1段階ずつ進める。失敗が起きたら1段階戻す。Identity Layerで「自動化しない」と宣言された領域はロックされる — どれだけ完璧な実績があっても、これは動かない。
禁じ手
禁じ手: 「AI自動化 ON / OFF」の単一トグルで出荷する。初回利用からAutoで始める。失敗が起きてもAutonomyを高いまま維持する。DisclosureがHiddenのままAutonomyを上げる（トークン⑧参照）。
重要なインサイト

Autonomy Dialは純粋にユーザーが制御するものではない。 3つの力で形作られる: サービス側のデフォルト、AIの自動調整、ユーザーの選択。Uber Eatsが再注文の許可をいちいち聞かないのは、サービス側のデフォルトがすでに高いAutonomyを前提にしているからだ。3つの力モデルの全体像はTrust Design →で扱う。

⑧ Disclosure Dial 「AIはあなたについてどこまで知っているか」 ★☆☆☆☆ コンセプト段階
定義
ユーザーが自分自身についてAIに開示する量 — 領域ごと × 相手ごとに独立で。これはAutonomyの論理的な前提: Hidden × Autoは「保守的な選択」ではなく、矛盾だ。
4段階
Level 1
Full
Level 2
Summary
Level 3
Existence
Level 4
Hidden

Full — すべてのデータを開示。  |  Summary — 集計値のみ、生ログは渡さない。  |  Existence — 「この領域が存在する」ことだけ。  |  Hidden — AIはこの領域の存在自体を知らない。

仕組み
ドメイン（家計 / 健康 / 仕事 / 子育て / 人間関係 / 趣味）× 相手（AI / 家族 / 同僚 / 友人 / 公共）のマトリクス。各セルが4段階のいずれかを取る。アプリごとの権限トグルではなく、OSレベルの統一ダイヤルとして実装する。
シグナル源
  • Identity Layer宣言的な設定 — 「家計: 配偶者にはFull、子どもにはHidden、同僚にはHidden」
  • Learning Layer過去に手動で非公開化した履歴 — 「彼女は前にもこの種のコンテンツを隠した」
具体例
舞は「家計」をAIにFullで開示している。「健康診断の結果」はHidden。
AIは食費の最適化はできるが、コレステロール値に基づく食事提案には踏み込めない。
家計の設定は: 夫にはFull、子どもにはHidden、同僚にはHidden — それぞれ独立に決められる。この構造は、現在のどのOSにも存在しない。
投影ルール
DisclosureがHiddenの領域は、AutonomyをAutoにしてはいけない（開示していないものは委譲できない）。AutonomyがAutoを要求するなら、UIはまずDisclosureを上げる確認を出すこと。Disclosure → Autonomyは、一方向の前提条件である。
禁じ手
禁じ手: 「プライバシー設定 ON / OFF」を2値トグルにする。UI上でHidden × Autoの組み合わせを許可してしまう。明示的な同意なしに、内部で「学習」と称してデータを使う。
重要なインサイト

DisclosureはAutonomyの前提条件だ。 「AIには何も教えたくない」と言いながら「全部自動で任せたい」とは言えない。その組み合わせは論理的に不可能 — そして危険だ。Autonomy Dialが上がる前に、Disclosure Dialが先に開いていなければならない。

トークンはどう組み合わさるか

単独では成立しない — 掛け算で効く

ひとつのトークンだけでAIの振る舞いが決まることはない。山城家の2つのシナリオで、3〜5個のトークンがどう絡み合ってひとつの具体的な判断を生むかを見ていく。

07:02 — 舞が冷蔵庫の前で立ち止まる

— 山城家 · 火曜の朝

Combo 1 — 「お弁当に何を入れる?」 3 tokens × 1 dial
  • ② Cognitive Load平日朝07:02 = 過負荷（カレンダー密度 + 平日パターン）
  • ① Physical State立ったまま、両手はふさがっている
  • ③ Social Exposure家族のみ（プライベート）
  • ⑦ Autonomy Dial朝食領域 = Auto-suggest（提案を出す、確認不要）
→ 結論: 冷蔵庫の画面は1行だけ表示する — 「昨日の残り + 卵焼き」。タップは不要。
Combo 2 — 「いま、塾代の話を表に出していいか?」 3 tokens × 2 dials
  • ③ Social Exposure会議中、画面共有ON（同僚から画面が見えている）
  • ⑤ Form FactorMacBook、会議室TVにミラーリング中
  • ⑥ Feasibility金銭の話は緊急ではない — 夕方まで待てる
  • ⑧ Disclosure Dial家計 = 同僚にはHidden
  • ⑦ Autonomy Dial金銭通知 = Notifyレベル（確認が必要）
→ 結論: 通知を抑制。舞が一人になる19:30に再浮上させる。

重要な観察: 同じ「塾代の通知」が、タイミングと場所で全く別物になる。これを決めるのは単独のトークンではない — 8つのトークンが掛け算で「いま、これを出していいか?」を決定する。

Tokens × Brain

トークンは複数のBrain Layerから引き出される

各トークンは、ひとつのセンサー値ではない — Context Brainの中の複数の記憶レイヤーが連動して出すアウトプットだ。この多層構造の出自を理解しているかどうかが、token-awareなシステムと、ただのルールエンジンを分ける。

レイヤーが各トークンを供給する仕組み

あらゆるBrain — 個人のContext Brainでも、企業のBrainでも — は3つのレイヤーを持つ: Identity Layer（変わらないもの）、Learning Layer（蓄積されていくもの）、Now Layer（いま流動しているもの）。トークンは、必要なレイヤーから引き出される。

Priority Weightが最もわかりやすい例だ: いまの緊急度（Now Layer） + 学習されたトレードオフのパターン（Learning Layer） + 絶対に譲れない原則（Identity Layer）。3つすべてのレイヤーがひとつの複合的な読みを作る。Physical StateはNow Layerが中心。Disclosure DialはIdentity Layerが中心だ。

なぜこれがデザインに効いてくるか

Brainが記憶を保持する。トークンが瞬間を捉える。Rule Engineが判断を下す — 3つすべてが揃って、はじめてAIは反射ではなく判断で動ける。AIが判断の理由を説明するとき、シグナルがどのレイヤーから来たかを正確に指し示せる: 「Learning Layerの記録上、あなたの会議は10:00に終わるので、通知を後ろにずらしました」。

なぜ7ではなく8なのか

7から8へ — Disclosureを独立したトークンに

Context Grammarは7つのトークンから始まった。2026年初頭、Disclosure Dialを独立したトークンに昇格させた — プライバシーをSocial Exposureに埋め込まれた付け足しではなく、設計の一級市民にするためだ。

軸 7トークン時代 8トークン時代（現行）
プライバシー Social Exposureの内側に埋め込み（曖昧） Disclosure Dialとして独立（明示）
Autonomyとの関係 暗黙の前提 「Hidden × Autoは不可能」を明文化
領域ごとの制御 不可 家計 / 健康 / 仕事 / 子育てを別々に開示
相手ごとの制御 不可 家族にはFull、同僚にはHidden
ダイヤルの数 1ダイヤル（Autonomyのみ） 2ダイヤル（Autonomy + Disclosure のペア）

議論の中心: Autonomy Dial（どこまで委譲するか）とDisclosure Dial（どこまで共有するか）は必ずペアで動く。 AIに何も教えないまま「全部任せたい」と言うのは、自分のことを知らないアシスタントに完璧な仕事を期待するのと同じだ。Disclosureを一級の概念として独立させる以外に道はなかった。

実装する人へ

技術的な現実 + どこから始めるか

「8つすべてが今日にも出荷可能」と書いたら嘘になる。各トークンの2026年時点の状態と、推奨される実装順序を以下に示す。

トークン 現実 ステータス 一行サマリ
① Physical State★★★★☆ほぼ実装済みActivity Recognition + Watchセンサー — 今すぐ実装可能
② Cognitive Load★★☆☆☆推定のみ直接測定は不可 — 代理指標による推定
③ Social Exposure★★★★☆ほぼ実装済みVoice ID / 近接 / ミラーリング — 今日すべて読み取れる
④ Priority Weight★★★☆☆一部実装中領域内ならYes、領域横断の衝突解決はこれから
⑤ Form Factor★★★★☆ほぼ実装済みOSがすでに保持。マルチサーフェスへの配信が次の壁。
⑥ Feasibility★★★☆☆一部実装中個別APIはある、複数制約の統合がギャップ
⑦ Autonomy Dial★★★☆☆開発ツールで実装済みClaude Code / Cursorに事例あり、コンシューマ展開はこれから
⑧ Disclosure Dial★☆☆☆☆コンセプト段階領域 × 相手のマトリクスUIは現在のどのOSにも存在しない

推奨される実装順序

1
③ Social Exposureと⑤ Form Factorから始める
どちらも★★★★☆。OSがすでに情報を保持している — ミラーリング状態、デバイスの種類。それを読むだけで「画面共有中は家庭領域の通知を抑制する」が実装できる。ユーザー体験の変化は即時に出る。
2
⑦ Autonomy Dialを、機能ごとの4段階UIとして露出する
Suggest / Confirm / Notify / Auto を、システム全体の単一トグルではなく機能ごとに切り替えられるようにする。エージェント系プロダクト（Claude Code、Cursor）はすでにこの形に標準化している。Disclosureとビジュアル上ペアにして、「両方を一緒に動かす」設計にすると、即座に安心感が立つ。
3
⑧ Disclosure Dialを、領域 × 相手のマトリクスとして実装する
家計 / 健康 / 仕事 / 子育て × 家族 / 同僚 / 友人 / 公共 のグリッドを見せる。各セルでFull / Summary / Existence / Hidden を選ばせる。このひとつのUIがあるだけで、Autonomyを上げることが安全に感じられる — AIが何を知っていて何を知らないかが、ユーザーから見える。
4
② Cognitive LoadはUI上で「推定」と明示する
直接測定していないのだから、正直に書く — 「ビジー・モード（推定）」。常にユーザーが上書きできる手段を用意する: 「いや、空いてる」。これがないと、AIは「分かったふり」をしているように見え、推定を外したときに信頼が崩れる。
5
8つ全部を一度にやる必要はない — シーンごとに3〜4個で十分
ひとつの判断に8つすべてが必要なことはまずない。「朝のお弁当提案」に必要なのは ② + ① + ③ + ⑦ だけ。残りはデフォルトのまま。デザイナーがシーンごとにアクティブなトークンを選ぶ — システム全体の一括ON/OFFスイッチではない。
Q&A

よくある質問

Q1. トークンとBrainは同じものですか?
違います。 トークンはいまの状況 — センサーの読み取り値。Brainは長期の記憶 — 積み上がった知識。「舞はいま会議中」はトークン（瞬間）。「火曜日の朝は舞が必ず一番忙しい」はBrain（パターン）。Rule Engineがトークン × Brainを掛け合わせて、振る舞いを決める。
Q2. Cognitive Loadは本当に測れますか?
直接は測れません。 EEGも脳スキャナーもない。だから推定するしかない: 「平日朝7時 + カレンダー満杯 + 直近1時間で12タスク完了」→ おそらく高負荷。この限界を正直に書くのがContext Grammarの立場だ。「Cognitive Loadを直接測る」と主張するフレームワークは、技術的に間違っている。
Q3. Autonomy Dialはユーザー自身が設定するんですか?
純粋にはそうではありません。 3つの力が決める:
① サービス側のデフォルト — Netflixのレコメンドはすでに高いAutonomyで出荷されている
② AIの自動調整 — 夜間・初回・失敗直後はデフォルトを下げる
③ ユーザーの能動的な変更 — 自分でスライダーを動かす
「ユーザーがゼロから決める」というのは古いUIの前提で、現実には3つの力の合成で決まる。
Q4. Disclosure Dialは既存のプライバシー設定と同じですか?
違います — 粒度が圧倒的に細かい。 既存のプライバシー設定はON / OFFの2値。Disclosure Dialは領域ごと × 相手ごと。たとえば: 舞は「家計」をAIにFull、夫にFull、子どもにHidden、同僚にHidden — それぞれ独立に設定する。このマトリクス構造は、現在のどのOSにも存在しない。
Q5. 各トークンは、ひとつのBrainから来るんですか? 複数からですか?
多くは複数のレイヤーから引き出されます。 Priority Weightは「いまの緊急度（Now Layer）」+「学習されたトレードオフのパターン（Learning Layer）」+「絶対に譲れない軸（Identity Layer）」の合算。Multi-Brainモデルでは、各トークンが「このシグナルはどのレイヤーから来たか」の参照を保持する — だからAIは後から、なぜその判断をしたかを説明できる。
Q6. トークンを持つと、結局何が変わるんですか?
AIの振る舞いがコンテキスト感応的になります。 今日のAI（ChatGPT、Siri）は、あなたがどんな状況でも同じトーンを返す。トークンがあれば、AIはこう動ける: 「舞はいま会議中 — 返信は後で」「颯太がそろそろ寝る — 明るい色は避けよう」。気の利くウェイターと、機械的に皿を運ぶ店員の差だ。

語彙はもう手に入った。
次は、AIがどう記憶するか。

Context Tokensは瞬間を捉える。Brainは瞬間を超えて「その人が誰か」を記憶する。両方が揃ってはじめて、AIは反射ではなく判断で動ける。
