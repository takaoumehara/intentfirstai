Context Grammar — Floor 2

Context Tokens

AIが「空気を読む」ための8つの測定可能な次元。話す前に状況を読む — Context Grammarの語彙。

Context Tokenとは

AIが空気を読むために

AIが状況に応じて動くには、まず「今、何が起きているか」を読む必要がある。Context Tokenはその8つの測定可能な信号だ。優れたウェイターが話しかける前にテーブルを読んでいる、あの直感と同じことをAIに与える。

レストランに例えると

優れたウェイターは、一つも聞かずに8つの信号を同時に読む。テーブルが満席で忙しそう — Cognitive Load高。キャンドルディナーの二人組 — Social Exposure高（デート、同僚ではない）。お客さんが時計をちらちら見ている — Priority Weightは時間、料理の質ではない。カウンター席が狭い — Form Factorがフルコースを制限している。

Context Grammarはこの直感を8つの軸でAIに与える。① Physical State、② Cognitive Load、③ Social Exposure、④ Priority Weight、⑤ Form Factor、⑥ Feasibility、⑦ Autonomy Dial、⑧ Disclosure Dial — それぞれが1つのTokenに対応する。

Two Groups

8 Tokens — 6 Situation + 2 Dials

8つを一気に覚えるのは大変。2グループに分けると即座に意味が通る。世界の状況を読む6つのセンサーと、AIが「どこまで知り、どこまで動くか」を決める2つのダイヤル。

Group A · 6 Situation Tokens
状況センサー

「今、何が起きているか」を6つの軸で測る。外側の事実を数値化するセンサー群。AIが読む入力であり、ユーザーが操作する設定ではない。

  • ① Physical State — 体の状態（歩いてる／運転中／座ってる）
  • ② Cognitive Load — 頭の忙しさ（朝ピーク／低負荷／リラックス）
  • ③ Social Exposure — 周りの目（一人／家族／同僚）
  • ④ Priority Weight — 衝突した時に何が勝つか（時間 vs お金 vs 安全）
  • ⑤ Form Factor — 今どの画面があるか（Watch／Phone／TV／車）
  • ⑥ Feasibility — 今実際に可能なことは何か（在庫・時間・距離）
+
Group B · 2 Relationship Dials
関係性のダイヤル

人とAIの距離感を決める。サービスのデフォルト × AIの調整 × ユーザーの選択 — 3つの力が同時に形を決める。

  • ⑦ Autonomy Dial — どこまでAIに任せるか（Suggest / Confirm / Notify / Auto）
  • ⑧ Disclosure Dial — どこまでAIに教えるか（領域別・人別）
重要な違い

Situation Tokenは「今のあなた」を見る — 瞬間ごとに変わる。Relationship Dialは「あなたとAIの関係」を決める — ゆっくりと育つ。瞬間の状況 + 長期の関係性 = AIの動きが決まる。

8つのTokenを一望する
Overview · 山城家

8つのToken — 山城家の朝で見る

抽象的な定義だけだと忘れる。山城家のMai（母）・Sota（11歳）・Hana（6歳）の日常から各Tokenを拾う。星の数は2026年3月時点の技術リアリティ。

① Physical State ★★★★☆
体が今どんな状態にあるか。歩行・運転・座位・運動中。
山城家 · 7:45 MaiはWatchが「速度6km/h・心拍110」と検出。AIは全通知を停止 — 走りながらは読めない。
② Cognitive Load ★★☆☆☆
頭がどれだけ忙しいか。直接は測れない — 時刻 × カレンダー × 行動パターンから推定するしかない。
山城家 · 7:02 Maiは弁当2つ作りながらHanaの保育園バッグも準備中。AIは「overload」と推定。冷蔵庫に1行だけ表示。タップ操作不要。
③ Social Exposure ★★★★☆
周りに誰がいるか。一人 / 家族 / 同僚 / 不特定多数。8つの中で最も実装が進んでいるToken。
山城家 · 会議中 Maiが会議室のTVにミラーリングした瞬間、AIは家計の通知を消す。「他人がこの画面を見ている」と察知。
④ Priority Weight ★★★☆☆
競合する欲求のうち今は何を優先するか。「時間 vs お金 vs 健康」の衝突解決のため。
山城家 · 夕方 Sotaの塾が遅延。MaiのBrainは「平日は時間 > 食事クオリティ」と学習済み → AIは冷凍ストック夕食 + 19:50駅迎えを提案。
⑤ Form Factor ★★★★☆
今AIが届けられる面（surface）の集合。Watch / Phone / TV / 冷蔵庫 / 車 / Voice / Ambient。
山城家 · 同じ情報 MaiのWatchには「塾迎え19:00」の1行。冷蔵庫には家族全員のタイムライン。CarPlayでは声で「7時に塾」と読み上げ。
⑥ Feasibility ★★★☆☆
そもそも今それは可能か。在庫・時間・距離・天気・お金のどれかが足りなければ不可能。
山城家 · 夕食 「カレー」を提案しかけたが、冷蔵庫に玉ねぎが無く雨で買い物に行けない → 「在庫で作れるパスタ」に切り替え。
⑦ Autonomy Dial ★★★☆☆
どこまでAIに任せるか。Suggest → Confirm → Notify → Autoの4段。サービスのデフォルト × AI調整 × ユーザー選択の3つの力で決まる。
山城家 · リスクで変わる Sotaの靴$48（消耗品・低リスク）= Auto。家族ホテル予約$400 = Confirm。Maiの手術同意 = Suggest（決して自動化しない — Identity Layer宣言）。
⑧ Disclosure Dial ★☆☆☆☆
どこまでAIに自分のことを教えるか。領域別・人別。Autonomyの論理的前提条件（知らせない × 任せる は不可能）。
山城家 · プライバシー Maiは「家計」をAIにFull開示するが「健康診断結果」はHidden。AIは食費の最適化提案はできるが、コレステロール値に踏み込んだ献立は出さない。
星の読み方

★★★★☆ = 今すぐ実装できる — センサーやOS APIがある。★★☆☆☆ = 推定のみ — 直接測定不可。★☆☆☆☆ = コンセプト段階 — 横断的APIが未存在。「Cognitive Loadは測定できる」と書けば嘘になる。Context Grammarは実態を正直に記述する。

技術的詳細

8つのToken — 機構レベルで分解する

各Tokenの仕組み（どう計算するか）、信号源（BrainのどのLayerから来るか）、具体例、投影ルール、禁じ手を順番に整理する。

① Physical State "Are they rushing or relaxed?" ★★★★☆ Mostly shipping
Definition
体が今どんな状態にあるか。歩行・走行・運転・座位・睡眠・運動中。デザイン判断の最初に効く軸 — 状態が読めなければ、内容を変える前に形（form）を変えるべき場面で何もできない。
Mechanism
Activity Recognition API（iOS / Android）が walking / running / driving / still を分類。Galaxy Watch / Apple Watchが心拍・ストレス・睡眠負債を加算。複数信号を1つの「state」に圧縮し、設計判断（出すか出さないか、声か画面か）に渡す。
Signal sources
  • Now Layer加速度センサー、心拍、ジャイロ、CarPlay/Android Auto接続状態
  • Learning Layer「Maiは平日朝7:30〜7:50は必ず駅まで走る」というパターン
  • Identity Layer持病・身体的制約（妊娠中・術後など）
Concrete example
7:45、Maiは駅まで全力ダッシュ中。Watchが「速度6km/h・心拍110」と検出 → AIは通知を全停止し、19:00の塾迎えリマインダーは「電車に座ったあと」に再スケジュール。
逆に土曜の朝、ソファで座位 + 心拍65のときは、家族カレンダーの提案を画面に出してよい。
Projection rule
「読めない」ときほど慎重に。 走行中・運転中は通知を声に切り替える、もしくは抑制する。形を先に変えてから、内容を考える。
Forbidden
禁じ手: 走っている人に長文のリッチ通知を出す。運転中に画面操作を要求する確認ダイアログを出す。「ベル鳴らせば届く」と思い込む設計。
② Cognitive Load "How much mental bandwidth remains?" ★★☆☆☆ Estimation only
Definition
頭がどれだけ忙しいか — 残っている認知帯域。直接は測れない。脳波計を付けてるわけじゃないので、推定するしかない。これがContext Grammarで最も正直さが要求されるToken。
Mechanism
時刻 × カレンダー密度 × 直近10分のアプリ切替回数 × 行動パターン履歴。複数のプロキシを重み付け平均し、3〜5段階の density（minimal / low / medium / high / overload）に丸める。常に「推定値」というメタ情報を付ける。
Signal sources
  • Now Layerカレンダー15分粒度の埋まり具合、直近のタスク完了数、画面切替頻度
  • Learning Layer「平日朝7:00-7:30は必ずoverload」のパターン、過去の「No, I'm free」上書き履歴
Concrete example
平日朝7:02、Maiは弁当2つ作りながらHanaの保育園バッグも準備中。AIはdensity:overloadと推定し、冷蔵庫の画面には「昨日の残り + 卵焼き」と1行だけ表示。タップ操作は不要。
同じMaiでも土曜10:00ならゆっくりレシピ提案を出してよい。
Projection rule
high / overloadでは1画面 1判断。3択以上を出さない。低Cognitive Loadの時にだけ「探索」「学習」系の提案を解禁。AIが「分かったフリ」をして外したら、ユーザーが手動で「No, I'm free」と上書きできるUIが必須。
Forbidden
禁じ手: 「あなたは今high loadです」と断定するUI。推定だと書かずに脳波測定したかのように振る舞う。overload時に複数の選択肢ダイアログを出す。フォールバックを用意しない。
Honest Design Note

Cognitive Loadは8つの中で最も推測的なTokenである。今日、直接測定する手段は存在しない。このTokenに基づくデザイン判断には、必ず適切なフォールバックを用意すべきであり、推定以上の確実性を主張してはいけない。

③ Social Exposure "Who else is watching?" ★★★★☆ Mostly shipping
Definition
いま誰がこの画面・この音声を一緒に見聞きしているか。一人 / 家族 / 同僚 / 不特定多数（カフェ・電車）。8つの中で最も実装が進んでいるToken。
Mechanism
Bluetooth / Wi-Fi近接で他人のデバイスを検出。Voice IDで家族メンバーを区別（Samsung Family Hubは最大6プロファイル対応）。ミラーリング状態（AirPlay / Cast / DeX）をOSから取得。可能ならオンデバイスVisionで人数を推定。
Signal sources
  • Now Layer近接デバイス、Voice ID一致、ミラーリングON/OFF、画面共有ON
  • Identity Layer「家族」「同僚」「友人」の関係マップ — 誰が近くに居るかを意味づけ
Concrete example
Maiが会議室のTVにミラーリングした瞬間、AIは家計の通知を消し、Sotaの塾代の話題は19:30まで遅延配信。Voice IDが「Sotaが居間に居る」と検出すると、Maiのスマホで開いていた「Sotaへの誕生日サプライズ」プランは自動でhidden化。
Projection rule
誰が見ているかで、内容ではなくフィルタを変える。 同僚が居るなら「家計」領域は出さない。子供が居るなら「サプライズ」は出さない。Disclosure Dialの領域設定と掛け算で動く。
Forbidden
禁じ手: 画面共有中に金額・パスワード・健康情報を表示する。家族用デバイスで「個人」スコープの通知を全員に晒す。Voice IDなしで「いつもこの人」と決め打ちする。
④ Priority Weight "When demands collide, what wins?" ★★★☆☆ Partially shipping
Definition
複数の欲求が衝突したとき、今は何を優先するか。「速さ vs 値段 vs 健康 vs 家族の都合」の衝突解決のため。単なる「重要度ランキング」ではなく、競合した瞬間のトレードオフ判定。
Mechanism
2層構造。Layer 1 = 今この瞬間の緊急度（Now Layerから、カレンダー直前度・通知の種類・期限）。Layer 2 = 学習済みのトレードオフパターン（Learning Layerから、「Maiは平日は時間 > 食事のクオリティ」など）。Rule Engineが両者を掛け合わせる。
Signal sources
  • Now Layerカレンダー優先度、メールのflag、通知importance、期限まで残時間
  • Learning Layer過去の衝突解決履歴 — 「同じ状況で何を捨てたか」
  • Identity Layer絶対譲れない軸（アレルギーは食味より勝つ、子供の安全は仕事より勝つ）
Concrete example
Sotaの塾が遅延 → 夕食を早めるか、迎えに行くか。MaiのBrainは「平日は時間 > 食事のクオリティ」と学習済み → AIは「冷凍ストックでパッと夕食、Maiは7:50に駅で迎え」を提案。
別の例：会議が5分後に始まる + 娘の学校から電話 → アレルギーや安全に関わる電話なら「会議に1分遅れる」を選ぶ。Identity Layerが勝つ。
Projection rule
AIは勝手に重みを決めない。学習履歴に基づいて提案する。ユーザーが上書きしたらその選択をLearning Layerに書き戻す。Identity Layerに書かれた軸（安全・健康）は他のどの軸より絶対に勝つ。
Forbidden
禁じ手: ユーザーに「優先順位を1〜5で並べてください」と毎回聞く設計。Identity Layerの軸（アレルギー・既往症）を「学習済みパターン」で上書きしてしまう。
Design Note

Priority Weightには2つのレイヤーがある。今の緊急度（このToken、瞬間ごとに変わる）と、学習済みのトレードオフパターン（Brainに蓄積）。Tokenは「今、何が差し迫っているか」を捉え、Brainは「過去に似た衝突をどう解決したか」を記憶する。

⑤ Form Factor "What surfaces surround them?" ★★★★☆ Mostly shipping
Definition
いまAIが話しかけられる面（surface）の集合。Watch / Phone / Tablet / TV / 冷蔵庫 / 車、それからVoice-only / AR / Ambient（環境）も含む。画面の話だけではない。
Mechanism
OSが常時保持しているデバイス情報 + Continuity / DeX / CarPlay / Castの接続状態。複数面が同時に有効なら、内容ごとに最適な面を選ぶ（dynamic multi-screen allocation）。Voice / Gesture / AmbientもSurfaceの1種として扱う。
Signal sources
  • Now Layer接続中デバイス、画面サイズ、入力モダリティ、CarPlay/AR起動状態
  • Identity Layer所有デバイス・主に使う面（「MaiはWatchを常時装着」）
Concrete example
家族の予定をMaiのWatchに出すと「19:00塾迎え」だけ。同じ情報を冷蔵庫の画面に出すと、家族全員のタイムラインが広がる。同じ情報をCarPlayに出すと、声で「19時に塾」とだけ読み上げる。
Voice-only（Earbuds単独）なら、確認は「Yes / No」だけで完結する形に圧縮する。
Projection rule
面が変われば、情報量を変える。 Watch = 1行、Phone = 段落、Tablet/TV = 並列表示、Voice = 1問1答。面ごとに「同じ情報の別の見せ方」を持つのがContext GrammarのForm Factor。
Forbidden
禁じ手: PhoneのUIをそのままWatchに縮小コピーする。Voiceの応答をPhoneと同じ長文で読み上げる。「Responsive Web」だけで済むと思ってAmbient / Voiceを考えない。
⑥ Feasibility "What's actually possible right now?" ★★★☆☆ Partially shipping
Definition
そもそも今この瞬間、それは実行可能か。在庫・時間・距離・天気・お金・人的リソース — どれかが足りないと不可能。「No」で終わらせず、「代わりに何ができるか」まで返すための判定。
Mechanism
各ドメインのAPI（在庫 / 配送ETA / 天気 / 営業時間 / 残高）から個別フィージビリティを取得 → 複数制約を1つのfeasibility scoreに統合 → 不足があればSubstitution Mode（Exact/Flexible/Exploring/Surprise）と組んで代替案を提示。
Signal sources
  • Now Layer在庫API、天気API、配送ETA、店舗営業状況、家計残高
  • Learning Layer「在庫切れのとき何を代替に選んだか」の履歴 → Substitution Modeの学習
Concrete example
AIが「今夜カレー」を提案しかけたが、冷蔵庫に玉ねぎが無く、雨で買い物に行けない → 提案を「在庫で作れるパスタ」に切り替え。
別例：Maiが「明治ブルガリアヨーグルト」を頼んだが品切れ → Substitution ModeがFlexibleなら「他のブルガリア風ヨーグルト」を勝手に置き換え、Exactなら「今日は無理」と返す。
Projection rule
不可能を「不可能」で終わらせない。 必ず「では何ができるか」を1〜3案添える。Substitution Modeと必ず組で実装する。
Forbidden
禁じ手: 「在庫がありません」だけで終わる。複数制約を見ずに「行けます」と返してから現地で詰む（雨 + 営業時間切れ + 子供同伴を見落とす）。Exact以外のモードで勝手に変な代替をして信頼を失う。
⑦ Autonomy Dial "How much can AI act on its own?" ★★★☆☆ Shipping in dev tools
Definition
AIにどこまで任せるか。Suggest → Confirm → Notify → Autoの4段。これは「ユーザーが自由に決めるトグル」ではなく、3つの力の合成で決まる。
The 4 stages
Stage 1
提案
Stage 2
確認
Stage 3
通知
Stage 4
自動

Suggest — AIが選択肢を見せる、ユーザーが選ぶ。 |  Confirm — AIが1案に決め打ち、実行前にユーザー承認。 |  Notify — AIが実行する、終わってから通知。 |  Auto — AIが静かに実行、通知すらしない。

Mechanism
3つの力で1つのdial値が決まる：
① サービスのデフォルト（NetflixのレコメンドはすでにhighAutonomyで出荷されている）
② AIの調整（夜中・休日・初回利用時はデフォを下げる）
③ ユーザーの能動的変更（明示的にスライダーを動かす）
ドメイン別（家計 / 健康 / 仕事 / 子育て）に独立して持つ。
Signal sources
  • Now Layer金額の大きさ、可逆性、緊急度
  • Learning Layer過去のAI提案の成功率、ユーザーの介入履歴 → trust score
  • Identity Layer「絶対自動化しない領域」の宣言（医療同意・大型契約）
Concrete example
Sotaの靴$48（消耗品・低リスク・前回も同型）= Auto。家族旅行のホテル予約$400 = Confirm。Maiの手術同意書 = Suggest（決して自動化しない、Identity Layer宣言）。
Projection rule
初回は必ずSuggestから始める。track record（成功・失敗の履歴）に応じて段階を上げる。失敗が起きたら1段階下げる（trust drop）。Identity Layerに「絶対自動化しない」と書かれた領域は、track recordがどれだけ良くても上げない。
Forbidden
禁じ手: 「AI自動化 ON / OFF」の二択トグル。初回からAutoで出荷する。失敗してもダイヤルを下げない。Disclosure Dialが低いままAutonomyだけ上げる（次項参照）。
Key Insight

Autonomy Dialはユーザーだけが制御するものではない。3つの力が形を決める。サービスのデフォルト設定、観察された信頼パターンに基づくAIの調整、ユーザーの能動的な選択。Uber Eatsが再注文に許可を求めないのは、サービスのデフォルトがすでに高いAutonomyを前提としているからである。完全な3力モデルは Trust Design →

⑧ Disclosure Dial "How much does AI know about you?" ★☆☆☆☆ Concept stage
Definition
ユーザーがAIにどこまで自分のことを開示するか。領域別 × 人別に独立して持つ。Autonomyの論理的前提条件（知らせない × 任せる は不可能）。
The 4 levels
Level 1
全開示
Level 2
要約
Level 3
存在のみ
Level 4
非開示

Full — 全データをAIに開示。 |  Summary — 集計・要約だけ開示（個別ログは隠す）。 |  Existence — 「そういう領域がある」だけAIに伝える。 |  Hidden — AIに存在自体を隠す。

Mechanism
領域（家計 / 健康 / 仕事 / 子育て / 性 / 趣味 …）× 受け手（AI / 家族 / 同僚 / 友人 / 公開）のマトリクス。各セルがFull / Summary / Existence / Hiddenの4段から1つを取る。OSレベルの統一dialとして実装する。
Signal sources
  • Identity Layer「家計は配偶者にはFull、子供にはHidden」のような宣言的設定
  • Learning Layer過去にユーザーが「これは見せたくない」と非公開化した履歴
Concrete example
Maiは「家計」をAIにFull開示するが、「健康診断結果」はHidden。
AIは食費の最適化提案はできるが、コレステロール値を踏まえた献立変更は提案しない。
家計を「夫にはFull、子供にはHidden、同僚には絶対Hidden」と人別に設定可能。これは既存のOSには存在しない構造。
Projection rule
DisclosureがHiddenの領域ではAutonomyをAutoに上げてはいけない（知らせていないのに任せるのは不可能）。AutonomyがAutoを求めるなら、まずDisclosureを上げるUIを先に出す。Disclosure → Autonomyの順序は不可逆。
Forbidden
禁じ手: 「プライバシー設定 ON / OFF」の二択トグル。DisclosureとAutonomyを独立に動かして、Hidden × Autoの不可能組み合わせを許す。同意なしに「学習」名目でデータを内部利用する。
Key Insight

DisclosureはAutonomyの前提条件である。「AIに何も教えるな」と言いながら「すべてを自動でやれ」とは言えない。その組み合わせは論理的に危険である。Autonomy Dialが前進するには、まずDisclosure Dialが開かなければならない。

組み合わせ

Tokenは1つでは機能しない — 掛け算で意味を持つ

1つのTokenだけではAIの動きは決まらない。山城家の2つのシナリオで、3〜5個のTokenが重なって1つの具体的な判断を生む様子を見る。

朝7:02、Maiが冷蔵庫の前で立ち止まる

— 山城家 · ある火曜の朝

Combo 1 · 「弁当のおかず、何にする？」 3 tokens × 1 dial
  • ② Cognitive Load朝7:02 = ピーク（カレンダー密度 + 平日パターン）
  • ① Physical State立ち作業中、両手は塞がってる
  • ③ Social Exposure家族のみ（プライベート）
  • ⑦ Autonomy Dial朝の食事 = Auto-suggest（提案だけ表示、確認不要）
→ 結論: 冷蔵庫画面に「昨日の残り + 卵焼き」と1行だけ表示。タップ操作不要。
Combo 2 · 「Sotaの塾代の相談、今出していい？」 3 tokens × 2 dials
  • ③ Social Exposure会議中、画面共有ON（同僚が見ている）
  • ⑤ Form FactorMacBook、ミラーリング先は会議室TV
  • ⑥ Feasibility金額の議論は今すぐは不要、夜でも可
  • ⑧ Disclosure Dial家計 = 同僚には非開示の領域
  • ⑦ Autonomy Dial金銭の通知 = Notify（確認させる）レベル
→ 結論: 通知を抑制。19:30、Maiが一人になった時点で再表示。

気づきポイント: 同じ「塾代の通知」でも、出すタイミングと場所が完全に変わる。これは1つのTokenでは決まらない。8つのTokenが掛け算のように作用して、初めて「今この瞬間に出すべきか」が決まる。

Tokens × Brain

TokenはBrainの複数のLayerから算出される

各Tokenは単一センサーの読み取り値ではない。Context Brainの複数のLayerが連携して出す出力だ。この「複数Layer起源」を理解することが、単純なルールエンジンとToken対応システムを分ける。

各LayerがTokenにどう供給するか

すべてのBrain（個人のContext BrainでもEnterpriseのBrainでも）は同じ3つのLayerを持つ: Identity Layer（変わらないもの）、Learning Layer（積み上がるもの）、Now Layer（今流動しているもの）。Tokenはそれぞれ関連するLayerから信号を取る。

Priority Weightが最もわかりやすい例だ: 今この瞬間の緊急度（Now Layer） + 学習済みのトレードオフパターン（Learning Layer） + 絶対譲れない軸（Identity Layer）。3つのLayerが合わさって1つの複合値になる。Physical StateはNow Layerが主な供給源。Disclosure DialはIdentity Layerが主な供給源だ。

設計上の意味

Brainが記憶する。Tokenが瞬間を捉える。Rule Engineが判断する — この3つが組になって初めてAIは「反射」ではなく「判断」ができる。AIが決定を説明する時、どのLayerがどの信号を供給したかを参照できる: 「会議が10時に終わることをLearning Layerが知っていたので、通知を遅延しました。」

なぜ8つか

7つから8つへ — Disclosure Dialが一級市民になった理由

Context Grammarは当初7つのTokenだった。2026年初頭にDisclosure Dialを独立Tokenとして昇格させ、8つになった。プライバシーをTokenの一級市民にするためである。

項目 7-Token時代 8-Token時代（現在）
プライバシー Social Exposureに内包（曖昧） Disclosure Dialとして独立（明示的）
Autonomyとの関係 暗黙の前提 「知らせない × 任せるは不可能」と明文化
領域別の制御 不可能 家計 / 健康 / 仕事 / 子育てを別々に開示できる
人別の制御 不可能 家族には開示、同僚には非開示
ダイヤル数 1 dial（Autonomyのみ） 2 dials（Autonomy + Disclosureが対）

キーポイント: Autonomy Dial（任せる度合い）とDisclosure Dial（教える度合い）は対になっている。AIに何も教えていないのに「全自動でやって」と頼むのは、自分のことを何も知らない執事に「いい感じにやって」と言うようなもの。だからDisclosureはAutonomyの前提条件。独立Tokenに昇格させる必要があった。

実装する人へ

技術リアリティとどこから手をつけるか

8つを「全部いま実装できる」と書いたら嘘になる。2026年3月時点での出荷可能度を1枚にまとめ、推奨アクションを示す。

Token Reality Status One-liner
① Physical State★★★★☆Mostly shippingActivity Recognition + Watchセンサーで実装可
② Cognitive Load★★☆☆☆Estimation only直接測定不可。proxyベースの推定

推奨アクション（実装順）

1
最初に着手すべきは ③ Social Exposure と ⑤ Form Factor
どちらも★★★★☆。OSが既に持っている情報（画面のミラーリング状態、デバイス種別）を読むだけで実装できる。「会議中は通知を抑える」だけでも体感が大きく変わる。
2
次に ⑦ Autonomy Dial の4段を機能ごとのUIに出す
Suggest / Confirm / Notify / Autoを機能ごとに切り替えられるUIを入れる。エージェント系プロダクトでは標準になりつつある（Claude Code / Cursorなど）。DisclosureとセットでUIに見せると一気に「制御できている」感が出る。
3
⑧ Disclosure Dial は「領域 × 人」のマトリクスUIで
家計 / 健康 / 仕事 / 子育て × 家族 / 同僚 / 友人 / 公開のグリッドを見せる。Full / Summary / Existence / Hiddenの4段を選ばせる。これがあるだけで、Autonomyを高くしても「怖くない」感覚になる。
4
② Cognitive Load は「推定値だ」と明示する
直接測定ではないので、「busy mode（推定）」のようにUIに書く。確実に外れる時があるので、ユーザーが手動で「No, I'm free」と上書きできるUIが必要。これがないとAIが「分かったフリ」をして信頼を失う。
5
8つを「全部使う」必要はない — シーンごとに3〜4個で十分
1つの判断で8つ全部を読む必要はない。「朝の弁当提案」なら② + ① + ③ + ⑦で足りる。残りはデフォルト値のまま。設計者はシーンごとに「使うToken」を選ぶだけでいい。
Q&A

よくある質問を整理する

Q1. TokenとBrainは同じ？
違います。 Tokenは今この瞬間の状況（センサー値）。Brainは長期の記憶（蓄積した知識）。
たとえば「今Maiは会議中」はToken（瞬間）、「Maiは毎週火曜の朝が一番忙しい」はBrain（パターン）。Rule EngineがToken × Brainを掛け算して動きを決める。
Q2. Cognitive Loadって本当に測れるの？
直接は測れません。 脳波計を付けてるわけじゃない。だから推定するしかない。「平日の朝7時 + カレンダーが詰まっている + 直近1時間で12個タスクをこなした」= 高いだろう、と。
この限界を正直に書くのがContext Grammarの立ち位置。「測れる」と言い切る他社のフレームワークは、技術的に嘘になる。
Q3. Autonomy Dialはユーザーが自分で決めるんでしょ？
純粋に自分で決めるわけではありません。 3つの力で決まる：
① サービスのデフォルト（NetflixのレコメンドはすでにhighAutonomy）
② AIの調整（夜中はデフォを下げて確認多めにするなど）
③ ユーザーの能動的変更（明示的にスライダーを動かす）
「ユーザーがゼロから決める」と書くのは古いUI教科書の発想。現実は3者の合成である。
Q4. Disclosure Dialと「プライバシー設定」は同じ？
違います、もっと細かい。 既存のプライバシー設定はON / OFFの二択。Disclosure Dialは領域別 × 人別。
たとえばMaiは「家計をAIには開示」「家計を夫には開示」「家計を子供には非開示」「家計を同僚には絶対非開示」を別々に設定できる。これは既存のOSには存在しない構造。
Q5. Tokenは1つのBrainから来るの？それとも複数？
多くは複数のLayerから合算されます。 たとえばPriority Weightは「今この瞬間の緊急度（Now Layer）」+「学習済みのトレードオフパターン（Learning Layer）」+「絶対譲れない軸（Identity Layer）」の合算。
Multi-Brainモデルでは、各Tokenは「どのLayerがソースか」を必ず持つ。AIが「なぜそう判断したか」を後から説明できるように。
Q6. 結局、Tokenがあると何がうれしいの？
AIの動きが「気が利く」ようになります。 今のAI（ChatGPT/Siri）は、相手の状況を見ずに同じトーンで返事をする。
Tokenが読めると「Maiは今会議中だから後で返す」「Sotaは寝る前だから明るい色は避ける」といった状況に応じた振る舞いができる。優れたウェイターと、機械的なファミレス店員の差である。

語彙は揃った。
次は、AIがどう記憶するか。

Context Tokenは「今この瞬間」を記述する。Brainは「あなたが誰か」を瞬間を超えて記憶する。両方が揃って初めて、AIは反応ではなく判断ができるようになる。
